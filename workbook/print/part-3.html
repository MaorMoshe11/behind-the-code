8.3Image ו-container

Image הוא תמונת מצב קפואה של מערכת קבצים: מערכת הפעלה מינימלית של Linux, Python, ה-.venv, הקוד, ופקודת ברירת מחדל. הוא לא משתנה. Container הוא תהליך שרץ מתוך image, עם שכבה דקה משלו שאפשר לכתוב אליה. היחס דומה ליחס בין מחלקה לאובייקט: מ-image אחד מריצים כמה containers שרוצים, וכל אחד מתחיל מאותה נקודה בדיוק. מה שנכתב בתוך container נעלם כשמוחקים אותו. זה מכוון, וזו הסיבה שבסיס נתונים צריך volume (8.6).

במה זה שונה ממכונה וירטואלית? מכונה וירטואלית מדמה מחשב שלם, עם מערכת הפעלה מלאה משלה, ולכן היא כבדה ועולה בדקות. container חולק את הליבה (kernel) של Linux עם המכונה שמריצה אותו, ומבודד רק את הקבצים, התהליכים והרשת. הוא עולה בשניות, ושוקל עשרות מגה-בייט. ב-Windows אין ליבת Linux, ולכן Docker Desktop מריץ מכונת Linux קטנה אחת ברקע (דרך WSL 2), וכל ה-containers חיים בתוכה.

Images מוכנים מגיעים מ-registry, מאגר ציבורי או פרטי. הברירה של Docker היא Docker Hub. השם postgres:17-alpine הוא image בשם postgres עם tag בשם 17-alpine: גרסה 17, על בסיס Alpine Linux הקטן. תמיד מצמידים tag מפורש, מאותה סיבה ש-uv.lock קיים: latest של היום הוא לא latest של עוד חצי שנה.

8.4מתקינים Docker Desktop

Docker Desktop דורש WSL 2 (Windows Subsystem for Linux), הרכיב של Windows שמריץ Linux. פתחו PowerShell כמנהל (קליק ימני על Terminal, Run as administrator):

PowerShell (as administrator)
wsl --install --no-distribution             # turns on WSL 2; skip if wsl --status already works
winget install --id Docker.DockerDesktop -e
  1. הפעילו את המחשב מחדש. בלי זה WSL לא פעיל, ו-Docker Desktop יודיע שהוא לא מוצא אותו.
  2. פתחו את Docker Desktop מתפריט ההתחלה. בהפעלה הראשונה הוא מציג תנאי שימוש ושואל על חשבון; אפשר לדלג על החשבון. חכו שבפינה יופיע Engine running.
  3. רישיון: Docker Desktop חינמי לשימוש אישי, ללימודים, לקוד פתוח ולעסקים קטנים. בחברות גדולות (נכון לכתיבת שורות אלה: מ-250 עובדים או מ-10 מיליון דולר הכנסה בשנה) הוא דורש מנוי בתשלום. בעבודה, שאלו לפני שאתם מתקינים.
  4. Docker Desktop תופס זיכרון גם כשלא משתמשים בו. כשסיימתם לעבוד, סגרו אותו מהאייקון ליד השעון (Quit Docker Desktop).

8.5Dockerfile, שכבות ו-cache

Dockerfile הוא המתכון של ה-image: רשימת הוראות, מלמעלה למטה. זה ה-Dockerfile של הסוכן, ותיצרו אותו בדוגמה המודרכת:

Dockerfile
# The image of the agent's HTTP service: Python, the locked packages, and the code.
FROM python:3.13-slim

# uv, copied from its official image (same version as on your computer).
COPY --from=ghcr.io/astral-sh/uv:0.11.14 /uv /bin/uv

WORKDIR /app

# Packages first: this layer is rebuilt only when pyproject.toml or uv.lock change.
COPY pyproject.toml uv.lock ./
RUN uv sync --locked --no-dev

# Then the code, which changes often.
COPY . .

# Use the packages in .venv without `uv run` (which would also install the dev tools).
ENV PATH="/app/.venv/bin:$PATH" \
    PYTHONUNBUFFERED=1

EXPOSE 8000
# 0.0.0.0: accept connections from outside the container, not only from inside it.
CMD ["uvicorn", "agent.api:create_app", "--factory", "--host", "0.0.0.0", "--port", "8000"]
הוראהמה היא עושה
FROMנקודת ההתחלה: image רשמי של Python 3.13 על Debian מצומצם (slim). ה-Python של השרת נקבע כאן, לא במחשב של מי שבונה
COPY --from=...מעתיקה קובץ מ-image אחר: את uv עצמו. החליפו את 0.11.14 בגרסה ש-uv --version מדפיס אצלכם
WORKDIRתיקיית העבודה מכאן והלאה, גם כשה-container רץ. חשוב ל-alembic.ini, ש-prepend_sys_path = . שלו יחסי (פרק 7)
RUNמריצה פקודה בזמן הבנייה. --locked: בדיוק לפי uv.lock, ונכשל אם הוא לא מעודכן. --no-dev: בלי pytest, ruff ו-mypy
ENVמשתני סביבה קבועים ב-image. PYTHONUNBUFFERED: הדפסות יוצאות מיד, ולא נתקעות בחוצץ
EXPOSEתיעוד בלבד: "השירות מקשיב ב-8000". לא פותח שום דבר
CMDמה רץ כשמפעילים container, אם לא ביקשו משהו אחר. לא רץ בזמן הבנייה

שכבות, ולמה הסדר חשוב

כל הוראה שמשנה קבצים (COPY, RUN) יוצרת שכבה (layer): ההבדל בקבצים לעומת השכבה שמתחתיה. ה-image הוא ערימת השכבות. בבנייה הבאה, Docker בודק כל הוראה: אם היא והקבצים שהיא מעתיקה לא השתנו, הוא לוקח את השכבה מה-build cache ולא מריץ דבר. אבל ברגע שהוראה אחת השתנתה, כל מה שמתחתיה נבנה מחדש.

מכאן הסדר: מה שמשתנה לעיתים רחוקות למעלה, ומה שמשתנה כל הזמן למטה. uv sync מוריד ומתקין 32 חבילות, דקה ויותר. אילו COPY . . היה לפניו, כל שינוי של פסיק בקוד היה מריץ אותו מחדש. כשהוא אחרי COPY pyproject.toml uv.lock בלבד, הוא רץ רק כשהחבילות באמת השתנו. תרגיל 3 מודד את ההבדל.

.dockerignore: מה לא נכנס

הנקודה בסוף docker build -t my-agent . היא ה-build context: התיקייה ש-Docker אורז ושולח למנוע, ומשם COPY . . מעתיק. בלי סינון, נכנסים גם .venv של Windows (שלא יעבוד על Linux), .git, ובעיקר .env עם המפתחות ו-agent.db עם השיחות. image נשלח ל-registry ולשרתים, ומי שמחזיק אותו יכול לקרוא כל קובץ בו. לכן:

גם לא בשורת ENV ANTHROPIC_API_KEY=... ב-Dockerfile: היא נשמרת בשכבה, ו-docker history מראה אותה לכל מי שיש לו את ה-image. סודות מגיעים ל-container כשהוא מופעל, כמשתני סביבה (8.6). פרקים 10 ו-14 יראו איך עושים את זה בשרת.

8.6Ports, volumes ומשתני סביבה

Container מבודד גם ברשת: יש לו כתובת משלו, ו-127.0.0.1 בתוכו הוא הוא עצמו, לא המחשב שלכם. מכאן שני דברים שצריך לחבר במפורש:

  • Port publishing: -p 127.0.0.1:8000:8000 פירושו "חיבור ל-8000 במחשב שלי, רק מהמחשב שלי, יועבר ל-8000 ב-container". בלי 127.0.0.1: בהתחלה, Docker פותח את הפורט לכל הרשת שהמחשב מחובר אליה, כולל ה-Wi-Fi של בית הקפה.
  • להקשיב על 0.0.0.0: uvicorn מקשיב כברירת מחדל על 127.0.0.1, כלומר רק לחיבורים מתוך ה-container עצמו. החיבור שמגיע מבחוץ דרך הפורט לא מגיע אליו, ו-curl מקבל Empty reply from server. לכן --host 0.0.0.0 ב-CMD: "כל כתובת שלי". בתוך container זה בטוח, כי רק מה שפורסם ב--p נגיש מבחוץ. תראו את זה בצעד 3.

Volume הוא תיקייה שמנוהלת על ידי Docker, מחוץ לכל container, ומחוברת לנתיב בתוכו. Postgres כותב ל-/var/lib/postgresql/data; כשהנתיב הזה הוא volume, אפשר למחוק את ה-container, להחליף גרסה, ולהרים חדש, והנתונים שם. אפשרות אחרת היא bind mount, תיקייה מהמחשב שלכם; לבסיס נתונים ב-Windows עדיף volume, מהיר יותר ובלי בעיות הרשאות.

משתני סביבה נכנסים בהפעלה: -e NAME=value לאחד, --env-file .env לקובץ שלם. אותו image בדיוק רץ עם SQLite בזיכרון, עם Postgres מקומי, או עם Postgres בענן, ורק הסביבה משתנה. זה הרעיון של פרק 1, עכשיו בקנה מידה של שרת. ושימו לב: load_dotenv() לא ימצא .env בתוך ה-container, כי .dockerignore השאיר אותו בחוץ. הערכים מגיעים מ-Docker.

8.7docker compose: כמה שירותים בקובץ אחד

אפשר להרים את Postgres ואת ה-API בשתי פקודות docker run ארוכות, ליצור להם רשת משותפת ו-volume ביד, ולזכור להריץ את ה-migrations ביניהן. או לכתוב את כל זה פעם אחת, בקובץ שנכנס ל-git:

compose.yaml
# The agent's service and its database, started together: docker compose up --build
services:
  db:
    image: postgres:17-alpine
    environment:
      # A local development database. Real passwords never go in this file (chapter 10).
      POSTGRES_USER: agent
      POSTGRES_PASSWORD: agent
      POSTGRES_DB: agent
    volumes:
      - pgdata:/var/lib/postgresql/data  # the data lives in a volume, not in the container
    ports:
      - "127.0.0.1:5432:5432"  # only this computer can connect, for tools and scripts
    healthcheck:
      # "Ready" means Postgres accepts connections, not just that the process started.
      test: ["CMD-SHELL", "pg_isready -U agent -d agent"]
      interval: 2s
      timeout: 5s
      retries: 30  # a new database needs time to initialise on its first start

  migrate:
    build: .
    command: ["alembic", "upgrade", "head"]  # a separate step, as in chapter 7
    environment:
      DATABASE_URL: postgresql+psycopg://agent:agent@db:5432/agent
    depends_on:
      db:
        condition: service_healthy

  api:
    build: .
    env_file: .env  # AGENT_API_KEY, CHAT_MOCK and the rest, from your private file
    environment:
      DATABASE_URL: postgresql+psycopg://agent:agent@db:5432/agent  # wins over .env
    ports:
      - "127.0.0.1:8000:8000"
    depends_on:
      migrate:
        condition: service_completed_successfully

volumes:
  pgdata:
  • כל שירות הוא container. db מ-image מוכן; migrate ו-api נבנים מה-Dockerfile שלכם (build: .). migrate מחליף את ה-CMD ב-command משלו.
  • רשת ושמות. compose מחבר את כולם לרשת אחת, שבה כל שירות נגיש בשמו. לכן ב-DATABASE_URL כתוב db, לא 127.0.0.1: מתוך api, 127.0.0.1 הוא api עצמו.
  • סדר. depends_on לבדו מחכה רק שה-container יתחיל. Postgres צריך כמה שניות אחרי שהתחיל כדי לקבל חיבורים, ולכן service_healthy, לפי ה-healthcheck. ו-api מחכה ש-migrate יסתיים בהצלחה. נכשל? api לא עולה בכלל (תרגיל 4). זה הכלל מפרק 7, עכשיו נאכף: האפליקציה לא מריצה migrations, ולא עולה לפניהם.
  • env_file ו-environment. ה-API מקבל את .env שלכם, ו-DATABASE_URL מ-environment גובר עליו. הסיסמה agent כתובה בקובץ כי זה בסיס נתונים מקומי, בלי שום דבר אמיתי. בשרת, לא כך.

9.1הבעיה: main נשבר, ואף אחד לא שם לב

עמיתה מוסיפה לסוכן ניסיונות חוזרים, וצריכה לשם כך חבילה חדשה. היא כותבת אותה ביד ב-pyproject.toml, מריצה uv run pytest, והכול ירוק. היא שומרת ב-commit את הקוד ואת pyproject.toml, פותחת pull request, אתם קוראים את השינוי, הוא נראה טוב, וממזגים. למחרת אתם מושכים את main ומריצים את מה שעבד אתמול:

מה קרה? uv run במחשב שלה עדכן את uv.lock בשקט, והבדיקות עברו מול הקובץ המעודכן. אבל הקובץ המעודכן לא נכנס ל-commit. ב-main יש עכשיו pyproject.toml חדש ו-uv.lock ישן, וה-image (שבונה עם --locked, פרק 8) מסרב. אף אחד לא עשה משהו טיפשי. העמיתה בדקה, אתם קראתם. אבל שניכם בדקתם את התיקייה שלכם, ולא את מה שבאמת נכנס ל-main.

וזה רק המקרה הבולט. בדיקה שנשברת רק על Postgres, ruff ששכחו להריץ, גרסת Python אחרת: כל אחד מהם עובר "אצלי" ונכשל אצל מישהו אחר, מאוחר יותר, כשכבר לא ברור איזה שינוי אשם. הרשימה בסוף פרק 8 (להריץ pytest, ruff, mypy, לבנות את ה-image) נכונה, אבל היא תלויה בזיכרון של אנשים.

הפתרון: מכונה נקייה, שאינה של אף אחד מכם, מורידה את הקוד בדיוק כפי שהוא ב-pull request, ומריצה את כל הבדיקות, בכל פעם, לפני שמותר למזג. לזה קוראים continuous integration, או CI. ואחרי שיש מכונה שבודקת כל שינוי, הצעד הבא טבעי: שהיא גם תארוז ותוציא את הגרסה. זה CD, ונגיע אליו בסוף הפרק.

9.3המילים של pipeline

Pipeline הוא רצף אוטומטי של שלבים שקוד עובר בדרך מ-commit לתוצר. בפרק נשתמש ב-GitHub Actions, ה-CI שמובנה ב-GitHub. יש כלים אחרים (GitLab CI, Jenkins, CircleCI), והמושגים זהים כמעט מילה במילה:

מונחמה זהאצלנו
workflowקובץ YAML אחד שמתאר pipeline. GitHub מוצא אותו בתיקייה .github/workflows/ci.yml, release.yml
event / triggerמה מפעיל אותופתיחה או עדכון של pull request; push ל-main; tag של גרסה
jobקבוצת צעדים שרצה על מכונה אחת. Jobs רצים במקביל, אלא אם כתוב needschecks, image
stepפקודה אחת (run) או action מוכן (uses). רצים לפי הסדר, ועוצרים בכישלון הראשוןuv run ruff check
runnerהמכונה שמריצה job: מכונה וירטואלית חדשה, שנמחקת בסוףubuntu-24.04 של GitHub
actionצעד ארוז לשימוש חוזר, שמישהו כתב ופרסם במאגר ב-GitHubactions/checkout, astral-sh/setup-uv

המילה החשובה בטבלה היא "חדשה". ה-runner לא ראה את הפרויקט שלכם מעולם. אין עליו .venv, אין .env, אין uv.lock שעודכן בשקט. יש עליו רק מה שנמצא ב-git. בדיוק לכן הוא תופס את מה שאתם לא יכולים לתפוס במחשב שלכם.

          - 5432:5432

      - name: Format
        run: uv run ruff format --check

      - name: Tests

שורהמה היא אומרת
on:מתי לרוץ: על כל pull request (כשנפתח, וכל פעם שנוסף לו commit), ועל push ל-main, כדי לדעת ש-main עצמו ירוק אחרי המיזוג
permissionsמה מותר לטוקן האוטומטי של הריצה לעשות במאגר. כאן רק לקרוא. ברירת מחדל מצומצמת היא הרגל טוב (פרק 14)
runs-onעל איזה runner. גרסה מפורשת ולא ubuntu-latest, מאותה סיבה שה-image של Postgres מוצמד ל-17
timeout-minutesבדיקה שנתקעה נעצרת אחרי רבע שעה, במקום לבזבז שש שעות (ברירת המחדל) של דקות ריצה
servicescontainers שעולים לפני הצעדים וחיים לאורך ה-job (סעיף 9.6)
envמשתני סביבה לכל צעדי ה-job

run:פקודה ב-shell של ה-runner (bash). אם היא מסתיימת בקוד יציאה שאינו 0, הצעד נכשל, וה-job נעצר

שימו לב לסדר הצעדים: הזול והמהיר קודם. ruff לוקח שנייה, pytest עשרות שניות. אם יש import מיותר, עדיף לדעת אחרי שנייה. ושימו לב גם למה אין בקובץ: אין שם מפתח API, אין .env, ואין שום ערך שקיים רק במחשב שלכם. הבדיקות רצות על ה-mock, כמו מאז פרק 3.

מאיפה @v7 ו-@v10.3.3?

Action הוא קוד של מישהו אחר שרץ על הקוד שלכם, ולכן מצמידים גרסה. @v7 הוא tag שהמפרסם מזיז לגרסה האחרונה בסדרה 7. @v10.3.3 קבוע. ההצמדה החזקה ביותר היא ל-commit מלא (40 תווים), שאיש לא יכול להזיז; צוותים שמקפידים על אבטחה עושים כך. כדי לראות אילו גרסאות קיימות: git ls-remote --tags https://github.com/astral-sh/setup-uv, או דף ה-Releases של ה-action.

9.5גרסת Python אחת, ו-cache

פרק 8 השאיר סדק: הבדיקות רצו אצלכם על Python 3.12, וה-image על 3.13. CI היה מוסיף גרסה שלישית, מה שיש ב-runner. התיקון הוא לכתוב את הגרסה במקום אחד: קובץ .python-version, שבו כתוב רק 3.13. uv קורא אותו בכל פקודה, אצלכם וב-CI, ומתקין את הגרסה אם חסרה. ה-Dockerfile לא יודע לקרוא אותו, ולכן בדיקה קטנה (בצעד 1) נכשלת אם FROM python:3.13-slim לא תואם. הכלל: מה שחייב להיות זהה בשני מקומות, בודקים במכונה, לא בהערה.

Cache. Runner נקי פירושו גם שכל ריצה מורידה את כל החבילות מחדש. enable-cache: true שומר את התיקייה שבה uv מחזיק חבילות שהורדו, ומחזיר אותה בריצה הבאה. ה-cache נשמר לפי מפתח (cache key) שמחושב מתוכן uv.lock: אותו קובץ, אותו מפתח, החבילות מוכנות. שינוי ב-uv.lock נותן מפתח חדש, ומתחילים מאפס. זה אותו רעיון כמו שכבות ה-Dockerfile בפרק 8: לשמור עבודה שנעשתה, ולזרוק אותה בדיוק כשהקלט שלה השתנה. תרגיל 3 מודד כמה זה חוסך. גם ל-docker build ב-CI אפשר לשמור את שכבות ה-build cache בין ריצות (למשל עם docker/build-push-action); בפרויקט בגודל הזה לא נטרח.

"""One Python version for everything: written once, in .python-version.

uv reads that file on your computer and in CI. The Dockerfile cannot read it, so this
test makes sure the image starts FROM the same version, and that the tests run on it.
"""

import re
import sys
from pathlib import Path

ROOT = Path(__file__).resolve().parent.parent


def pinned_version():
    return (ROOT / ".python-version").read_text(encoding="utf-8").strip()


def test_the_image_uses_the_pinned_python():
    dockerfile = (ROOT / "Dockerfile").read_text(encoding="utf-8")
    base = re.search(r"^FROM python:(\S+)-slim", dockerfile, re.MULTILINE)
    assert base is not None, "the Dockerfile does not start FROM python:<version>-slim"
    assert base.group(1) == pinned_version()


def test_the_tests_run_on_the_pinned_python():
    running = f"{sys.version_info.major}.{sys.version_info.minor}"
    assert running == pinned_version()

4CI במחשב שלכם: scripts/ci_local.py

אפשר להקליד את הפקודות של ה-workflow אחת אחת. אבל אז יש שתי רשימות, וביום שמישהו יוסיף צעד ל-ci.yml, הרשימה שלכם תתיישן. במקום זה, סקריפט שקורא את ci.yml עצמו ומריץ כל צעד run, לפי הסדר, עם ה-env של ה-job:

scripts\ci_local.py
"""Run the commands of a GitHub Actions workflow on this computer, in the same order as CI.

    uv run --locked python scripts/ci_local.py         # every job of .github/workflows/ci.yml
    uv run --locked python scripts/ci_local.py --job image  # one job, by its id in the file

Only `run:` steps run here. `uses:` steps (checkout, setup-uv) prepare GitHub's machine;
on yours, the project folder and your own uv play their part. Services (Postgres) are not
started: start them first (see README). Like CI, it stops at the first step that fails.
"""

import argparse
import os
import subprocess
import sys
import time
from pathlib import Path
from typing import Any

import yaml

DEFAULT_WORKFLOW = Path(".github/workflows/ci.yml")


def run_job(job_id: str, job: dict[str, Any]) -> None:
    """Run the steps of one job; exit with the step's exit code if one fails."""
    print(f"=== job {job_id}: {job.get('name', job_id)}", flush=True)
    if "services" in job:
        print(f"    services, not started here: {', '.join(job['services'])}", flush=True)
    job_env = {name: str(value) for name, value in job.get("env", {}).items()}
    for number, step in enumerate(job["steps"], start=1):
        title = step.get("name") or step.get("uses") or step.get("run")
        if "run" not in step:
            print(f"--- step {number}: {title} (skipped: GitHub only)", flush=True)
            continue
        print(f"--- step {number}: {title}\n    $ {step['run']}", flush=True)
        step_env = {name: str(value) for name, value in step.get("env", {}).items()}
        started = time.monotonic()
        result = subprocess.run(step["run"], shell=True, env={**os.environ, **job_env, **step_env})
        if result.returncode != 0:
            print(
                f"FAILED: step {number} of job {job_id} ended with exit code "
                f"{result.returncode}. The steps after it did not run.",
                flush=True,
            )
            sys.exit(result.returncode)
        print(f"    ok ({time.monotonic() - started:.1f}s)", flush=True)


def main() -> None:
    parser = argparse.ArgumentParser(description="Run a workflow's commands locally.")
    parser.add_argument("workflow", nargs="?", type=Path, default=DEFAULT_WORKFLOW)
    parser.add_argument("--job", help="run only this job")
    args = parser.parse_args()
    workflow = yaml.safe_load(args.workflow.read_text(encoding="utf-8"))
    jobs: dict[str, dict[str, Any]] = workflow["jobs"]
    if args.job and args.job not in jobs:
        sys.exit(f"No job {args.job!r}. The jobs are: {', '.join(jobs)}")
    for job_id, job in jobs.items():
        if args.job in (None, job_id):
            run_job(job_id, job)
    print("All steps passed.")


if __name__ == "__main__":
    main()

9.10גרסאות, tags ו-releases

שאלו את הפרויקט מה הגרסה שלו, ותקבלו שתי תשובות: pyproject.toml אומר 0.1.0 מאז פרק 1, ו-api.py אומר 0.8.0, כי כל פרק שינה אותו ביד. ומשתמש שמדווח על באג "בגרסה של יום שלישי" לא אומר לכם כלום. Release הוא תשובה לשאלה "מה בדיוק רץ אצל מי": מספר אחד, commit אחד, image אחד, ורשימה של מה השתנה.

Tag ב-git הוא שם קבוע ל-commit אחד: git tag -a v0.9.0 -m "my-agent 0.9.0" (-a: tag עם מחבר, תאריך והודעה). בניגוד לענף, הוא לא זז. git push origin v0.9.0 שולח אותו, כי git push רגיל לא שולח tags. Changelog הוא קובץ CHANGELOG.md, שבו כל גרסה מקבלת סעיף: מה נוסף, מה השתנה, מה תוקן, במילים של מי שמשתמש בסוכן ולא של מי שכתב את ה-commits. כל pull request מוסיף שורה תחת ## [Unreleased], וב-release הסעיף הזה מקבל מספר ותאריך.

ה-workflow השני רץ רק כשמגיע tag של גרסה:

.github/workflows/release.yml
# Release: runs when a version tag (v1.2.3) is pushed, never on a pull request.
# Builds the image, tags it with the version, pushes it to GitHub's registry (ghcr.io)
# and creates a GitHub release with the notes from CHANGELOG.md.
name: Release

on:
  push:
    tags: ["v*.*.*"]

permissions:
  contents: write  # to create the GitHub release
  packages: write  # to push the image to ghcr.io

jobs:
  release:
    name: Release ${{ github.ref_name }}
    runs-on: ubuntu-24.04
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@v7
      - uses: astral-sh/setup-uv@v10.3.3
        with:
          version: "0.11.14"
      - name: Check the tag, and take the notes from CHANGELOG.md
        run: uv run --locked python scripts/release_notes.py "$GITHUB_REF_NAME" > notes.md
      - name: Name the image
        # ghcr.io/<owner>/<repo>:<version>, lowercase as the registry requires; v0.9.0 -> 0.9.0
        run: echo "IMAGE=ghcr.io/${GITHUB_REPOSITORY,,}:${GITHUB_REF_NAME#v}" >> "$GITHUB_ENV"
      - name: Build
        run: docker build -t "$IMAGE" .
      - uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}  # made by GitHub for this run only
      - name: Push
        run: docker push "$IMAGE"
      - name: Create the GitHub release
        run: gh release create "$GITHUB_REF_NAME" --title "$GITHUB_REF_NAME" --notes-file notes.md
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
  • הצעד הראשון שומר על הדלת. scripts/release_notes.py (תכתבו אותו בתרגיל 5) נכשל אם ה-tag לא תואם את הגרסה ב-pyproject.toml, או אם אין לה סעיף ב-CHANGELOG.md. Tag שגוי עוצר כאן, לפני שנבנה דבר.
  • ה-image מקבל את מספר הגרסה כ-tag, ונשלח ל-registry של GitHub, ghcr.io. מעכשיו שרת שמריץ my-agent:0.9.0 מריץ בדיוק את ה-commit הזה. $GITHUB_REF_NAME ו-$GITHUB_REPOSITORY הם משתנים ש-GitHub מגדיר בכל ריצה; ${...,,} ו-${...#v} הם תחביר של bash להקטנת אותיות ולהסרת ה-v.
  • שמרני בכוונה: רק tag מפעיל אותו, לא כל push; רק GITHUB_TOKEN של הריצה, בלי סיסמה של אדם; ואין latest, שהיה זז מתחת לרגליים של מי שמשתמש בו. אחרי ה-push הראשון, בדקו בדף ה-Package במאגר מי רשאי לראות את ה-image.

למה לא לבדוק את בסיס הנתונים גם ב-liveness? כי אז Postgres שנפל לדקה גורם לכל העותקים של השירות להיות מופעלים מחדש, שוב ושוב, ואף אחד מהם לא מתקן כלום. הפעלה מחדש עוזרת רק לבעיה שבתוך התהליך.

מי שואל את השאלות? מערכת שמריצה containers (orchestrator, כמו Kubernetes או שירות ענן) שואלת את שתיהן בנפרד ופועלת לפי הטבלה. Docker לבד פשוט יותר, ושני כלים שלו נכנסים לפרק:

  • HEALTHCHECK ב-Dockerfile: פקודה ש-Docker מריץ בתוך ה-container כל כמה שניות. שלושה כישלונות ברצף, והסטטוס הופך ל-unhealthy. Docker רק מדווח (ב-docker ps, וב-docker compose up --wait שמחכה ל-healthy); הוא לא מפעיל מחדש בגלל זה. נחבר אותו ל-/ready.
  • Restart policy ב-compose: restart: unless-stopped מפעיל מחדש container שהתהליך שלו יצא, עד שמישהו עוצר אותו ביד. זה בדיוק המקרה של השירות שלנו כשבסיס הנתונים לא זמין בהפעלה: make_engine נכשל, uvicorn יוצא, ו-Docker מנסה שוב, עד שבסיס הנתונים חוזר.

def read_secret(name: str) -> str | None:
    """A secret from the file named in NAME_FILE (how secret stores hand them over), or NAME."""
    path = os.getenv(f"{name}_FILE")
    if path:
        try:
            return Path(path).read_text(encoding="utf-8").strip() or None
        except OSError as error:
            raise ConfigError(f"{name}_FILE is {path!r}, which cannot be read.") from error
    return os.getenv(name) or None


def read_app_env() -> str:
    """APP_ENV: local (the default), staging or prod. Anything else is a typo, so stop."""
    app_env = os.getenv("APP_ENV", "local")
    if app_env not in ENVIRONMENTS:
        raise ConfigError(f"APP_ENV must be one of {', '.join(ENVIRONMENTS)}, got {app_env!r}.")

def database_url() -> str:
    """DATABASE_URL, with the password from DATABASE_PASSWORD(_FILE) when that is set.

    The URL says where the database is (configuration); the password is a secret.
    """
    url = os.getenv("DATABASE_URL")
    if url is None:

            # A server must never fall back to a SQLite file inside its container.
            raise ConfigError("DATABASE_URL is not set. Outside local, it is required.")
        url = DEFAULT_DATABASE_URL

    if password:
        url = make_url(url).set(password=password).render_as_string(hide_password=False)
    return url

"""The container's health check: exit 0 when the service is ready, 1 when it is not.

Docker runs it inside the container, every few seconds (HEALTHCHECK in the Dockerfile).
"""

import sys
import urllib.error
import urllib.request

READY_URL = "http://127.0.0.1:8000/ready"


def main() -> None:
    try:
        # A health check that hangs is worse than one that fails: always a timeout.
        with urllib.request.urlopen(READY_URL, timeout=3) as response:
            print(f"ready ({response.status})")
    except urllib.error.HTTPError as error:  # the service answered: 503, not ready
        sys.exit(f"not ready ({error.code})")
    except OSError as error:  # no answer at all: the process is down or stuck
        sys.exit(f"no answer: {error}")


if __name__ == "__main__":
    main()

    parser = argparse.ArgumentParser(description="Deploy one environment and check it.")
    parser.add_argument("environment", choices=["staging", "prod"])
    parser.add_argument("--skip-migrations", action="store_true", help="for a rollback")
    args = parser.parse_args()
    env_file = DEPLOY / f"{args.environment}.env"
    config = read_env_file(env_file)
    version, base = config["IMAGE_TAG"], f"http://127.0.0.1:{config['API_PORT']}"
    compose = ["docker", "compose", "-p", f"my-agent-{args.environment}"]
    compose += ["-f", str(DEPLOY / "compose.yaml"), "--env-file", str(env_file)]

    print(f"=== deploy my-agent:{version} to {args.environment}", flush=True)
    if args.skip_migrations:
        print("--- 1. migrations: skipped", flush=True)
    else:
        print("--- 1. migrations, with the new image", flush=True)
        run([*compose, "run", "--rm", "migrate"])
    print("--- 2. start the new containers, and wait until they are healthy", flush=True)
    run([*compose, "up", "-d", "--wait", "--wait-timeout", "120"])
    try:
        print("--- 3. /ready reports the new version", flush=True)
        ready = call("GET", f"{base}/ready")
        print(f"    {ready}", flush=True)
        if ready["version"] != version:
            sys.exit(f"FAILED: {args.environment} runs {ready['version']}, not {version}.")
        print("--- 4. smoke test: one message, then delete the conversation", flush=True)
        key = (DEPLOY / "secrets" / args.environment / "agent_api_key.txt").read_text().strip()
        reply = call("POST", f"{base}/chat", key, {"message": "smoke test"})
        call("DELETE", f"{base}/conversations/{reply['conversation_id']}", key)
        print(f"    ok: {reply['reply']}", flush=True)

        sys.exit(f"FAILED: {error}")

SQLite, שעליו רצות הבדיקות, לא אוכף אורך של VARCHAR; Postgres אוכף. לכן הבדיקות ירוקות, ה-health check ירוק, ה-smoke test (הודעה קצרה) ירוק, וכל הודעה ראשונה מעל 200 תווים נכשלת. זה בדיוק מה ש-staging בשבילו: סביבה שדומה ל-prod (Postgres, הגדרות, רשת) ולא למחשב שלכם. ($staging הוא מערך של ארגומנטים, ו-@staging פורש אותו בתוך הפקודה. כך לא מקלידים אותם שוב ושוב.)

קודם חוזרים, אחר כך חוקרים. Rollback הוא פריסה של הגרסה הקודמת, שה-image שלה עדיין קיים: git revert --no-edit HEAD מחזיר את IMAGE_TAG=0.10.0, ו-deploy.py staging:

שניות, וגרסה 0.10.0 חזרה, על בסיס נתונים של 0.10.1. היא עובדת כי בפרק 7 החלטנו ש-check_schema רק מזהיר על revision חדש ממנו, ובעיקר כי 0006 היה expand: עמודה חדשה שאפשר להתעלם ממנה. לו 0.10.1 הייתה מוחקת או משנה שם של עמודה שגרסה 0.10.0 משתמשת בה (contract), לא הייתה דרך חזרה מהירה. לכן contract נכנס רק בגרסה מאוחרת, אחרי שברור שהגרסה הקודמת לא תחזור.

מה עכשיו? Prod לא ראה את 0.10.1 בכלל. התיקון יגיע כגרסה חדשה (0.10.2, roll forward), עם migration שמרחיבה את title, ועם 0006 כפי שהיא, כי היא כבר רצה ב-staging. בדוגמה שלנו הענף היה זמני, ולכן מוחקים אותו (git branch -D try/longer-titles) ומאפסים את staging, שהנתונים בו אינם חשובים: docker compose @staging down -v, ואז deploy.py staging. ב-prod לא מאפסים לעולם. 10.10Infrastructure as code

אפשר להקים את כל זה בלחיצות באתר של הספק. אחרי חצי שנה אף אחד לא יודע מי שינה מה, ו-staging כבר לא דומה ל-prod. Infrastructure as code (IaC) פירושו לתאר את התשתית בקבצים שנמצאים ב-git: עוברים review, יש להם היסטוריה, ומקימים מהם סביבה שנייה זהה. הכלי הנפוץ, שעובד עם כל הספקים, הוא Terraform (ויש לו גרסה פתוחה תואמת, OpenTofu). הנה staging שלנו על Google Cloud, מקוצר. לקריאה בלבד: לא מריצים אותו בפרק.

main.tf (a sketch for reading: no network, database user, IAM or migrations job)
terraform {
  required_providers {
    google = { source = "hashicorp/google" }
  }
}

variable "project" { type = string }
variable "image_tag" { type = string } # the version to run, like IMAGE_TAG

provider "google" {
  project = var.project
  region  = "europe-west1"
}

# The managed database. deletion_protection: `terraform destroy` refuses to delete it.
resource "google_sql_database_instance" "db" {
  name                = "my-agent-staging"
  database_version    = "POSTGRES_17"
  deletion_protection = true
  settings {
    edition = "ENTERPRISE"
    tier    = "db-f1-micro"
  }
}

# A place for a secret. The value is added by a person, never written in this file.
resource "google_secret_manager_secret" "agent_api_key" {
  secret_id = "my-agent-staging-agent-api-key"
  replication {
    auto {}
  }
}

# The service: the same image as on your computer, with staging's settings.
resource "google_cloud_run_v2_service" "api" {
  name     = "my-agent-staging"
  location = "europe-west1"
  template {
    containers {
      image = "europe-west1-docker.pkg.dev/${var.project}/my-agent/my-agent:${var.image_tag}"
      ports {
        container_port = 8000
      }
      env {
        name  = "APP_ENV"
        value = "staging"
      }
      env {
        name = "AGENT_API_KEY"
        value_source {
          secret_key_ref {
            secret  = google_secret_manager_secret.agent_api_key.secret_id
            version = "latest"
          }
        }
      }
      startup_probe {
        http_get { path = "/ready" }
      }
      liveness_probe {
        http_get { path = "/health" }
      }
    }
  }
}

הקובץ מצהיר מה צריך להתקיים (declarative), לא אילו פקודות להריץ. ארבע פקודות מנהלות אותו: terraform init מוריד את ה-provider (הקוד שמדבר עם הספק); terraform plan משווה את הקובץ למה שקיים ומדפיס תוכנית, בלי לשנות דבר; terraform apply מבצע אותה, אחרי אישור; terraform destroy מוחק. בתוכנית, + הוא יצירה, ~ שינוי במקום, -/+ החלפה (מחיקה ויצירה מחדש: לקרוא פעמיים כשזה בסיס נתונים), ו-- מחיקה. Terraform זוכר מה הקים בקובץ state, שיכולים להיות בו ערכים רגישים, ולכן בצוות שומרים אותו באחסון מרוחק מוצפן עם נעילה, ולא ב-git. ומה עם deploy? גרסה חדשה היא image_tag חדש: התוכנית מראה ~ על השירות, וזה הכול. ה-startup_probe וה-liveness_probe הם 10.5 בשפה של Cloud Run.

10.11סיור מודרך בענן (קריאה)

אם תרצו לעלות באמת, כך נראה המסלול על Google Cloud, בקווים כלליים. הוא שמרני בכוונה; בדקו כל צעד בתיעוד העדכני של הספק, כי ממשקים ומחירים משתנים.

  1. פרויקט לכל סביבה, ותקציב קודם. my-agent-staging ו-my-agent-prod כפרויקטים נפרדים: הרשאות וחשבונות נפרדים, וטעות ב-staging לא נוגעת ב-prod. לפני כל משאב, התראת תקציב (budget alert). Cloud SQL, למשל, עולה כסף כל שעה שהוא קיים, גם כשאין שימוש.
  2. Registry. מאגר ב-Artifact Registry, ו-release.yml מפרק 9 דוחף אליו (במקום, או בנוסף, ל-ghcr.io). ההתחברות מ-GitHub Actions נעשית בלי מפתח קבוע, דרך workload identity federation.
  3. בסיס נתונים וסודות. Cloud SQL עם Postgres 17, משתמש agent, והסיסמה, AGENT_API_KEY ו-ANTHROPIC_API_KEY ב-Secret Manager. ל-service account של השירות יש הרשאת קריאה (Secret Accessor) רק לסודות שלו (פרק 14).
  4. Migrations כצעד. Cloud Run job עם אותו image ו-alembic upgrade head, שמריצים לפני השירות: migrate שלנו.
  5. השירות. Cloud Run עם ה-tag, ההגדרות כמשתני סביבה, הסודות כמשתנים או כקבצים (ואז _FILE שלנו עובד כמו שהוא), container_port 8000 (ברירת המחדל שם 8080), ושתי הבדיקות. Cloud Run נותן כתובת HTTPS עם תעודה, ומוסיף עותקים לפי העומס.
  6. Deploy ו-rollback. כל deploy יוצר revision חדש. Rollback הוא העברת התנועה ל-revision הקודם; canary הוא חלוקת תנועה, למשל 90/10. וה-migrations: אותו כלל כמו ב-10.7.
  7. דומיין, וסיום. שם משלכם דרך DNS, אם רוצים. כשמסיימים להתנסות: מחיקת הפרויקט מוחקת את כל מה שבו, ועוצרת את החיוב.

scripts\copy_conversations.py
"""Copy every conversation and message from one database into another, empty one.

For example, from the SQLite file into the Postgres of docker compose:
    uv run python scripts/copy_conversations.py sqlite:///agent.db \
        postgresql+psycopg://agent:agent@127.0.0.1:5432/agent
Both databases must be at the same migration (run `alembic upgrade head` on both first).
"""

import argparse
import sys

from sqlalchemy import Connection, MetaData, create_engine, func, insert, select, text


def revision(connection: Connection) -> str | None:
    """Where the database is in the migration chain."""
    found = connection.scalar(text("SELECT version_num FROM alembic_version"))
    return str(found) if found is not None else None


def copy(source_url: str, target_url: str) -> tuple[int, int]:
    """Copy the rows; return how many conversations and messages were copied."""
    source = create_engine(source_url)
    target = create_engine(target_url)
    tables = MetaData()
    tables.reflect(target, only=["conversations", "messages"])  # the tables as they really are
    conversations = tables.tables["conversations"]
    messages = tables.tables["messages"]

    with source.connect() as reading, target.begin() as writing:  # one transaction
        if revision(reading) != revision(writing):
            sys.exit("The databases are at different migrations. Run alembic upgrade head on both.")
        if writing.scalar(select(func.count()).select_from(conversations)):
            sys.exit("The target already has conversations. Copy only into an empty database.")
        conversation_rows = [dict(row._mapping) for row in reading.execute(select(conversations))]
        message_rows = [dict(row._mapping) for row in reading.execute(select(messages))]
        if conversation_rows:
            writing.execute(insert(conversations), conversation_rows)
        if message_rows:
            writing.execute(insert(messages), message_rows)
        if message_rows and writing.dialect.name == "postgresql":
            # Postgres numbers new messages from a sequence. The copied rows brought their own
            # ids and did not move it, so the next new message would get id 1 again.
            writing.execute(
                text(
                    "SELECT setval(pg_get_serial_sequence('messages', 'id'), MAX(id)) FROM messages"
                )
            )
    source.dispose()
    target.dispose()
    return len(conversation_rows), len(message_rows)


def main() -> None:
    parser = argparse.ArgumentParser(description="Copy conversations between databases.")
    parser.add_argument("source", help="where to read, e.g. sqlite:///agent.db")
    parser.add_argument("target", help="where to write: migrated and empty")
    args = parser.parse_args()
    conversation_count, message_count = copy(args.source, args.target)
    print(f"Copied {conversation_count} conversations and {message_count} messages.")


if __name__ == "__main__":
    main()

"""Print the notes of one release from CHANGELOG.md, after checking that the tag is right.

    uv run python scripts/release_notes.py v0.9.0

Exits with an error when the tag does not match the version in pyproject.toml, or when
CHANGELOG.md has no section for it: then the release workflow stops before it builds.
"""

import argparse
import re
import sys
import tomllib
from pathlib import Path

ROOT = Path(__file__).resolve().parent.parent


def project_version() -> str:
    with (ROOT / "pyproject.toml").open("rb") as file:
        return str(tomllib.load(file)["project"]["version"])


def notes(version: str, changelog: str) -> str | None:
    """The text under '## [version]', up to the next '## ' heading."""
    pattern = rf"^## \[{re.escape(version)}\][^\n]*\n(.*?)(?=^## |\Z)"
    found = re.search(pattern, changelog, re.MULTILINE | re.DOTALL)
    return found.group(1).strip() if found else None


def main() -> None:
    parser = argparse.ArgumentParser(description="Check a release tag and print its notes.")
    parser.add_argument("tag", help="the git tag, for example v0.9.0")
    tag = parser.parse_args().tag
    version = project_version()
    if tag != f"v{version}":
        sys.exit(f"The tag {tag} does not match the version in pyproject.toml ({version}).")
    text = notes(version, (ROOT / "CHANGELOG.md").read_text(encoding="utf-8"))
    if not text:
        sys.exit(f"CHANGELOG.md has no notes for {version}.")
    print(text)


if __name__ == "__main__":
    main()

CONTRIBUTING.md
## Deploying

Staging and prod are described in `deploy/` (README.md, "Deploy"). What runs where is the
`IMAGE_TAG` line of `deploy/<environment>.env`, so every deploy is a commit on `main`.

1. Only an image of a release is deployed: `my-agent:X.Y.Z`, built from the tag `vX.Y.Z`.
   An image is never rebuilt under the same tag.
2. Staging first. Set `IMAGE_TAG`, commit ("Deploy X.Y.Z to staging"), and run
   `uv run python scripts/deploy.py staging`. Then try what changed, as a user would.
3. Prod only after staging was checked, with the same image: set `IMAGE_TAG` in
   `deploy/prod.env`, commit, `uv run python scripts/deploy.py prod`.
4. If `deploy.py` fails, or users see errors after a deploy: roll back first, investigate
   after. `git revert` the deploy commit and run `deploy.py <environment> --skip-migrations`.
   A rollback never runs migrations, and never runs `alembic downgrade` on prod data.
5. Every migration must work with the version before it: expand in one release, contract
   (drop or rename what the old version uses) only in a later one, after the old version
   can no longer come back.
6. A fix after a rollback is a new version (X.Y.Z+1), deployed like any other. It keeps
   every migration that already ran somewhere, unchanged.
7. Secrets live only in `deploy/secrets/` (created by `scripts/make_secrets.py`), never in
   git, in an env file or in the image. A secret that leaked is rotated at once.
