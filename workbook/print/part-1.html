1.3ה-terminal

ה-terminal הוא חלון שבו מקלידים פקודה, לוחצים Enter, ומקבלים תשובה בטקסט. כל הכלים שתפגשו בחוברת (git, uv, docker) מופעלים ממנו. גם שרתים בענן מנוהלים כך, כי אין להם מסך. לכן זה הכלי הראשון.

ב-Windows נשתמש ב-PowerShell. כדי לפתוח: לחצו על מקש Win, הקלידו terminal, ולחצו Enter. תראו שורה כזו:

PowerShell
PS C:\Users\you>

השורה הזו נקראת prompt. החלק C:\Users\you הוא תיקיית העבודה (working directory): המקום שבו אתם "עומדים" כרגע. כל פקודה שתריצו פועלת ביחס אליו. בדוגמאות בחוברת לא מקלידים את PS ...>, רק את מה שבא אחריו.

ב-Windows, התיקיות Desktop ו-Documents מסונכרנות לעיתים קרובות ל-OneDrive. פרויקט קוד מכיל אלפי קבצים קטנים שמשתנים כל הזמן, והסנכרון מאט אותו ולפעמים נועל קבצים. לכן עובדים בתיקייה C:\Users\you\projects, שאינה מסונכרנת.

1.5דוגמה מודרכת: מקובץ לפרויקט

עכשיו עושים את זה ביחד, צעד אחרי צעד. הקלידו את הפקודות בעצמכם. המטרה של הסעיף היא שהידיים שלכם יכירו את התהליך.

בתיקייה שבה נמצאת החוברת יש תיקייה בשם starter ובה שלושה קבצים. העתיקו אותם לתיקיית פרויקט חדשה. החליפו את הנתיב בשורה השלישית בנתיב שבו שמרתם את החוברת:

הפקודה ls צריכה להראות שלושה קבצים: chat.py, debug_me.py ו-.env.example.

2מריצים, ונכשלים

PowerShell

תקבלו את השגיאה מתחילת הפרק: ModuleNotFoundError: No module named 'anthropic'. קראו אותה מלמטה למעלה, כמו כל traceback ב-Python: השורה האחרונה אומרת מה קרה (אין מודול כזה), והשורה שמעליה אומרת איפה (שורה 16, import anthropic).

anthropic היא חבילה חיצונית. היא לא חלק מ-Python, מישהו צריך להתקין אותה. השאלה היא איפה.

3למה לא פשוט pip install?

הדרך המוכרת היא pip install anthropic. זה מתקין את החבילה ב-Python הראשי של המחשב, והיא משותפת לכל הפרויקטים שלכם. זה עובד עד שיש שני פרויקטים:

  • פרויקט א' נכתב מול גרסה 1 של חבילה מסוימת.
  • פרויקט ב' צריך את גרסה 2 של אותה חבילה, שבה שינו שמות של פונקציות.

אפשר להתקין רק גרסה אחת במקום אחד, ולכן אחד הפרויקטים יישבר. הפתרון הוא לתת לכל פרויקט מקום משלו: תיקייה בשם .venv בתוך הפרויקט, שמכילה עותק של Python ואת החבילות של הפרויקט הזה בלבד. זה ה-virtual environment.

4הופכים את התיקייה לפרויקט

PowerShell
uv init --bare
output
Initialized project `my-agent`

נוצר קובץ אחד חדש, pyproject.toml. זו "תעודת הזהות" של הפרויקט. הציגו אותו עם cat pyproject.toml:

pyproject.toml
[project]
name = "my-agent"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = []

שימו לב לשתי שורות: requires-python קובעת איזו גרסת Python הפרויקט דורש (המספר אצלכם עשוי להיות שונה), ו-dependencies היא רשימת החבילות שהוא צריך. כרגע היא ריקה.

למה שני קבצים, pyproject.toml וגם uv.lock?

pyproject.toml אומר מה אתם רוצים: "anthropic, מגרסה 2.10.0 ומעלה". uv.lock מתעד מה קיבלתם בפועל: הגרסה המדויקת של כל אחת מהחבילות שהותקנו. מי שיבנה את הפרויקט מחר, או בעוד שנה, יקבל מה-lock file בדיוק את אותן גרסאות, גם אם בינתיים יצאו חדשות. כך נפתרת הבעיה של "אצלי זה עובד".

6מריצים שוב

PowerShell
uv run python chat.py
output
ANTHROPIC_API_KEY is not set.
Put it in a .env file, or set CHAT_MOCK=1 to run without a key.

התקדמנו: ה-import הצליח, והשגיאה עכשיו אחרת. התוכנית מחפשת משהו בשם ANTHROPIC_API_KEY ולא מוצאת. זה משתנה סביבה, והוא הנושא של הסעיף הבא.

ומה עושה uv run? הוא מריץ את הפקודה שאחריו בתוך ה-.venv של הפרויקט. בלי uv run, הפקודה python chat.py הייתה משתמשת ב-Python הראשי של המחשב, שבו החבילות לא מותקנות. לפני הריצה, uv run גם בודק שה-.venv תואם ל-uv.lock, ומתקן אותו אם לא.

1.6משתני סביבה וקובץ .env

פתחו את chat.py והסתכלו על השורות האלה:

chat.py
load_dotenv()

MODEL = os.getenv("CHAT_MODEL", "claude-opus-5-5")
MOCK = os.getenv("CHAT_MOCK", "0") == "1"

התוכנית לא מחליטה בעצמה עם איזה מודל לעבוד. היא שואלת את הסביבה: "יש משתנה בשם CHAT_MODEL? אם לא, אשתמש בברירת המחדל". משתנה סביבה (environment variable) הוא זוג של שם וערך, שנמצא מחוץ לקוד, וכל תוכנית שרצה יכולה לקרוא אותו.

למה לא לכתוב את הערכים בקוד?

  • סודות. מפתח API הוא כמו סיסמה לחשבון הבנק. הקוד ישותף עם אחרים ויעלה ל-GitHub. אם המפתח כתוב בקוד, הוא משותף יחד איתו. זו אחת הטעויות הנפוצות והיקרות ביותר של מתכנתים מתחילים.
  • אותו קוד, סביבות שונות. במחשב שלכם תרצו מצב mock. בשרת האמיתי תרצו מודל אמיתי ומפתח של החברה. הקוד נשאר זהה ורק הסביבה משתנה. תפגשו את הרעיון הזה שוב בפרק 10, על deployment.

דרך ראשונה: להגדיר ב-terminal

PowerShell

$env:CHAT_MOCK             # print its value
uv run python chat.py

הפעם התוכנית עולה ואפשר לדבר איתה. הקלידו הודעה או שתיים, ואז exit:

output

Type a message and press Enter. Type 'exit' to quit.

you> hello

החיסרון: משתנה שהוגדר כך חי רק בחלון ה-terminal הזה. סגרתם את החלון, והוא נעלם. כדי למחוק אותו בלי לסגור את החלון:

PowerShell
Remove-Item Env:CHAT_MOCK

דרך שנייה: קובץ .env

קובץ .env הוא קובץ טקסט פשוט בתיקיית הפרויקט, עם שורה לכל משתנה. הפונקציה load_dotenv() בתחילת chat.py קוראת אותו והופכת כל שורה למשתנה סביבה. בתיקייה יש כבר תבנית, .env.example. העתיקו אותה:

PowerShell
cp .env.example .env
cat .env
.env
# Your secret key from https://platform.claude.com (not needed in mock mode)
ANTHROPIC_API_KEY=

# Which Claude model to chat with
CHAT_MODEL=claude-opus-5-5

# 1 = fake answers, free, no key needed. 0 = real answers from the API.
CHAT_MOCK=1

הריצו שוב uv run python chat.py. התוכנית עולה במצב mock, בלי שהגדרתם דבר ב-terminal.

שני קבצים, שני תפקידים

.env מכיל את הערכים האמיתיים שלכם, כולל סודות. הוא פרטי: לא שולחים אותו לאף אחד, ולא מעלים אותו ל-git (בפרק 2 תלמדו איך מוודאים את זה). .env.example מכיל רק את שמות המשתנים, בלי ערכים סודיים. הוא משותף, והתפקיד שלו לספר למי שמקבל את הפרויקט אילו משתנים צריך להגדיר.

רוצים תשובות אמיתיות? (רשות)

כל החוברת אפשרית במצב mock. אם תרצו לדבר עם Claude אמיתי, צריך מפתח API, והשימוש עולה כסף לפי כמות הטקסט. לשיחות הקצרות של החוברת מדובר בסכומים קטנים.

  1. היכנסו ל-platform.claude.com, פתחו חשבון והוסיפו אמצעי תשלום.
  2. צרו מפתח בעמוד API Keys והעתיקו אותו. הוא מוצג פעם אחת בלבד.
  3. פתחו את .env, הדביקו את המפתח אחרי ANTHROPIC_API_KEY=, ושנו את CHAT_MOCK ל-0.

כדי להוזיל, אפשר לשנות את CHAT_MODEL בקובץ .env למודל קטן וזול יותר, למשל claude-haiku-5-5. שימו לב שלא נגעתם בקוד כדי להחליף מודל. זה בדיוק היתרון של משתני סביבה.

  2. השתמשו בו בשורה שמדפיסה את התשובה.

2.3מה זה commit, והגדרה חד-פעמית

Commit הוא צילום של כל הפרויקט ברגע מסוים, ולא רק של מה שהשתנה. לכל צילום יש:

  • מזהה (hash): מחרוזת כמו 517d756bba66f14c2df085a654bda1663c0842b1, שמחושבת מהתוכן. בדרך כלל מספיקים שבעת התווים הראשונים, 517d756.
  • מחבר ותאריך: מי שמר ומתי.
  • הודעה (commit message): משפט שאתם כותבים, ומסביר מה השתנה ולמה.
  • הורה (parent): ה-commit שקדם לו. כך נוצרת שרשרת, וזו ההיסטוריה.

כדי ש-git ידע מה לכתוב בשדה "מחבר", צריך להציג את עצמכם פעם אחת לכל מחשב. הדגל --global אומר "לכל הפרויקטים במחשב הזה":

PowerShell
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global core.editor "code --wait"

השורה השלישית חשובה יותר ממה שנראה. יש פקודות git שפותחות עורך טקסט כדי שתכתבו בו הודעה. ברירת המחדל של Git for Windows היא Vim, עורך שמי שלא מכיר לא יודע אפילו איך לצאת ממנו. השורה הזו אומרת ל-git לפתוח את VS Code במקום, ולחכות (--wait) עד שתסגרו את הלשונית.

האימייל יהיה ציבורי

מה שתכתבו ב-user.email נשמר בכל commit, ומי שיקבל את הקוד יראה אותו. אם תעלו פרויקט ציבורי ל-GitHub ולא תרצו לחשוף את האימייל הפרטי, GitHub נותן כתובת חלופית בהגדרות החשבון, בעמוד Emails.

מה הופך commit לטוב

  • שינוי הגיוני אחד. "הוספתי פקודת /reset" ולא "הוספתי /reset, תיקנתי שגיאת כתיב ושיניתי את המודל". כשמשהו נשבר, קל למצוא ולבטל שינוי אחד קטן. קשה לבטל ערבוב.
  • הודעה בציווי, באנגלית, קצרה: Add /reset command, ולא added stuff או fix. נסו להשלים את המשפט "If applied, this commit will...". מה שבא אחריו הוא ההודעה.
  • הקוד עובד בכל commit. מי שיחזור לנקודה הזו בעוד חודש צריך לקבל פרויקט שרץ.

.gitignore משפיע רק על קבצים ש-git עוד לא עוקב אחריהם. אם .env כבר נכנס ל-commit לפני שהוספתם את הכלל, git ימשיך לעקוב אחריו. כדי להפסיק לעקוב בלי למחוק את הקובץ מהדיסק:

אבל זה לא מספיק. ה-commit הישן עדיין קיים בהיסטוריה, ובתוכו המפתח, וכל מי שיש לו עותק יכול להגיע אליו. אם הקוד כבר נשלח לשרת, הנחת העבודה היחידה הבטוחה היא שהמפתח דלף: נכנסים ל-platform.claude.com, מבטלים את המפתח, ויוצרים חדש. קודם מחליפים את המפתח, ורק אחר כך מנקים. לנושא הזה, כולל כלים שסורקים קוד ומחפשים סודות, נחזור בפרק 14 על אבטחה.

שימו לב לכיוון של git revert: הוא לא מוחק את העבר, הוא מוסיף לו. זה נראה פחות "נקי", אבל זו הדרך הבטוחה, כי אם מישהו אחר כבר קיבל את ה-commit הגרוע, ההיסטוריה שלו ושלכם נשארות תואמות. תתרגלו את זה בתרגיל 1.

תפגשו באינטרנט את git reset --hard ואת git commit --amend. שתיהן משנות את ההיסטוריה עצמה. reset --hard גם מוחקת שינויים שלא נשמרו, בלי לשאול ובלי דרך פשוטה להחזיר. הכלל: מותר לשכתב רק היסטוריה שעוד לא שלחתם לשום מקום. מה שכבר נשלח, מתקנים עם revert.

2.7Remote: עותק משותף

עד עכשיו ההיסטוריה נמצאת רק במחשב שלכם. אם הדיסק ייהרס, היא תיעלם יחד איתו, ואף אחד אחר לא יכול לעבוד עליה. Remote הוא עוד עותק של ה-repository, בדרך כלל בשרת, שכולם שולחים אליו ומושכים ממנו.

בעבודה אמיתית ה-remote נמצא ב-GitHub (או בשירות דומה כמו GitLab). בפרק הזה נדמה אותו בתיקייה מקומית, כדי שתוכלו לתרגל הכול בלי חשבון ובלי אינטרנט. מבחינת git אין הבדל: אותן פקודות בדיוק עובדות מול תיקייה ומול שרת.

2.8Branches ו-merge

נניח שאתם מתחילים לבנות פקודה חדשה, וזה לוקח יומיים. בינתיים מישהו מבקש תיקון דחוף. אם כל העבודה נעשית ישר על main, הקוד החצי-גמור שלכם מעורבב בתיקון. Branch (ענף) פותר את זה: קו פיתוח נפרד, שבו עובדים על דבר אחד בלי להפריע לאחרים, ומחברים אותו חזרה רק כשהוא מוכן.

טכנית, branch הוא רק תווית עם שם, שמצביעה על commit. כשאתם שומרים commit חדש, התווית של הענף שאתם עומדים עליו זזה קדימה אליו. לכן יצירה של branch לוקחת אפס זמן ואפס מקום, וזה בסדר גמור ליצור הרבה מהם.

PowerShell
git switch -c feature/reset-command   # create a branch and move to it
git branch                            # list branches; * marks the current one
git switch main                       # move back to main
git merge feature/reset-command       # bring the branch's commits into main
git branch -d feature/reset-command   # delete the label once it is merged

כשעוברים ענף, git מחליף את הקבצים בתיקייה לגרסה של הענף ההוא. אל תיבהלו כשקוד "נעלם" אחרי git switch main: הוא מחכה בענף שלו.

שני סוגים של merge

אם מאז שיצרתם את הענף אף אחד לא שמר commit חדש ב-main, אין מה לאחד. git פשוט מזיז את התווית main קדימה עד הסוף של הענף שלכם. זה נקרא fast-forward, וההיסטוריה נשארת קו ישר. תראו את זה בתרגיל 2.

אם בזמן הזה נוספו commits גם ב-main, יש שני קווים שהתפצלו. git יוצר merge commit: commit מיוחד עם שני הורים, שמחבר את הקווים. כך זה נראה ב-git log --oneline --graph, אחרי תרגיל 3:

output
*   637eb78 (HEAD -> main) Merge remote-tracking branch 'origin/main'
|\
| * 3ac2720 (origin/main, origin/HEAD) Ask for clear answers in the system prompt
* | d68df42 Answer in the user's language
|/
* 405a787 Add /reset command to clear the conversation

קוראים מלמטה למעלה: מ-405a787 יצאו שני קווים, ב-637eb78 הם התאחדו. הכוכביות הן commits, והקווים הם הקשרים להורים.

2.9קונפליקטים: merge conflicts

ברוב המקרים git מאחד לבד: אתם שיניתם את תחילת הקובץ, השותפה את סופו, ו-git לוקח את שני השינויים. הוא נעצר רק כששני הצדדים שינו את אותן שורות בצורות שונות. אז אין לו דרך לדעת מה נכון, והוא מחזיר את ההחלטה אליכם. זה merge conflict. זו לא שגיאה ולא תקלה, זו שאלה.

output
Auto-merging chat.py
CONFLICT (content): Merge conflict in chat.py
Automatic merge failed; fix conflicts and then commit the result.

git כותב את שתי הגרסאות לתוך הקובץ, מסומנות כך:

chat.py
<<<<<<< HEAD
SYSTEM_PROMPT = "You are a friendly assistant. Answer in the language the user writes in."
=======
SYSTEM_PROMPT = "You are a friendly assistant. Keep your answers short and clear."
>>>>>>> origin/main

מה שבין <<<<<<< HEAD לבין ======= הוא הגרסה שלכם. מה שבין ======= לבין >>>>>>> הוא הגרסה שמגיעה מבחוץ. פותרים בארבעה צעדים:

  1. מחליטים מה התוצאה הנכונה: אחת הגרסאות, או שילוב. כאן שני השינויים רצויים, אז משלבים.
  2. עורכים את הקובץ כך שיכיל רק את התוצאה, ומוחקים את שלוש שורות הסימון. VS Code מציג מעל הקונפליקט כפתורים: Accept Current Change (שלכם), Accept Incoming Change (שלהם), Accept Both Changes (שניהם). אפשר להתחיל מהם ולתקן ביד.
  3. מריצים את הקוד. git בודק רק טקסט, לא היגיון. שילוב של שתי שורות תקינות יכול לתת תוכנית שבורה.
  4. מסמנים ושומרים: git add chat.py, ואז git commit.

ואם התבלבלתם באמצע ורוצים לחזור למצב שלפני הניסיון לאחד, git merge --abort מבטל הכול.

איך מקטינים קונפליקטים

קונפליקטים גדלים עם הזמן. ענף שחי שבועיים צובר הרבה שינויים, וגם main צובר, ובסוף מתנגשים בעשרה מקומות. ענף שחי יום, ומתעדכן מ-main לעיתים קרובות, מתנגש לכל היותר במקום אחד. ענפים קטנים וקצרים הם ההרגל החשוב ביותר בפרק.

2.10Rebase

יש דרך שנייה להביא את השינויים של main לתוך הענף שלכם. נניח שפתחתם ענף, שמרתם בו commit, ובינתיים מישהו הוסיף commit ל-main:

output
* 0efd356 (origin/main, origin/HEAD, main) Document the chat commands in README
| * c338483 (HEAD -> docs/contributing) Add CONTRIBUTING.md with the team git workflow
|/
*   637eb78 Merge remote-tracking branch 'origin/main'

merge היה מחבר את הקווים עם merge commit. git rebase main עושה משהו אחר: הוא לוקח את ה-commits של הענף שלכם, ו"משחק אותם מחדש" אחד אחד מעל הסוף של main, כאילו התחלתם לעבוד רק עכשיו:

output
* 4a68c39 (HEAD -> docs/contributing) Add CONTRIBUTING.md with the team git workflow
* 0efd356 (origin/main, origin/HEAD, main) Document the chat commands in README
*   637eb78 Merge remote-tracking branch 'origin/main'

ההיסטוריה ישרה, ואפשר לאחד בעזרת fast-forward. אבל שימו לב למזהה: ה-commit שהיה c338483 הוא עכשיו 4a68c39. התוכן זהה, ההורה השתנה, ולכן זה commit חדש. rebase משכתב היסטוריה.

כלל הזהב של rebase

עושים rebase רק לענף שאתם לבד עובדים עליו. אם כבר שלחתם את הענף ל-remote, אחרי rebase הפקודה git push תיכשל, כי מבחינת השרת ההיסטוריה שלכם סותרת את שלו. במקרה כזה, ורק בענף שלכם, שולחים עם git push --force-with-lease, שמסכים לדרוס רק אם אף אחד אחר לא שלח לענף בינתיים. על main, או על ענף משותף, לא עושים rebase אף פעם.

צוותים שונים בוחרים אחרת, ושתי הגישות לגיטימיות. מה שחשוב הוא שכולם בצוות יעבדו באותה דרך, ושהיא כתובה במקום שכולם רואים. תכתבו מסמך כזה בתרגיל 4.

2.11Pull requests ו-code review

בצוות, אף אחד לא מאחד ענף ל-main לבד ובשקט. במקום זה פותחים pull request (ב-GitLab קוראים לזה merge request): בקשה רשמית לאחד ענף לתוך main, שאחרים קוראים, מעירים עליה ומאשרים. Pull request אינו פקודת git. זה כלי של GitHub שבנוי מעל branches ו-merge.

מחזור החיים

  1. יוצרים ענף מ-main מעודכן, עובדים, שומרים commits.
  2. שולחים את הענף: git push -u origin feature/reset-command.
  3. ב-GitHub פותחים pull request מהענף אל main, עם כותרת ותיאור.
  4. בדיקות אוטומטיות רצות על הקוד. את זה תבנו בפרק 9.
  5. חבר צוות עושה code review: קורא את השינויים בלשונית Files changed, מעיר על שורות ספציפיות, ומסיים באחד משלושה: Comment, Approve או Request changes.
  6. מתקנים לפי ההערות עם commits נוספים באותו ענף. ה-pull request מתעדכן לבד.
  7. אחרי אישור, לוחצים Merge, ומוחקים את הענף.

תיאור טוב

מי שקורא את ה-pull request לא היה בראש שלכם. תנו לו את מה שהוא צריך כדי לבדוק בעשר דקות:

pull request description
## What
Adds a /reset command that clears the conversation and starts a new one.

## Why
Long conversations get slow and expensive. Users had to restart the program to start over.

## How to test
1. Set CHAT_MOCK=1 and run `uv run python chat.py`.
2. Send two messages, then `/reset`, then one more.
3. The mock reply should say "turn 1" again.

## Notes for the reviewer
The help line printed at startup also changed.

איך עושים review

  • האם זה עושה מה שהתיאור אומר? הריצו את הקוד לפי "How to test", אל תסתפקו בקריאה.
  • מה עלול להישבר? קלט ריק, שיחה ארוכה, הודעת שגיאה מה-API.
  • האם נכנס משהו שלא שייך? סודות, הדפסות שנשארו מ-debugging, שינויים שלא קשורים לנושא.
  • האם יבינו את זה בעוד חצי שנה? שמות, הערות, הודעות commit.

כתבו הערות על הקוד ולא על האדם ("השורה הזו מדפיסה את כל השיחה", ולא "שכחת להוריד print"), הסבירו למה, והבחינו בין "חייב לתקן" לבין "הצעה". ומהצד השני: כשמקבלים הערה, עונים על כל אחת, בתיקון או בהסבר. Review הוא שיחה על הקוד, לא מבחן.

2.12אסטרטגיית branching

ברגע שיש יותר מאדם אחד, צריך להסכים על כללים: מאיזה ענף יוצאים, איך קוראים לענפים, ומי מאחד לאן. לזה קוראים branching strategy. שתי הנפוצות:

GitHub flow (או trunk-based)Git flow
ענפים קבועיםרק mainmain ו-develop, ועוד ענפי release/ ו-hotfix/
עבודהענף קצר מ-main, pull request, חזרה ל-mainענף מ-develop, חזרה ל-develop, ומשם בגרסאות מתוכננות ל-main
מתאים לשירותים שמעדכנים הרבה פעמים, רוב הצוותים היוםמוצרים שיוצאים בגרסאות ממוספרות, עם כמה גרסאות נתמכות במקביל

לפרויקט שלכם, ולרוב הצוותים שתפגשו, GitHub flow מספיק: main תמיד עובד, כל שינוי בענף קצר עם שם שמסביר אותו (feature/reset-command, fix/empty-input), ושום דבר לא נכנס ל-main בלי pull request. ב-GitHub אפשר לאכוף את הכלל האחרון בעזרת branch protection, הגדרה שחוסמת push ישיר ל-main ודורשת אישור. בחברות תפגשו לפעמים גם ענפים לפי סביבה, כמו staging. נדבר על סביבות בפרק 10.

2.13תרגילים

התרגילים בונים זה על זה ומספרים סיפור אחד: אתם מוסיפים יכולת לסוכן, מצטרפת שותפה, ואתם לומדים לעבוד יחד. עשו אותם לפי הסדר, באותו repository. פתרונות, כולל הפלט שהתקבל בכל צעד, נמצאים בדף נפרד.

תרגיל 1 · מכונת זמן

מודרך

חלק א: שינוי שעוד לא נשמר.

  1. ב-chat.py, מחקו את כל הפונקציה ask_mock ושמרו. הריצו את הסוכן במצב mock ושלחו הודעה. תקבלו את השגיאה מתחילת הפרק.
  2. הריצו git status ואז git diff --stat. כמה שורות נמחקו?
  3. החזירו את הקובץ: git restore chat.py. הריצו שוב את הסוכן.

חלק ב: commit שכבר נשמר.

  1. הוסיפו את השורה print(messages) מיד אחרי messages.append({"role": "user", "content": user_text}).
  2. שמרו בפקודה אחת: git commit -am "Print the conversation before each request". הדגל -a מכניס ל-staging את כל הקבצים שכבר במעקב ששונו, כך שאין צורך ב-git add נפרד. קבצים חדשים הוא לא מכניס.
  3. הריצו את הסוכן. הרשימה מודפסת לפני כל תשובה, וזה מכוער. בטלו: git revert --no-edit HEAD. הדגל --no-edit מקבל את הודעת ברירת המחדל בלי לפתוח עורך.
  4. הסתכלו על git log --oneline, ושלחו הכול ל-remote עם git push.

מודרך

בפרק 1 ראיתם שהסוכן שולח את כל השיחה בכל תור. כשרוצים להתחיל נושא חדש, צריך היום לסגור את התוכנית. הוסיפו פקודה שמנקה את השיחה, על ענף נפרד.

  1. צרו ענף ועברו אליו: git switch -c feature/reset-command
  2. ב-chat.py, בתוך הלולאה, מיד אחרי הבדיקה if not user_text: והשורה continue שאחריה, הוסיפו:
chat.py
        if user_text == "/reset":
            # Forget the whole conversation and start a new one.
            messages.clear()
            print("Conversation cleared. Starting over.\n")
            continue
  1. עדכנו את שורת ההסבר שמודפסת בהתחלה ל-"Type a message and press Enter. Type '/reset' to start over, 'exit' to quit.\n"
  2. בדקו במצב mock: שתי הודעות, /reset, ועוד הודעה. מה מספר התור בתשובה האחרונה?
  3. שמרו: git add chat.py ואז git commit -m "Add /reset command to clear the conversation". שלחו את הענף, כפי שהייתם עושים לפני pull request: git push -u origin feature/reset-command
  4. חזרו ל-main עם git switch main, ובדקו שהפקודה לא שם: Select-String -Path chat.py -Pattern "/reset" לא מחזיר כלום. הריצו git log --oneline --graph --all.
  5. אחדו: git merge feature/reset-command, ושלחו: git push.
  6. נקו: git branch -d feature/reset-command ו-git push origin --delete feature/reset-command

בינוני

אין לכם שותפה? תהיו שניכם. תיקייה שנייה במחשב, עם שם אחר בהגדרות, מתנהגת בדיוק כמו אדם אחר עם מחשב אחר.

  1. פתחו חלון terminal שני, ובו "הצטרפו לצוות":

  2. בתור דנה: שנו ב-chat.py את SYSTEM_PROMPT ל-"You are a friendly assistant. Keep your answers short and clear.", שמרו עם git commit -am "Ask for clear answers in the system prompt", ושלחו עם git push.

3.3pytest בחמש דקות

בדיקה אוטומטית (automated test) היא פונקציה שמריצה חלק מהקוד ובודקת שהתוצאה היא מה שציפיתם. pytest הוא הכלי המקובל ב-Python להריץ אותן. הוא מחפש קבצים ששמם מתחיל ב-test_, ובתוכם פונקציות ששמן מתחיל ב-test_. בדיקה היא assert רגיל: אם התנאי שקרי, הבדיקה נכשלת ו-pytest מדפיס את הערכים שהיו בו. כל בדיקה רצה בנפרד, וכישלון של אחת לא עוצר את האחרות.

רוב הבדיקות בנויות משלושה שלבים: מכינים קלט (arrange), מריצים (act), ובודקים (assert). מה הופך בדיקה לטובה:

  • השם אומר מה נבדק, כמשפט. כשהיא תיכשל בעוד חצי שנה, השם הוא הדבר הראשון שתקראו.
  • מהירה ודטרמיניסטית: אותה תוצאה בכל הרצה, בלי רשת ובלי שעון. בדיקה שנכשלת "לפעמים" מלמדת את כולם להתעלם מכישלונות.
  • בודקת התנהגות, לא מימוש: "השיחה מתחילה בהודעה של user", ולא "הפונקציה משתמשת ב-slice".
  • ראיתם אותה נכשלת. בדיקה שמעולם לא נכשלה אולי לא בודקת כלום. לכן בדוגמה המודרכת תחזירו את הבאג של פרק 1, בכוונה.

"""The conversation history, and how it is kept short."""

from anthropic.types import MessageParam


def trim_history(messages: list[MessageParam], max_turns: int) -> list[MessageParam]:
    """Keep only the last `max_turns` turns of the conversation.

    One turn is two messages: the user's message and the assistant's reply.
    """
    if len(messages) <= max_turns * 2:
        return messages
    return messages[-max_turns * 2:]

"""Clients that turn a conversation into a reply.

ClaudeClient talks to the real Claude API. MockClient returns fake replies,
costs nothing, and is the one the tests use.
"""

from typing import Protocol

import anthropic
from anthropic.types import MessageParam


class ChatClient(Protocol):
    """Anything that can answer a conversation."""

    def reply(self, messages: list[MessageParam]) -> str: ...


class ClaudeClient:
    """Sends the whole conversation to Claude and returns the reply text."""

    def __init__(
        self, model: str, system_prompt: str, sdk: anthropic.Anthropic | None = None
    ) -> None:
        self.model = model
        self.system_prompt = system_prompt
        # Tests pass a fake SDK client here, so they never touch the network.
        self.sdk = sdk or anthropic.Anthropic()

    def reply(self, messages: list[MessageParam]) -> str:
        response = self.sdk.messages.create(
            model=self.model,
            max_tokens=16000,
            system=self.system_prompt,
            messages=messages,
        )
        if response.stop_reason == "refusal":
            return "(The model declined to answer this request.)"
        return "".join(block.text for block in response.content if block.type == "text")


class MockClient:
    """Returns a predictable fake reply. Free, offline, the same every time."""

    def reply(self, messages: list[MessageParam]) -> str:
        last_message = messages[-1]["content"]
        turn = (len(messages) + 1) // 2
        return f"[mock reply, turn {turn}] You said: {last_message}"

"""The terminal chat: reads what you type and prints the agent's replies."""

import os
import sys

import anthropic
from anthropic.types import MessageParam
from dotenv import load_dotenv
from rich.console import Console

from agent.config import SYSTEM_PROMPT, Settings, load_settings
from agent.history import trim_history
from agent.llm import ChatClient, ClaudeClient, MockClient

console = Console()


def make_client(settings: Settings) -> ChatClient:
    """Pick the mock or the real client, according to the settings."""
    if settings.mock:
        print("Running in MOCK mode - answers are fake, nothing is sent to the API.")
        return MockClient()
    if not settings.api_key:
        print("ANTHROPIC_API_KEY is not set.")
        print("Put it in a .env file, or set CHAT_MOCK=1 to run without a key.")
        sys.exit(1)
    print(f"Chatting with {settings.model}.")
    return ClaudeClient(settings.model, SYSTEM_PROMPT)


def chat_loop(client: ChatClient, settings: Settings) -> None:
    """Run the conversation until the user quits."""
    print("Type a message and press Enter. Type '/reset' to start over, 'exit' to quit.\n")
    messages: list[MessageParam] = []

    while True:
        user_text = input("you> ").strip()
        if user_text.lower() in ("exit", "quit", "bye"):
            break
        if not user_text:
            continue
        if user_text == "/reset":
            # Forget the whole conversation and start a new one.
            messages.clear()
            print("Conversation cleared. Starting over.\n")
            continue

        messages.append({"role": "user", "content": user_text})

        try:
            reply = client.reply(messages)
        # ... the three "except anthropic...." blocks, copied unchanged from chat.py ...

        messages.append({"role": "assistant", "content": reply})
        # Keep only the last turns, so long chats do not get slow and expensive.
        messages = trim_history(messages, settings.max_turns)
        console.print(f"{settings.agent_name}> {reply}\n", style="cyan", markup=False)

    print("Bye!")


def main() -> None:
    load_dotenv()
    settings = load_settings()
    client = make_client(settings)
    chat_loop(client, settings)

"""Integration tests: the whole chat loop, with the mock client."""

from agent.cli import chat_loop
from agent.config import Settings
from agent.llm import MockClient

SETTINGS = Settings(
    model="test-model", mock=True, agent_name="agent", max_turns=2, api_key=None
)


def type_lines(monkeypatch, *lines):
    """Make input() return these lines one by one, as if a user typed them."""
    answers = iter(lines)
    monkeypatch.setattr("builtins.input", lambda prompt: next(answers))


def test_a_short_conversation(monkeypatch, capsys):
    type_lines(monkeypatch, "hello", "how are you", "exit")
    chat_loop(MockClient(), SETTINGS)
    output = capsys.readouterr().out
    assert "agent> [mock reply, turn 1] You said: hello" in output
    assert "agent> [mock reply, turn 2] You said: how are you" in output
    assert output.endswith("Bye!\n")


def test_long_conversation_is_trimmed(monkeypatch, capsys):
    type_lines(monkeypatch, "one", "two", "three", "four", "exit")
    chat_loop(MockClient(), SETTINGS)
    output = capsys.readouterr().out
    # max_turns is 2: the model sees two earlier turns plus the new message.
    assert "[mock reply, turn 3] You said: three" in output
    assert "[mock reply, turn 3] You said: four" in output

  • אפשרות ה-merge: כל אחת לגיטימית אם יש לה סיבה. Squash and merge מתאים כשה-commits בענף הם "ניסיון", "תיקון", "עוד תיקון", ומה שחשוב ב-main הוא commit אחד מסודר. Create a merge commit שומר את כל הצעדים. מה שחשוב הוא לבחור אחת ולכתוב אותה ב-CONTRIBUTING.md.
  • אישור עצמי: GitHub לא מאפשר למי שפתח pull request לאשר אותו. אפשר להעיר (Comment), אבל Approve שמור לאדם אחר. זה בדיוק הרעיון: עוד זוג עיניים.

def trim_history(messages: list[MessageParam], max_turns: int) -> list[MessageParam]:
    """Keep only the last `max_turns` turns of the conversation.

    One turn is two messages: the user's message and the assistant's reply.
    The result always starts with a user message, because the API requires it.
    """
    if max_turns < 1:
        # messages[-0:] would silently return everything, so refuse instead.
        raise ValueError(f"max_turns must be 1 or more, got {max_turns}")
    if len(messages) <= max_turns * 2:
        return messages
    trimmed = messages[-max_turns * 2 :]
    if trimmed[0]["role"] != "user":
        # The cut fell between a question and its answer: drop the orphan answer.
        trimmed = trimmed[1:]
    return trimmed
