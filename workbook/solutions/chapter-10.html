שלב 1: /health ענה 200 ו-/ready ענה 503. התהליך חי, אבל אין לו איך לשרת צ'אט. אחרי שלושה כישלונות של ה-HEALTHCHECK הסטטוס הפך ל-unhealthy, ו-Docker לא עשה שום דבר מעבר לזה: הוא רק מדווח. (db לא מופיע ב-ps כי הוא עצור; ps -a מראה גם אותו.)

שלב 2: בהפעלה, make_engine בודק את ה-migrations ונכשל, uvicorn יוצא, ו-restart: unless-stopped מפעיל אותו שוב. ארבע הפעלות ב-25 שניות; Docker מאריך את ההמתנה בין ניסיונות, כדי לא לשרוף מעבד. בשלב 3 בסיס הנתונים חזר, ההפעלה החמישית הצליחה, ואף אחד לא נגע בשירות. הסוף הטוב הזה הוא בזכות ה-restart policy; בלעדיה ה-container היה נשאר Exited (1).

ה-orchestrator: על liveness שנכשל הוא מפעיל מחדש את העותק. על readiness שנכשל הוא מוציא אותו מה-load balancer, ומחזיר אותו כשהבדיקה עוברת. בשלב 1 הוא היה משאיר את התהליך חי (/health 200) ומפסיק לשלוח אליו בקשות (/ready 503), וזו בדיוק ההתנהגות הנכונה כשבסיס הנתונים נפל: הפעלה מחדש לא הייתה מתקנת כלום.

הוא נעצר בצעד 2. אבל עד אז compose כבר החליף את ה-container הטוב בחדש, שלא עולה: מהרגע הזה ועד התיקון, staging לא ענה בכלל. ב-recreate אין "הישן ממשיך לשרת בינתיים". ב-prod זו הפסקה עד שמישהו שם לב ומתקן. 5לקרוא Terraform

  1. בשום מקום. הקובץ יוצר את המקום לסוד (google_secret_manager_secret) ומפנה אליו (secret_key_ref, version = "latest"). הערך מוכנס בנפרד, על ידי אדם עם הרשאה. אילו היה בקובץ, הוא היה ב-git, ב-plan וב-state.
  2. אף שורה בקובץ: image_tag הוא משתנה, וגרסה חדשה היא terraform plan -var image_tag=0.10.1 (או קובץ staging.tfvars ב-git, כמו staging.env שלנו). התוכנית: ~ אחד, עדכון במקום של google_cloud_run_v2_service.api, ושינוי אחד בתוכו: ה-image. בסיס הנתונים והסוד לא זזים.
  3. הוא ייכשל על בסיס הנתונים, בגלל deletion_protection = true. כדי למחוק צריך קודם לשנות את השורה ל-false ולעשות apply: צעד מכוון, שעובר review. Terraform מוחק בדיוק מה שכתוב; ההגנה קיימת כי destroy בחלון הלא נכון מוחק את prod. (גם לשירות Cloud Run יש הגנה דומה, שבגרסאות חדשות של ה-provider פועלת כברירת מחדל.)
  4. חיבור והרשאות: DATABASE_URL, משתמש ובסיס נתונים (google_sql_user, google_sql_database), הסיסמה כסוד נוסף, דרך להגיע (חיבור Cloud SQL לשירות, או רשת פרטית), service account עם הרשאה לקרוא את הסודות, ו-job של migrations. הכותרת של הקובץ אומרת שהם הושמטו.
  5. אותו קוד, משתנים אחרים: הפכו את השמות הקבועים (my-agent-staging, "staging") למשתנה environment, ו-apply בפרויקט נפרד עם prod.tfvars. לכל סביבה state משלה. בדיוק deploy/compose.yaml עם שני קובצי .env.

CONTRIBUTING.md
## Deploying

Staging and prod are described in `deploy/` (README.md, "Deploy"). What runs where is the
`IMAGE_TAG` line of `deploy/<environment>.env`, so every deploy is a commit on `main`.

1. Only an image of a release is deployed: `my-agent:X.Y.Z`, built from the tag `vX.Y.Z`.
   An image is never rebuilt under the same tag.
2. Staging first. Set `IMAGE_TAG`, commit ("Deploy X.Y.Z to staging"), and run
   `uv run python scripts/deploy.py staging`. Then try what changed, as a user would.
3. Prod only after staging was checked, with the same image: set `IMAGE_TAG` in
   `deploy/prod.env`, commit, `uv run python scripts/deploy.py prod`.
4. If `deploy.py` fails, or users see errors after a deploy: roll back first, investigate
   after. `git revert` the deploy commit and run `deploy.py <environment> --skip-migrations`.
   A rollback never runs migrations, and never runs `alembic downgrade` on prod data.
5. Every migration must work with the version before it: expand in one release, contract
   (drop or rename what the old version uses) only in a later one, after the old version
   can no longer come back.
6. A fix after a rollback is a new version (X.Y.Z+1), deployed like any other. It keeps
   every migration that already ran somewhere, unchanged.
7. Secrets live only in `deploy/secrets/` (created by `scripts/make_secrets.py`), never in
   git, in an env file or in the image. A secret that leaked is rotated at once.
