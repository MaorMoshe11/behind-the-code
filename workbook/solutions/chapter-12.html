בלי DLQ: הודעה שבורה תישבר בכל ניסיון. אם ה-worker זורק שגיאה בלי commit, אחרי הפעלה מחדש הוא יקבל אותה שוב, וייפול שוב, לנצח. כל האירועים שאחריה באותה partition לא יטופלו, וה-lag רק יגדל. להודעה כזו קוראים poison message. וגם אסור פשוט לדלג עליה בשקט: אולי היא סימן לבאג אצל מי ששלח. ה-DLQ שומר אותה למי שיבדוק.

עם שניים, Kafka חילק מחדש (rebalance): אחד קיבל שתי partitions, השני אחת, וכל אירוע טופל בדיוק אצל מי שמחזיק את ה-partition שלו. עם ארבעה, אחד קיבל אפס: הוא רץ, מחובר, ולא עושה כלום. Partition אחת נקראת בתוך קבוצה בידי צרכן אחד בלבד, כי זו הדרך לשמור על הסדר. לכן מספר ה-partitions הוא התקרה של המקביליות בקבוצה, ובוחרים אותו מראש עם מרווח (להוסיף partitions אחר כך אפשר, אבל זה משנה לאן כל מפתח הולך, ושובר את הסדר של מפתחות קיימים לתקופת המעבר). ובשקט: שני ה-workers כתבו לאותו קובץ SQLite ב-volume משותף, וזה עבד כי הכתיבות קטנות; בשירות אמיתי היו כותבים ל-Postgres.

tests\test_saga.py
def test_a_failure_after_the_notes_were_deleted_restores_them(world, monkeypatch):
    service, notes, conversations, conversation_id = world

    def broken_delete(conversation_id):
        raise RuntimeError("the chat's database is down")

    monkeypatch.setattr(conversations, "delete", broken_delete)
    with pytest.raises(RuntimeError):
        run_saga("delete", delete_conversation(conversations, notes, conversation_id))
    # Both compensations ran: the notes are back (new notes: new ids), and so is the chat.
    assert [note["text"] for note in service.notes] == ["buy milk", "call Dana"]
    assert [note["id"] for note in service.notes] == ["n3", "n4"]
    assert conversations.title(conversation_id) == "hello"

הסדר: קודם שחזור ההערות (הצעד השני), אחר כך החזרת השיחה מהארכיון (הראשון): מהחדש לישן, כך שכל תיקון רואה את העולם כפי שהיה אחרי הצעד שלו. המזהים השתנו כי השחזור הוא פעולה חדשה, POST, ולא ביטול של המחיקה: שירות ההערות לא שמר את הישנות. מי שהחזיק מזהה של הערה (קישור, או בפרק 18 סוכן שזכר note_id) יקבל 404. אם זה חשוב, שירות ההערות צריך מחיקה רכה (deleted_at) ופעולת undelete אמיתית. המפתח נגזר מהמזהה הישן כדי שהשחזור עצמו יהיה idempotent: אם הוא נכשל באמצע ומנסים שוב, ההערות ששוחזרו כבר מקבלות את עצמן בחזרה (200) ולא נוצרות פעמיים. מפתח אקראי היה חדש בכל ניסיון.

6תכנון outbox

הסעיף ב-checkpoints\chapter-12\docs\architecture.md:

docs\architecture.md (the new section)
## Plan: an outbox for the events (not built yet)

1. Migration: a table `outbox` (id, topic, key, payload JSON, created_at, sent_at NULL).
2. `Conversations.send()` and the delete saga's last step add the event row in the same
   transaction as the messages: the event exists if and only if the change was committed.
3. A relay process (like the worker: same image, `python -m agent.relay`) reads unsent rows
   oldest first, publishes each with `acks=all`, waits for the confirmation, then sets
   `sent_at`. If it dies between the two, the row is published again: consumers must stay
   idempotent (they are: `event_id`).
4. A job deletes sent rows older than a week. Kafka's own transactions do not replace this:
   they cover Kafka writes only, not the chat's Postgres.

ההבטחה: at least once. האירוע לא יאבד, כי הוא שמור ב-Postgres יחד עם השינוי, אבל הוא עלול להישלח פעמיים, אם ה-relay נופל בין השליחה לסימון. ה-worker כבר מוכן לזה: הוא זוכר כל event_id, ואירוע שנשלח פעמיים נספר פעם אחת. זה הסיבה שבונים צרכנים idempotent מהיום הראשון: כל שיפור באמינות של הצד השולח מוסיף כפילויות, לא מוריד אותן.

מחיקה ב-choreography? אפשר: הצ'אט מפרסם conversation.deleted, ושירות ההערות מוחק כשהוא שומע. זה עובד יפה כשהצעד הבא לא יכול להיכשל מסיבה עסקית, וכל מה שחסר הוא שהשירות יהיה למעלה: האירוע יחכה לו. אבל כאן רצינו "הכול או כלום" מול המשתמש, עם תשובה ברורה עכשיו ותיקון כשמשהו נכשל, וזה קל יותר לכתוב, לבדוק ולקרוא כשהזרימה במקום אחד. תשובה סבירה אחרת: מחיקה רכה מיד, והודעה שמוחקת את ההערות מאוחר יותר; זה מוותר על התשובה המיידית ומרוויח שהמחיקה לעולם לא נכשלת בגלל שירות ההערות. שתיהן טובות אם הנימוק כתוב.
