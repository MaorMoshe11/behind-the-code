כל שש ההערות נשמרו, כל אחת פעם אחת. כל ניסיון הגיע לשירות, השירות סיים את העבודה אחרי שלוש שניות גם כשאיש כבר לא חיכה, וה-Idempotency-Key דאג שהניסיונות הבאים של אותה הערה יקבלו את הקיימת. המשתמש, לעומת זאת, קיבל בכל פעם "unavailable", על הערה שנשמרה. זה המחיר של timeout: אחריו לא יודעים.

הסכנה ב-timeout קצר מדי: שירות תקין שעונה לפעמים בשנייה ייחשב תקול, ייכשל לשווא, וינוסה שוב, כלומר יקבל עוד עומס בדיוק כשהוא איטי. בוחרים את המספר משני הכיוונים: כמה זמן המשתמש מוכן לחכות לכל הפעולה (חלקי מספר הניסיונות), וכמה זמן לוקחות התשובות האיטיות של השירות כשהוא תקין (נמדוד את זה בפרק 13). ה-timeout צריך להיות מעל השני ומתחת לראשון; אם אין מספר כזה, מורידים ניסיונות.

agent\notes.py
class CircuitBreaker:
    """After `threshold` failed calls in a row, stop calling for `cooldown` seconds.

    Closed: calls go through. Open: every call fails at once, without waiting. After the
    cooldown, one call may try (half-open): success closes the breaker, failure opens it again.
    """

    def __init__(
        self,
        threshold: int = 3,
        cooldown: float = 30.0,
        clock: Callable[[], float] = time.monotonic,
    ) -> None:
        self.threshold = threshold
        self.cooldown = cooldown
        self.clock = clock  # tests pass a fake clock
        self.failures = 0
        self.opened_at: float | None = None

    def allow(self) -> bool:
        return self.opened_at is None or self.clock() - self.opened_at >= self.cooldown

    def success(self) -> None:
        self.failures = 0
        self.opened_at = None

    def failure(self) -> None:
        self.failures += 1
        if self.failures >= self.threshold:
            self.opened_at = self.clock()

ב-NotesClient: פרמטר breaker: CircuitBreaker | None = None, ו-self.breaker = breaker or CircuitBreaker(). ב-_request, לפני הלולאה, if not self.breaker.allow(): raise NotesUnavailable(f"{method} {path}: circuit open, not calling for now"); self.breaker.success() מיד כשהסטטוס אינו ב-RETRY_STATUSES (השירות ענה, גם אם ב-4xx); ו-self.breaker.failure() לפני ה-raise האחרון. הבדיקה, ב-tests\test_notes.py:

tests\test_notes.py
def test_the_breaker_opens_after_three_failed_calls_and_tries_again_later():
    now = [0.0]
    breaker = CircuitBreaker(threshold=3, cooldown=30, clock=lambda: now[0])
    failures = [httpx2.ConnectError("refused")] * 9
    notes, requests = client_for(*failures, httpx2.Response(200, json=[]))
    notes.breaker = breaker
    for _ in range(3):
        with pytest.raises(NotesUnavailable):
            notes.list("c1")
    assert len(requests) == 9  # three calls, three attempts each
    with pytest.raises(NotesUnavailable, match="circuit open"):
        notes.list("c1")
    assert len(requests) == 9  # open: no request was sent at all
    now[0] = 31  # after the cooldown, one call may try, and it works
    assert notes.list("c1") == []
    assert breaker.opened_at is None

השיחה נמחקה (204), וההערה שלה נשארה, מחוברת למזהה שכבר לא קיים. Transaction חיה בתוך בסיס נתונים אחד; כאן יש שניים, ששייכים לשני שירותים. אפשר שהצ'אט יקרא, אחרי המחיקה, ל-DELETE על כל הערה. אבל מה אם שירות ההערות למטה באותו רגע? השיחה כבר נמחקה, וההערות לא. לבעיה הזו יש פתרונות מסודרים (הודעה שתטופל כשהשירות יחזור, ופעולת תיקון לכל צעד), והם פרק 12.

האם לפצל? בפרויקט הזה, לא. אין צוות שני, אין עומס שונה, ואין דרישה שההערות ייפרסו בנפרד. שווה לחשוב על modular monolith: מודול agent/notes עם טבלה משלו, שאף מודול אחר לא נוגע בה, ופונקציות במקום HTTP. כל מה שבנינו בפרק (timeouts, ניסיונות, מפתחות, מפסק, שני deploys, שני בסיסי נתונים) היה נעלם, וגם הבאג של המחיקה, כי transaction אחת הייתה מכסה את שניהם. ואם יום אחד יבוא צוות להערות, הגבולות כבר יהיו שם, והפיצול יהיה קל.
