Git ו-GitHub

איך שומרים כל גרסה של הקוד, חוזרים לגרסה שעבדה, ועובדים על אותו פרויקט עם אנשים אחרים בלי לדרוס אחד את השני.

בסוף הפרק תדעו

  • להסביר מה זה commit, ולשמור את ההיסטוריה של הפרויקט בצעדים קטנים עם הודעות ברורות.
  • לוודא עם .gitignore שסודות ותיקיות שנבנות מחדש לא נכנסים ל-git.
  • לחזור אחורה: לבטל שינוי שעוד לא נשמר, ולבטל commit שכבר נשלח.
  • לעבוד על branch, למזג אותו, ולהסביר מתי merge ומתי rebase.
  • לפתור merge conflict אמיתי מול שותף לצוות.
  • להסביר מה זה pull request, לכתוב תיאור טוב לאחד, ולעשות code review לקוד של מישהו אחר.

זמן משוער: ארבע עד חמש שעות, כולל התרגילים. מה צריך: הפרויקט מפרק 1 ו-git שהתקנתם שם. את כל הפרק אפשר לעשות בלי חשבון בשום אתר: את השרת המרוחק מדמים בתיקייה במחשב שלכם. חשבון GitHub חינמי נדרש רק לתרגיל האחרון, והוא רשות.

2.3מה זה commit, והגדרה חד-פעמית

Commit הוא צילום של כל הפרויקט ברגע מסוים, ולא רק של מה שהשתנה. לכל צילום יש:

  • מזהה (hash): מחרוזת כמו 517d756bba66f14c2df085a654bda1663c0842b1, שמחושבת מהתוכן. בדרך כלל מספיקים שבעת התווים הראשונים, 517d756.
  • מחבר ותאריך: מי שמר ומתי.
  • הודעה (commit message): משפט שאתם כותבים, ומסביר מה השתנה ולמה.
  • הורה (parent): ה-commit שקדם לו. כך נוצרת שרשרת, וזו ההיסטוריה.

כדי ש-git ידע מה לכתוב בשדה "מחבר", צריך להציג את עצמכם פעם אחת לכל מחשב. הדגל --global אומר "לכל הפרויקטים במחשב הזה":

PowerShell
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global core.editor "code --wait"

השורה השלישית חשובה יותר ממה שנראה. יש פקודות git שפותחות עורך טקסט כדי שתכתבו בו הודעה. ברירת המחדל של Git for Windows היא Vim, עורך שמי שלא מכיר לא יודע אפילו איך לצאת ממנו. השורה הזו אומרת ל-git לפתוח את VS Code במקום, ולחכות (--wait) עד שתסגרו את הלשונית.

האימייל יהיה ציבורי

מה שתכתבו ב-user.email נשמר בכל commit, ומי שיקבל את הקוד יראה אותו. אם תעלו פרויקט ציבורי ל-GitHub ולא תרצו לחשוף את האימייל הפרטי, GitHub נותן כתובת חלופית בהגדרות החשבון, בעמוד Emails.

מה הופך commit לטוב

  • שינוי הגיוני אחד. "הוספתי פקודת /reset" ולא "הוספתי /reset, תיקנתי שגיאת כתיב ושיניתי את המודל". כשמשהו נשבר, קל למצוא ולבטל שינוי אחד קטן. קשה לבטל ערבוב.
  • הודעה בציווי, באנגלית, קצרה: Add /reset command, ולא added stuff או fix. נסו להשלים את המשפט "If applied, this commit will...". מה שבא אחריו הוא ההודעה.
  • הקוד עובד בכל commit. מי שיחזור לנקודה הזו בעוד חודש צריך לקבל פרויקט שרץ.

2.4דוגמה מודרכת: הפרויקט נכנס ל-git

עובדים על הפרויקט מפרק 1, בתיקייה ~\projects\my-agent. אם התיקייה שלכם התבלגנה, העתיקו לתיקייה ריקה את הקבצים מ-checkpoints\chapter-01 (כולל .env.example), הריצו uv sync, ויצרו .env כמו בפרק 1.

המזהים (hashes) והשעות בפלטים כאן הם אלה שהתקבלו כשהפרק נכתב. אצלכם הם יהיו אחרים, וזה תקין.

1יוצרים repository

PowerShell
cd ~\projects\my-agent
git init -b main
output
Initialized empty Git repository in C:/Users/you/projects/my-agent/.git/

התיקייה הפכה ל-repository (בקיצור repo): תיקייה ש-git עוקב אחריה. הדגל -b main קובע שהענף הראשי ייקרא main, השם המקובל היום. בלעדיו גרסאות מסוימות של git קוראות לו master.

כל ההיסטוריה תישמר בתיקייה נסתרת אחת, .git. כדי לראות אותה צריך את הדגל -Force, שמציג גם קבצים נסתרים:

PowerShell
ls -Force

לא עורכים שום דבר בתוך .git ביד. ומי שמוחק אותה, מוחק את כל ההיסטוריה.

ולמה .venv לא מופיעה? כי uv יצר בתוכה קובץ .gitignore קטן שאומר ל-git להתעלם מכל מה שבתיקייה. זו הגנה שקיבלתם במתנה. על .env אף אחד לא הגן בשבילכם.

3כותבים .gitignore

הקובץ .gitignore הוא רשימה של שמות ותבניות ש-git יתעלם מהם. פתחו קובץ חדש ב-VS Code:

PowerShell
code .gitignore

כתבו בו את התוכן הבא ושמרו (Ctrl+S):

.gitignore
# Secrets and private settings: never commit these
.env

# The virtual environment is rebuilt from uv.lock with `uv sync`
.venv/

# Files Python generates while running
__pycache__/
*.pyc

# Editor settings that belong to one person
.vscode/
.idea/

שורה שמתחילה ב-# היא הערה. .venv/ עם לוכסן בסוף פירושו "תיקייה בשם הזה". *.pyc פירושו "כל קובץ שמסתיים ב-.pyc". את .venv כתבנו למרות ש-uv כבר מגן עליה, כי מי שקורא את הקובץ צריך לראות את כל הכללים במקום אחד.

אל תיצרו את הקובץ עם > ב-PowerShell

הפקודה ".env" > .gitignore נראית כמו קיצור דרך, אבל ב-Windows PowerShell 5.1 היא כותבת את הקובץ בקידוד UTF-16, ו-git לא מבין אותו. התוצאה: יש .gitignore, הוא נראה תקין, ו-.env עדיין מופיע ב-git status. בדקנו את זה, וזה בדיוק מה שקורה. צרו את הקובץ ב-VS Code.

2.5.gitignore וסודות

מה נכנס ל-.gitignore? הכלל מפרק 1 נשאר: משתפים את ההוראות לבניית הסביבה ולא את הסביבה עצמה. בפועל, מתעלמים משלושה סוגים של קבצים:

סוגדוגמאותלמה לא לשמור
סודות והגדרות פרטיות.envמי שמקבל את הקוד מקבל גם את המפתח שלכם
דברים שנבנים מחדש.venv/, __pycache__/, ובהמשך קבצי build ובסיסי נתונים מקומייםגדולים, תלויים במחשב, ואפשר לשחזר אותם בפקודה
העדפות אישיות.vscode/, .idea/שייכים לאדם אחד, ויוצרים שינויים מיותרים אצל כולם

שימו לב ש-.env.example לא ברשימה. התבנית בלי הסודות היא בדיוק מה שרוצים לשתף.

ומה אם כבר שמרתם סוד?

.gitignore משפיע רק על קבצים ש-git עוד לא עוקב אחריהם. אם .env כבר נכנס ל-commit לפני שהוספתם את הכלל, git ימשיך לעקוב אחריו. כדי להפסיק לעקוב בלי למחוק את הקובץ מהדיסק:

PowerShell
git rm --cached .env
git commit -m "Stop tracking .env"

אבל זה לא מספיק. ה-commit הישן עדיין קיים בהיסטוריה, ובתוכו המפתח, וכל מי שיש לו עותק יכול להגיע אליו. אם הקוד כבר נשלח לשרת, הנחת העבודה היחידה הבטוחה היא שהמפתח דלף: נכנסים ל-platform.claude.com, מבטלים את המפתח, ויוצרים חדש. קודם מחליפים את המפתח, ורק אחר כך מנקים. לנושא הזה, כולל כלים שסורקים קוד ומחפשים סודות, נחזור בפרק 14 על אבטחה.

2.6היסטוריה וחזרה אחורה

זו ההבטחה מסוף פרק 1: דרך לחזור לגרסה שעבדה. יש כמה מצבים, ולכל אחד פקודה משלו. לפני הטבלה, שלוש פקודות לקריאת ההיסטוריה:

PowerShell
git log --oneline -- chat.py   # only the commits that changed chat.py
git show 517d756               # what one commit changed, as a diff
git diff --staged              # what is in staging, about to be committed

בפקודות git אפשר לכתוב HEAD במקום מזהה. HEAD פירושו "ה-commit שאני עומד עליו עכשיו", ו-HEAD~1 הוא זה שלפניו.

המצבהפקודהמה היא עושה
שיניתי קובץ, עוד לא add, ואני רוצה לבטלgit restore chat.pyמחזירה את הקובץ למצב שלו ב-commit האחרון. השינויים נמחקים
עשיתי add לקובץ שלא רציתיgit restore --staged chat.pyמוציאה מה-staging. השינויים נשארים בקובץ
אני צריך את הגרסה של קובץ מלפני כמה commitsgit restore --source=517d756 chat.pyמביאה את הקובץ כפי שהיה ב-commit ההוא. אחר כך בודקים ושומרים ב-commit רגיל
שמרתי commit גרוע, ואולי כבר שלחתי אותוgit revert <hash>יוצרת commit חדש שמבטל את השינוי. ההיסטוריה לא נמחקת, רק מתווסף לה תיקון

שימו לב לכיוון של git revert: הוא לא מוחק את העבר, הוא מוסיף לו. זה נראה פחות "נקי", אבל זו הדרך הבטוחה, כי אם מישהו אחר כבר קיבל את ה-commit הגרוע, ההיסטוריה שלו ושלכם נשארות תואמות. תתרגלו את זה בתרגיל 1.

פקודות שמשכתבות היסטוריה

תפגשו באינטרנט את git reset --hard ואת git commit --amend. שתיהן משנות את ההיסטוריה עצמה. reset --hard גם מוחקת שינויים שלא נשמרו, בלי לשאול ובלי דרך פשוטה להחזיר. הכלל: מותר לשכתב רק היסטוריה שעוד לא שלחתם לשום מקום. מה שכבר נשלח, מתקנים עם revert.

2.7Remote: עותק משותף

עד עכשיו ההיסטוריה נמצאת רק במחשב שלכם. אם הדיסק ייהרס, היא תיעלם יחד איתו, ואף אחד אחר לא יכול לעבוד עליה. Remote הוא עוד עותק של ה-repository, בדרך כלל בשרת, שכולם שולחים אליו ומושכים ממנו.

בעבודה אמיתית ה-remote נמצא ב-GitHub (או בשירות דומה כמו GitLab). בפרק הזה נדמה אותו בתיקייה מקומית, כדי שתוכלו לתרגל הכול בלי חשבון ובלי אינטרנט. מבחינת git אין הבדל: אותן פקודות בדיוק עובדות מול תיקייה ומול שרת.

יוצרים remote מקומי

PowerShell
cd ~\projects
git init --bare -b main remotes\my-agent.git
output
Initialized empty Git repository in C:/Users/you/projects/remotes/my-agent.git/

Bare repository הוא repository בלי working directory: רק ההיסטוריה, בלי קבצים שאפשר לערוך. זה בדיוק מה ששרת מחזיק. אל תעבדו בתוך התיקייה הזו. עכשיו מחברים אליה את הפרויקט, ושולחים:

PowerShell
cd my-agent
git remote add origin $HOME\projects\remotes\my-agent.git
git push -u origin main
output
To C:\Users\you\projects\remotes\my-agent.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.

origin הוא שם ל-remote, כמו כינוי באנשי קשר. זה השם המקובל ל-remote הראשי. $HOME הוא משתנה של PowerShell שמכיל את תיקיית הבית שלכם, כי git צריך כאן נתיב מלא. הדגל -u אומר ל-git לזכור שהענף main שלכם קשור ל-main שב-origin, ולכן מעכשיו מספיק לכתוב git push ו-git pull בלי פרטים. הריצו git status ותראו שורה חדשה: Your branch is up to date with 'origin/main'.

פקודהמה היא עושה
git clone <url> <folder>מורידה עותק מלא של repository לתיקייה חדשה, כולל כל ההיסטוריה
git pushשולחת ל-remote את ה-commits שיש לכם ואין לו
git fetchמורידה את ה-commits שיש ל-remote ואין לכם, בלי לגעת בקבצים שלכם
git pullfetch ומיד אחריו merge: מורידה ומאחדת לתוך הענף שלכם

אותו דבר, מול GitHub

את החלק הזה לא תעשו עכשיו. הוא כאן כדי שתדעו מה משתנה כשה-remote אמיתי, ותעשו אותו בתרגיל 6 אם תרצו:

  1. ב-github.com, יוצרים repository חדש: כפתור New, שם, ובחירה ב-Private. לא מסמנים יצירה של README, .gitignore או רישיון, כי ה-repository צריך להיות ריק כדי לקבל את ההיסטוריה שכבר יש לכם.
  2. GitHub מציג כתובת בצורה https://github.com/<user>/my-agent.git. מחברים אותה עם git remote add, כמו קודם, ושולחים עם git push -u. אם השם origin כבר תפוס, בוחרים שם אחר.
  3. בפעם הראשונה ייפתח חלון דפדפן להתחברות. זה Git Credential Manager, שמותקן עם Git for Windows, והוא שומר את ההרשאה כדי שלא תצטרכו להתחבר שוב. אל תכתבו סיסמה או token בתוך הכתובת.

2.8Branches ו-merge

נניח שאתם מתחילים לבנות פקודה חדשה, וזה לוקח יומיים. בינתיים מישהו מבקש תיקון דחוף. אם כל העבודה נעשית ישר על main, הקוד החצי-גמור שלכם מעורבב בתיקון. Branch (ענף) פותר את זה: קו פיתוח נפרד, שבו עובדים על דבר אחד בלי להפריע לאחרים, ומחברים אותו חזרה רק כשהוא מוכן.

טכנית, branch הוא רק תווית עם שם, שמצביעה על commit. כשאתם שומרים commit חדש, התווית של הענף שאתם עומדים עליו זזה קדימה אליו. לכן יצירה של branch לוקחת אפס זמן ואפס מקום, וזה בסדר גמור ליצור הרבה מהם.

PowerShell
git switch -c feature/reset-command   # create a branch and move to it
git branch                            # list branches; * marks the current one
git switch main                       # move back to main
git merge feature/reset-command       # bring the branch's commits into main
git branch -d feature/reset-command   # delete the label once it is merged

כשעוברים ענף, git מחליף את הקבצים בתיקייה לגרסה של הענף ההוא. אל תיבהלו כשקוד "נעלם" אחרי git switch main: הוא מחכה בענף שלו.

שני סוגים של merge

אם מאז שיצרתם את הענף אף אחד לא שמר commit חדש ב-main, אין מה לאחד. git פשוט מזיז את התווית main קדימה עד הסוף של הענף שלכם. זה נקרא fast-forward, וההיסטוריה נשארת קו ישר. תראו את זה בתרגיל 2.

אם בזמן הזה נוספו commits גם ב-main, יש שני קווים שהתפצלו. git יוצר merge commit: commit מיוחד עם שני הורים, שמחבר את הקווים. כך זה נראה ב-git log --oneline --graph, אחרי תרגיל 3:

output
*   637eb78 (HEAD -> main) Merge remote-tracking branch 'origin/main'
|\
| * 3ac2720 (origin/main, origin/HEAD) Ask for clear answers in the system prompt
* | d68df42 Answer in the user's language
|/
* 405a787 Add /reset command to clear the conversation

קוראים מלמטה למעלה: מ-405a787 יצאו שני קווים, ב-637eb78 הם התאחדו. הכוכביות הן commits, והקווים הם הקשרים להורים.

2.9קונפליקטים: merge conflicts

ברוב המקרים git מאחד לבד: אתם שיניתם את תחילת הקובץ, השותפה את סופו, ו-git לוקח את שני השינויים. הוא נעצר רק כששני הצדדים שינו את אותן שורות בצורות שונות. אז אין לו דרך לדעת מה נכון, והוא מחזיר את ההחלטה אליכם. זה merge conflict. זו לא שגיאה ולא תקלה, זו שאלה.

output
Auto-merging chat.py
CONFLICT (content): Merge conflict in chat.py
Automatic merge failed; fix conflicts and then commit the result.

git כותב את שתי הגרסאות לתוך הקובץ, מסומנות כך:

chat.py
<<<<<<< HEAD
SYSTEM_PROMPT = "You are a friendly assistant. Answer in the language the user writes in."
=======
SYSTEM_PROMPT = "You are a friendly assistant. Keep your answers short and clear."
>>>>>>> origin/main

מה שבין <<<<<<< HEAD לבין ======= הוא הגרסה שלכם. מה שבין ======= לבין >>>>>>> הוא הגרסה שמגיעה מבחוץ. פותרים בארבעה צעדים:

  1. מחליטים מה התוצאה הנכונה: אחת הגרסאות, או שילוב. כאן שני השינויים רצויים, אז משלבים.
  2. עורכים את הקובץ כך שיכיל רק את התוצאה, ומוחקים את שלוש שורות הסימון. VS Code מציג מעל הקונפליקט כפתורים: Accept Current Change (שלכם), Accept Incoming Change (שלהם), Accept Both Changes (שניהם). אפשר להתחיל מהם ולתקן ביד.
  3. מריצים את הקוד. git בודק רק טקסט, לא היגיון. שילוב של שתי שורות תקינות יכול לתת תוכנית שבורה.
  4. מסמנים ושומרים: git add chat.py, ואז git commit.

ואם התבלבלתם באמצע ורוצים לחזור למצב שלפני הניסיון לאחד, git merge --abort מבטל הכול.

איך מקטינים קונפליקטים

קונפליקטים גדלים עם הזמן. ענף שחי שבועיים צובר הרבה שינויים, וגם main צובר, ובסוף מתנגשים בעשרה מקומות. ענף שחי יום, ומתעדכן מ-main לעיתים קרובות, מתנגש לכל היותר במקום אחד. ענפים קטנים וקצרים הם ההרגל החשוב ביותר בפרק.

2.10Rebase

יש דרך שנייה להביא את השינויים של main לתוך הענף שלכם. נניח שפתחתם ענף, שמרתם בו commit, ובינתיים מישהו הוסיף commit ל-main:

output
* 0efd356 (origin/main, origin/HEAD, main) Document the chat commands in README
| * c338483 (HEAD -> docs/contributing) Add CONTRIBUTING.md with the team git workflow
|/
*   637eb78 Merge remote-tracking branch 'origin/main'

merge היה מחבר את הקווים עם merge commit. git rebase main עושה משהו אחר: הוא לוקח את ה-commits של הענף שלכם, ו"משחק אותם מחדש" אחד אחד מעל הסוף של main, כאילו התחלתם לעבוד רק עכשיו:

output
* 4a68c39 (HEAD -> docs/contributing) Add CONTRIBUTING.md with the team git workflow
* 0efd356 (origin/main, origin/HEAD, main) Document the chat commands in README
*   637eb78 Merge remote-tracking branch 'origin/main'

ההיסטוריה ישרה, ואפשר לאחד בעזרת fast-forward. אבל שימו לב למזהה: ה-commit שהיה c338483 הוא עכשיו 4a68c39. התוכן זהה, ההורה השתנה, ולכן זה commit חדש. rebase משכתב היסטוריה.

כלל הזהב של rebase

עושים rebase רק לענף שאתם לבד עובדים עליו. אם כבר שלחתם את הענף ל-remote, אחרי rebase הפקודה git push תיכשל, כי מבחינת השרת ההיסטוריה שלכם סותרת את שלו. במקרה כזה, ורק בענף שלכם, שולחים עם git push --force-with-lease, שמסכים לדרוס רק אם אף אחד אחר לא שלח לענף בינתיים. על main, או על ענף משותף, לא עושים rebase אף פעם.

mergerebase
ההיסטוריהאמיתית: רואים שעבדו במקבילישרה: נראית כאילו עבדו בתור
משכתב commits?לאכן, נוצרים מזהים חדשים
קונפליקטיםפותרים פעם אחת, ב-merge commitעלולים לחזור בכל commit שמשוחק מחדש
מתיתמיד בטוח. ברירת המחדל כשלא בטוחיםלעדכן ענף פרטי מ-main לפני שמבקשים לאחד אותו

צוותים שונים בוחרים אחרת, ושתי הגישות לגיטימיות. מה שחשוב הוא שכולם בצוות יעבדו באותה דרך, ושהיא כתובה במקום שכולם רואים. תכתבו מסמך כזה בתרגיל 4.

2.11Pull requests ו-code review

בצוות, אף אחד לא מאחד ענף ל-main לבד ובשקט. במקום זה פותחים pull request (ב-GitLab קוראים לזה merge request): בקשה רשמית לאחד ענף לתוך main, שאחרים קוראים, מעירים עליה ומאשרים. Pull request אינו פקודת git. זה כלי של GitHub שבנוי מעל branches ו-merge.

מחזור החיים

  1. יוצרים ענף מ-main מעודכן, עובדים, שומרים commits.
  2. שולחים את הענף: git push -u origin feature/reset-command.
  3. ב-GitHub פותחים pull request מהענף אל main, עם כותרת ותיאור.
  4. בדיקות אוטומטיות רצות על הקוד. את זה תבנו בפרק 9.
  5. חבר צוות עושה code review: קורא את השינויים בלשונית Files changed, מעיר על שורות ספציפיות, ומסיים באחד משלושה: Comment, Approve או Request changes.
  6. מתקנים לפי ההערות עם commits נוספים באותו ענף. ה-pull request מתעדכן לבד.
  7. אחרי אישור, לוחצים Merge, ומוחקים את הענף.

תיאור טוב

מי שקורא את ה-pull request לא היה בראש שלכם. תנו לו את מה שהוא צריך כדי לבדוק בעשר דקות:

pull request description
## What
Adds a /reset command that clears the conversation and starts a new one.

## Why
Long conversations get slow and expensive. Users had to restart the program to start over.

## How to test
1. Set CHAT_MOCK=1 and run `uv run python chat.py`.
2. Send two messages, then `/reset`, then one more.
3. The mock reply should say "turn 1" again.

## Notes for the reviewer
The help line printed at startup also changed.

איך עושים review

  • האם זה עושה מה שהתיאור אומר? הריצו את הקוד לפי "How to test", אל תסתפקו בקריאה.
  • מה עלול להישבר? קלט ריק, שיחה ארוכה, הודעת שגיאה מה-API.
  • האם נכנס משהו שלא שייך? סודות, הדפסות שנשארו מ-debugging, שינויים שלא קשורים לנושא.
  • האם יבינו את זה בעוד חצי שנה? שמות, הערות, הודעות commit.

כתבו הערות על הקוד ולא על האדם ("השורה הזו מדפיסה את כל השיחה", ולא "שכחת להוריד print"), הסבירו למה, והבחינו בין "חייב לתקן" לבין "הצעה". ומהצד השני: כשמקבלים הערה, עונים על כל אחת, בתיקון או בהסבר. Review הוא שיחה על הקוד, לא מבחן.

שלוש דרכים ללחוץ Merge

אפשרות ב-GitHubמה קורה ל-main
Create a merge commitכל ה-commits של הענף נכנסים, ועוד merge commit שמחבר
Squash and mergeכל הענף נדחס ל-commit אחד. היסטוריה נקייה, אבל הצעדים הקטנים הולכים לאיבוד
Rebase and mergeה-commits של הענף משוחקים מחדש מעל main, בלי merge commit

2.12אסטרטגיית branching

ברגע שיש יותר מאדם אחד, צריך להסכים על כללים: מאיזה ענף יוצאים, איך קוראים לענפים, ומי מאחד לאן. לזה קוראים branching strategy. שתי הנפוצות:

GitHub flow (או trunk-based)Git flow
ענפים קבועיםרק mainmain ו-develop, ועוד ענפי release/ ו-hotfix/
עבודהענף קצר מ-main, pull request, חזרה ל-mainענף מ-develop, חזרה ל-develop, ומשם בגרסאות מתוכננות ל-main
מתאים לשירותים שמעדכנים הרבה פעמים, רוב הצוותים היוםמוצרים שיוצאים בגרסאות ממוספרות, עם כמה גרסאות נתמכות במקביל

לפרויקט שלכם, ולרוב הצוותים שתפגשו, GitHub flow מספיק: main תמיד עובד, כל שינוי בענף קצר עם שם שמסביר אותו (feature/reset-command, fix/empty-input), ושום דבר לא נכנס ל-main בלי pull request. ב-GitHub אפשר לאכוף את הכלל האחרון בעזרת branch protection, הגדרה שחוסמת push ישיר ל-main ודורשת אישור. בחברות תפגשו לפעמים גם ענפים לפי סביבה, כמו staging. נדבר על סביבות בפרק 10.

2.13תרגילים

התרגילים בונים זה על זה ומספרים סיפור אחד: אתם מוסיפים יכולת לסוכן, מצטרפת שותפה, ואתם לומדים לעבוד יחד. עשו אותם לפי הסדר, באותו repository. פתרונות, כולל הפלט שהתקבל בכל צעד, נמצאים בדף נפרד.

תרגיל 1 · מכונת זמן

מודרך

חלק א: שינוי שעוד לא נשמר.

  1. ב-chat.py, מחקו את כל הפונקציה ask_mock ושמרו. הריצו את הסוכן במצב mock ושלחו הודעה. תקבלו את השגיאה מתחילת הפרק.
  2. הריצו git status ואז git diff --stat. כמה שורות נמחקו?
  3. החזירו את הקובץ: git restore chat.py. הריצו שוב את הסוכן.

חלק ב: commit שכבר נשמר.

  1. הוסיפו את השורה print(messages) מיד אחרי messages.append({"role": "user", "content": user_text}).
  2. שמרו בפקודה אחת: git commit -am "Print the conversation before each request". הדגל -a מכניס ל-staging את כל הקבצים שכבר במעקב ששונו, כך שאין צורך ב-git add נפרד. קבצים חדשים הוא לא מכניס.

תרגיל 6 · מחזור מלא ב-GitHub

פתוח

התרגיל הזה דורש חשבון GitHub חינמי, והוא רשות. כל מה שקודם לו נעשה בלי חשבון.

העלו את הפרויקט ל-repository פרטי חדש ב-GitHub, לפי סעיף 2.7. מכיוון שהשם origin כבר תפוס על ידי ה-remote המקומי, תנו לחדש שם אחר, למשל git remote add github <url>, ושלחו עם git push -u github main. אחר כך עשו מחזור אחד שלם של pull request, על שינוי קטן לבחירתכם: ענף, commit, push, פתיחה עם תיאור לפי התבנית, review עם הערה אחת לפחות על שורה, תיקון בעקבות ההערה, merge, מחיקת הענף, ו-git pull אצלכם.

אין כאן הוראות צעד אחרי צעד. חלק מהתרגיל הוא למצוא בממשק של GitHub איפה כל דבר נמצא. החליטו בעצמכם באיזו מבין שלוש אפשרויות ה-merge להשתמש, ונסו להפעיל branch protection על main.

2.16מילון מונחים

repository (repo)
תיקייה ש-git עוקב אחריה, יחד עם כל ההיסטוריה שלה (בתיקייה .git).
working directory
הקבצים שאתם רואים ועורכים, בגרסה של הענף הנוכחי.
staging area
תחנת ביניים: השינויים שנבחרו (עם git add) להיכנס ל-commit הבא.
commit
צילום של הפרויקט, עם מזהה, מחבר, תאריך, הודעה והפניה ל-commit הקודם.
hash
המזהה של commit, מחושב מהתוכן. מספיקים בדרך כלל שבעת התווים הראשונים.
HEAD
ה-commit (ובדרך כלל הענף) שאתם עומדים עליו עכשיו.
.gitignore
קובץ עם רשימת שמות ותבניות ש-git מתעלם מהם.
diff
תצוגה של ההבדלים בין שתי גרסאות: שורות שנמחקו (-) ושנוספו (+).
revert
commit חדש שמבטל את השינוי של commit קודם, בלי למחוק אותו מההיסטוריה.
branch
קו פיתוח נפרד. טכנית, תווית עם שם שמצביעה על commit וזזה איתו.
merge
איחוד של ענף אחד לתוך אחר.
fast-forward
merge שבו רק מזיזים את התווית קדימה, כי ענף היעד לא השתנה בינתיים.
merge commit
commit עם שני הורים, שמחבר שני קווי פיתוח שהתפצלו.
merge conflict
מצב שבו שני הצדדים שינו את אותן שורות, ו-git מבקש מכם להחליט.
rebase
העברה של commits לבסיס חדש, על ידי משחק מחדש שלהם. יוצר commits חדשים.
remote
עותק נוסף של ה-repository, בדרך כלל בשרת. השם המקובל לראשי הוא origin.
bare repository
repository בלי working directory, רק היסטוריה. מה ששרת מחזיק.
clone / fetch / pull / push
העתקה של repository / הורדת commits חדשים / הורדה ואיחוד / שליחה.
pull request
בקשה ב-GitHub לאחד ענף, שאחרים קוראים, מעירים עליה ומאשרים.
code review
קריאה ביקורתית של שינוי בקוד על ידי אדם אחר, לפני שהוא מאוחד.
branching strategy
הכללים המוסכמים בצוות: אילו ענפים קיימים, איך קוראים להם, ומי מאחד לאן.

2.17מה הלאה

לכל שינוי בפרויקט יש עכשיו היסטוריה, הסבר, ודרך חזרה, ואתם יודעים לעבוד עליו עם אחרים. אבל שימו לב איך מצאתם את הבעיות בתרגיל 5: קראתם כל שורה בעיניים, והבאג של ספירת התורות התגלה רק כשהרצתם ביד. בפרק 1 הבאג ב-trim_history היה מתגלה רק בשיחה ארוכה. ו-chat.py הולך ומתארך, כשהכול בקובץ אחד.
