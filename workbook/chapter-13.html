מערכת חיה

איך יודעים מה קורה בתוך מערכת שרצה עכשיו, אצל משתמשים אמיתיים, בכמה שירותים, ואיך מוצאים מה קרה לבקשה אחת כשמישהו כותב "זה נתקע ואז קיבלתי שגיאה".

בסוף הפרק תדעו

  • לכתוב לוגים מובנים (JSON), לבחור רמה לכל שורה, ולדעת מה אסור לכתוב בלוג לעולם.
  • ליצור מזהה בקשה בכניסה למערכת ולהעביר אותו דרך HTTP ו-Kafka, כך שכל השורות של בקשה אחת נמצאות בחיפוש אחד.
  • להבדיל בין counter, gauge ו-histogram, להסביר את ארבעת האותות הזהובים, ולמה ממוצע משקר ו-percentile לא.
  • לחשוף /metrics, לתת ל-Prometheus לאסוף אותו, ולכתוב התראה על סימפטום, עם runbook.
  • להסביר tracing, SLO ו-error budget, ולטפל בתקלה: קודם לעצור את הנזק, אחר כך להבין, ובסוף postmortem בלי האשמות.

זמן משוער: חמש עד שש שעות. מה צריך: הפרויקט מסוף פרק 12, Docker Desktop עם כ-3 GB זיכרון פנוי. הכול במצב mock. בפעם הראשונה Docker יוריד את ה-image של Prometheus (כ-120 MB).

13.3לוגים מובנים

שורת לוג כמו WARNING agent.notes: notes: POST /v1/notes: ReadTimeout נכתבה בשביל אדם שקורא אותה. אבל במערכת חיה יש מיליוני שורות, ומי שקורא אותן קודם הוא תוכנה: מסננת, סופרת, מקבצת. לכן כותבים לוג מובנה (structured log): כל שורה היא אובייקט JSON אחד, עם שדות קבועים. כך תיראה אותה שורה בסוף הפרק:

לאן הלוגים הולכים

שירות כותב ל-standard output, ותו לא. לא לקובץ: קובץ בתוך container נעלם איתו (פרק 8), וגדל עד שהדיסק מתמלא. את הפלט אוסף מי שמריץ את השירות: Docker שומר אותו (docker compose logs), ובענן ה-platform שולח אותו למאגר לוגים (log aggregator): Grafana Loki, Elasticsearch, CloudWatch Logs, Google Cloud Logging. שם הלוגים של כל השירותים יושבים יחד, ומחפשים בהם בשאילתה: {service="notes"} | json | request_id="27fb...". אצלנו, במחשב אחד, docker compose logs ו-Select-String מספיקים. הקובץ agent.log נשאר רק לצ'אט ב-terminal, שבו הפלט שייך לשיחה.

13.4מזהה בקשה שעובר בין שירותים

מזהה בקשה (request id, וכשהוא עובר בין שירותים גם correlation id) נוצר פעם אחת, בנקודה שבה הבקשה נכנסת למערכת (edge), ונכתב בכל שורת לוג שנכתבת בשבילה, בכל שירות. שלושה מקומות להעביר אותו:

  • בתוך תהליך אחד: משתנה של Python שמחזיק "המזהה של הבקשה הנוכחית". משתנה גלובלי רגיל לא יעבוד, כי uvicorn מטפל בכמה בקשות במקביל. contextvars.ContextVar נותן לכל בקשה ערך משלה, ו-FastAPI מעביר אותו גם לפונקציות שרצות ב-thread אחר.
  • ב-HTTP: כותרת X-Request-ID. שירות ההערות לוקח אותה במקום ליצור חדש. ה-api מחזיר אותה גם ללקוח, כדי שמשתמש שקיבל שגיאה יוכל לצטט אותה.
  • ב-Kafka: להודעה יש headers, בדיוק כמו ל-HTTP: מטא-דאטה שאינו חלק מהאירוע עצמו. ה-worker קורא request_id מה-header ושם אותו ב-ContextVar שלו.

מזהה שמגיע מבחוץ מתקבל רק אם הוא נראה כמו מזהה (אותיות, ספרות, .-_, עד 64 תווים). אחרת לקוח יכול לכתוב ללוגים שלכם כל דבר, כולל שורה חדשה שנראית כמו שורת לוג אמיתית.

# The id of the request being handled right now, or None outside a request.
request_id: ContextVar[str | None] = ContextVar("request_id", default=None)
SAFE_ID = re.compile(r"[A-Za-z0-9._-]{1,64}")


def new_request_id(incoming: str | None = None) -> str:
    """Keep a well-formed id that a caller sent (X-Request-ID); otherwise make a new one."""
    if incoming and SAFE_ID.fullmatch(incoming):
        return incoming
    return uuid.uuid4().hex


class JsonFormatter(logging.Formatter):
    def format(self, record: logging.LogRecord) -> str:
        line = {
            "time": datetime.fromtimestamp(record.created, UTC).isoformat(timespec="milliseconds"),
            "level": record.levelname, "service": self.service,
            "logger": record.name, "message": record.getMessage(),
        }
        current = request_id.get()
        if current:
            line["request_id"] = current
        # Fields given with extra={...}: duration_ms, status, conversation_id, ...
        line.update({k: v for k, v in vars(record).items() if k not in STANDARD})
        if record.exc_info:
            line["error"] = self.formatException(record.exc_info)  # one line, not ten
        return json.dumps(line, ensure_ascii=False, default=str)

def setup_logging(level: str, service: str, filename: str | None = None) -> None:
    handler: logging.Handler
    if filename:
        handler = logging.FileHandler(filename, encoding="utf-8")
    else:
        handler = logging.StreamHandler(sys.stdout)
    handler.setFormatter(JsonFormatter(service))
    root = logging.getLogger()
    root.handlers = [handler]
    root.setLevel(level)
    # uvicorn has handlers of its own, in plain text. Send its lines through ours instead.
    for name in ("uvicorn", "uvicorn.error"):
        logging.getLogger(name).handlers = []
        logging.getLogger(name).propagate = True
    # Our middleware writes a better access line (with the request id and the duration).
    logging.getLogger("uvicorn.access").disabled = True

2Middleware: הכניסה למערכת

Middleware הוא קוד שעוטף כל בקשה, לפני ה-endpoint ואחריו. ב-create_app:

agent\api.py (shortened)
    @app.middleware("http")
    async def observe(request: Request, call_next: ...) -> Response:
        """Every request: an id, one access log line, and its metrics."""
        token = logs.request_id.set(logs.new_request_id(request.headers.get("X-Request-ID")))
        start = time.perf_counter()
        status = 500  # what the client gets if the endpoint raises
        try:
            response = await call_next(request)
            status = response.status_code
            response.headers["X-Request-ID"] = logs.request_id.get() or ""
            return response
        finally:
            seconds = time.perf_counter() - start
            route = getattr(request.scope.get("route"), "path", "unmatched")
            metrics.observe_request(request.method, route, status, seconds)  # part b
            log.log(logging.DEBUG if route in quiet else logging.INFO,
                    "%s %s %s", request.method, request.url.path, status,
                    extra={"status": status, "duration_ms": round(seconds * 1000)})
            logs.request_id.reset(token)

ב-conversations.py, השורה "sending %d messages" מתחלפת ב-"model replied" עם extra={"messages": ..., "llm_ms": ...}: כמה זמן לקח המודל. scripts\ask.py מדפיס את המזהה מכותרת התשובה, וגם בשגיאה; דף הצ'אט מציג אותו ליד כל שגיאה.

def test_the_log_lines_of_a_request_share_its_id(client, log_lines):
    response = client.post("/chat", json={"message": "hello"}, headers=AUTH)
    request_id = response.headers["X-Request-ID"]
    mine = [line for line in log_lines() if line.get("request_id") == request_id]
    # The model's line and the access line, both with the id and as JSON.
    assert [line["message"] for line in mine] == ["model replied", "POST /chat 200"]
    assert mine[-1]["status"] == 200
    assert "duration_ms" in mine[-1]

13.6מדדים

לוגים עונים על "מה קרה לבקשה הזו". הם לא עונים טוב על "כמה בקשות נכשלו בשעה האחרונה", כי בשביל זה צריך לקרוא ולספור מיליוני שורות. מדד (metric) הוא מספר שהשירות סופר בזיכרון כל הזמן, וזול לשמור ולשאול עליו. שלושה סוגים:

סוגמה הואאצלנו
Counterרק עולה. מה שמעניין הוא הקצב שלוhttp_requests_total, llm_tokens_total
Gaugeעולה ויורד: מצב ברגע הזהnotes_circuit_open, worker_consumer_lag
Histogramסופר תצפיות לפי טווחים (buckets): כמה מתחת ל-0.1 שנייה, כמה מתחת ל-0.25, ...http_request_duration_seconds

ארבעת האותות הזהובים

במקום למדוד הכול, מתחילים מארבעה, שנקראים golden signals: latency (כמה זמן לוקחת תשובה), traffic (כמה בקשות), errors (כמה נכשלות), ו-saturation (כמה קרוב משאב לגבול שלו: זיכרון, חיבורים, תור שמתארך). אצלנו הרוויה היא בעיקר ה-lag של ה-worker. מעליהם, מה שמיוחד למערכת: זמן ו-tokens של המודל (כסף), כישלונות מול שירות ההערות ומצב ה-circuit breaker, אירועים שאבדו (ה-dual write מפרק 12, עכשיו נספר), ו-sagas לפי איך שהסתיימו.

למה ממוצע משקר

תשעים ושמונה בקשות של 0.1 שנייה ושתי בקשות של 7 שניות: הממוצע הוא 0.24 שנייה. נשמע מצוין, ושניים מכל מאה חיכו 7 שניות. Percentile אומר את האמת: p50 (החציון) הוא מה שחצי מהבקשות לא עברו, p99 הוא מה ש-99 מכל מאה לא עברו. כאן p50 הוא 0.1 ו-p99 הוא 7. משתמש פעיל שולח עשרות בקשות ביום, ולכן כמעט כל אחד פוגש את ה-p99 מדי יום. היסטוגרמה מאפשרת לחשב percentiles אחר כך, מכל השירותים יחד; ממוצעים אי אפשר לחבר כך.

Labels, ומה לא לשים בהם

מדד מתפצל לפי labels: http_requests_total{route="/chat", status="200"}. כל צירוף של ערכים הוא סדרה נפרדת שנשמרת לאורך זמן. לכן ב-label שמים רק ערכים מעטים וידועים: /conversations/{conversation_id}, ולא /conversations/3976.... מזהה שיחה ב-label יוצר סדרה חדשה לכל שיחה, עד שמאגר המדדים קורס. לזה קוראים cardinality, והוא התקלה הנפוצה ביותר עם מדדים. מזהים שייכים ללוגים.

def measure_lag(consumer: Consumer) -> None:
    """Lag per partition: the newest offset in the topic minus the group's committed one."""
    for committed in consumer.committed(consumer.assignment(), timeout=5):
        low, high = consumer.get_watermark_offsets(
            TopicPartition(committed.topic, committed.partition), timeout=5)
        done = committed.offset if committed.offset >= 0 else low  # nothing committed yet
        LAG.labels(str(committed.partition)).set(high - done)

13.8Tracing: לאן הלך הזמן

ה-/chat מהצעד 4 לקח 45 מילישניות, ומהן 25 בשירות ההערות. את זה הבנו מחיבור ידני של שתי שורות. Tracing עושה את החיבור מראש: כל קטע עבודה (span) נרשם עם התחלה, סוף, שם, ו"מי הקטע שקרא לי". כל ה-spans של בקשה אחת יחד הם trace, וכלי מציג אותם כמפל:

מחיקת שיחה אחת בגרסה של סוף הפרק, משוחזרת מהשורות שלה בלוגים (כמו בתרגיל 1): כחול ב-api, סגול בשירות ההערות, כתום ב-worker, 26 מילישניות אחרי שה-api כבר ענה. כלי tracing מצייר את זה לבד.

כדי שה-span בשירות ההערות יידע מי ההורה שלו, הקורא שולח את מזהה ה-trace ואת מזהה ה-span שלו בכותרת. לזה קוראים context propagation, והתקן הוא כותרת W3C בשם traceparent. ה-X-Request-ID שלנו הוא הגרסה הצנועה של אותו רעיון: מזהה trace בלי spans.

הכלי המקובל היום הוא OpenTelemetry (OTel): תקן וספריות לכל השפות, שמייצרים traces, וגם מדדים ולוגים, ושולחים אותם לכל מאגר (Jaeger, Grafana Tempo, ענן). יש לו חבילות אוטומטיות ל-FastAPI, httpx, SQLAlchemy ו-Kafka: כמה שורות של הגדרה, וכל קריאה הופכת ל-span עם traceparent בכותרת. בפרויקט לא נבנה את זה: זה דורש עוד שרת לאסוף ולהציג, והמזהה כבר נותן לנו את רוב הערך. בפרק 21 תראו tracing של ריצות של סוכן, שם כל צעד של המודל הוא span.

13.9התראות

אף אחד לא יושב מול גרפים. התראה (alert) היא שאילתה ש-Prometheus בודק כל כמה שניות, ואם היא נכונה לאורך זמן (for), הוא מודיע. לאן: Prometheus מעביר ל-Alertmanager, שמקבץ, משתיק ושולח ל-Slack, למייל או לטלפון של התורן (on-call), דרך שירות כמו PagerDuty.

על סימפטומים, לא על כל סיבה

אפשר להתריע על כל דבר: מעבד מעל 80%, ניסיון חוזר מול שירות ההערות, הודעה ב-DLQ. אחרי שבוע יש מאה התראות ביום, רובן לא אומרות שמישהו סובל, והתורן מפסיק לקרוא אותן. לזה קוראים עייפות התראות (alert fatigue), וזה הרגע שבו ההתראה האמיתית מתפספסת. לכן מעירים אדם רק על סימפטום: משהו שמשתמשים מרגישים (שגיאות, איטיות), או נתונים שנפגעים. את הסיבות מחפשים אחרי ההתראה, בלוגים ובמדדים. שתי דרגות: page (להעיר עכשיו) ו-ticket (לטפל בשעות העבודה).

## ChatErrors

More than 5% of `/chat` and `/conversations` requests answer 5xx for 5 minutes.

1. Which status and route? In Prometheus:
   `sum by (route, status) (rate(http_requests_total{status=~"5.."}[5m]))`
2. 502 on `/chat`: the model fails. Check `llm_errors_total` by `reason` ...
3. 503 on `DELETE /conversations/...`: the notes service; see NotesFailing.
4. 500: a bug. Take a `request_id` from an ERROR line and read all its lines.
5. Mitigate: a recent deploy? Roll back. ...

Runbook שלא עודכן גרוע מאין runbook, כי סומכים עליו. לכן הבדיקה מכריחה אותו להתקיים, ומי שמוסיף התראה כותב גם את הסעיף שלה.

SLI, SLO ו-error budget

כמה שגיאות זה "יותר מדי"? מגדירים את זה מראש, במספרים. SLI (service level indicator) הוא מה שמודדים מנקודת המבט של המשתמש, למשל "החלק מבקשות /chat שהצליחו ב-3 שניות או פחות". SLO (objective) הוא היעד: 99% מהן, על פני 28 יום. ה-1% שנשאר הוא error budget: בעשרת אלפים בקשות ביום, מאה בקשות גרועות ביום מותרות.

SLOמותר להיכשל ב-28 יוםבזמן, אם הכול נופל בבת אחת
99%1 מכל 100 בקשותכ-6.7 שעות
99.9%1 מכל 1,000כ-40 דקות
99.99%1 מכל 10,000כ-4 דקות: עשרים deploys עם 12 השניות שמדדתם בפרק 10

כל תשיעייה נוספת עולה הרבה יותר מהקודמת, ומשתמש שהרשת הביתית שלו נופלת יותר מזה לא ירגיש בהבדל. כל עוד התקציב לא נגמר, משחררים גרסאות חדשות בקצב רגיל; כשהוא נגמר, עוצרים פיצ'רים ומשקיעים ביציבות. כך "כמה אמין" הופך מוויכוח להחלטה. מכאן גם התנאי של פרק 9 ל-continuous deployment: גרסה שיוצאת אוטומטית חייבת מדד שאומר אם היא פוגעת, והתראה שעוצרת אותה.

13.10תקלה (incident)

ההתראה צלצלה, או שמשתמשת כתבה. הסדר:

  1. לזהות ולהכריז. מישהו אחד לוקח אחריות (incident commander) ופותח ערוץ אחד לתקלה. גם "אני בודק" הוא הודעה.
  2. קודם לעצור את הנזק (mitigate), לפני שמבינים. Rollback לגרסה הקודמת (פרק 10), כיבוי של פיצ'ר, העברת תנועה. ההבנה המלאה יכולה לחכות; המשתמשים לא.
  3. לאבחן מהראיות: מדדים לתמונה הכללית ("מתי התחיל? מה עוד השתנה אז?"), לוגים לבקשה אחת, מזהה הבקשה כדי לעבור בין שירותים. לרשום כל ממצא עם השעה.
  4. לתקשר. למשתמשים, בדף סטטוס או בתשובה: מה מושפע, מה לעשות, מתי עדכון הבא. בלי ניחושים על הסיבה.
  5. ללמוד. אחרי שהכול שקט, postmortem.

13.15מילון מונחים

observability
היכולת לענות על שאלות על מערכת חיה מתוך מה שהיא כותבת ומודדת, בלי לשנות אותה.
structured log
שורת לוג עם שדות קבועים (כאן JSON), שתוכנה יכולה לסנן ולספור.
log level
חומרה של שורה: DEBUG, INFO, WARNING, ERROR.
request id / correlation id
מזהה שנוצר בכניסה למערכת ונכתב בכל שורה של אותה בקשה, בכל שירות.
log aggregator
מאגר שאוסף לוגים מכל השירותים ומאפשר לחפש בהם יחד (Loki, Elasticsearch, CloudWatch).
middleware
קוד שעוטף כל בקשה לשרת, לפני ה-endpoint ואחריו.
metric
מספר שהשירות סופר בזיכרון לאורך זמן: counter, gauge או histogram.
golden signals
latency, traffic, errors, saturation: ארבעת המדדים שמתחילים מהם.
percentile
p99: הערך ש-99 מכל 100 תצפיות לא עברו.
cardinality
מספר הסדרות שמדד יוצר: כל צירוף של ערכי labels.
scrape
Prometheus מושך את /metrics של שירות, כל כמה שניות.
PromQL
שפת השאילתות של Prometheus.
span / trace
קטע עבודה אחד עם התחלה וסוף; כל הקטעים של בקשה אחת.
context propagation
העברת מזהה ה-trace בין שירותים, למשל בכותרת traceparent.
OpenTelemetry
תקן וספריות לייצור traces, מדדים ולוגים, ולשליחתם לכל מאגר.
alert fatigue
כשיש כל כך הרבה התראות שאנשים מפסיקים להגיב להן.
runbook
הוראות למי שהתראה העירה: מה לבדוק ומה לעשות.
SLI / SLO
מה מודדים מנקודת המבט של המשתמש; היעד למדד הזה.
error budget
כמה כישלון ה-SLO מרשה; כשהוא נגמר, יציבות לפני פיצ'רים.
mitigate
לעצור את הנזק למשתמשים, לפני שמבינים את הסיבה.
postmortem (blameless)
מסמך שאחרי תקלה: מה קרה, למה, ומה משנים, בלי להאשים אנשים.

13.16מה הלאה

המערכת שקופה עכשיו: כל בקשה משאירה עקבות בשלושה שירותים, כל מספר חשוב נספר, ומי שמעירים אותו יודע מה לעשות. אבל תסתכלו מי עוד רואה: /metrics פתוח לכל מי שמגיע לפורט, בלי מפתח, ומספר כמה משתמשים יש, מה נכשל ומה עולה כסף. מזהה בקשה שמגיע מבחוץ נכתב ללוגים שלכם. המפתח בין הצ'אט לשירות ההערות הוא סיסמה אחת קבועה, Kafka מקבל כל מי שמתחבר, ה-containers רצים כ-root, ואף אחד לא בדק אם בחבילות שהתקנתם יש חולשה ידועה. מי שלא אמור להיות במערכת יכול לראות אותה, ולפעמים גם לגעת.

סודות שדולפים, הרשאות מינימליות, בדיקת קלט, תלויות פגיעות, הגבלת קצב, ומידע אישי: פרק 14: אבטחה.
