איך משנים מבנה של טבלה שכבר מלאה בשיחות של אנשים, בלי למחוק דבר, בלי לעצור את העולם, ועם דרך חזרה.

בסוף הפרק תדעו

  • להסביר מה זה migration, ולמה בסיס נתונים עם נתונים לא "נבנה מחדש".
  • לעבוד עם Alembic: revision, upgrade, downgrade, current, history ו-stamp.
  • להכניס בסיס נתונים קיים לשליטה של Alembic, ולהחליט מי יוצר טבלאות: האפליקציה, הבדיקות, או אף אחד מהם.
  • לכתוב backfill שממלא ערך לשורות ישנות, ולהריץ downgrade אמיתי.
  • לשנות מבנה בשלבים בטוחים (expand, migrate, contract) כשקוד ישן עדיין רץ.
  • לזהות ולתקן שני migrations שנכתבו במקביל בשני ענפים.

7.3Alembic בעמוד אחד

Alembic הוא כלי ה-migrations של SQLAlchemy, מאותו כותב. הוא מבין את המחלקות שלכם, ולכן יכול גם להציע migration: הוא משווה את בסיס הנתונים למחלקות, וכותב טיוטה של ההבדלים. לזה קוראים autogenerate. הפקודות:

פקודהמה היא עושה
alembic init migrationsיוצרת את התיקייה migrations ואת alembic.ini. פעם אחת בחיי הפרויקט
alembic revision --autogenerate -m "..."כותבת קובץ migration חדש מתוך ההבדל בין בסיס הנתונים למחלקות. לא מריצה אותו
alembic upgrade headמריצה את כל מה שעוד לא רץ, עד הסוף (head)
alembic downgrade -1מריצה את ה-downgrade() של האחרון. אפשר גם לתת מספר: downgrade 0001
alembic current / historyאיפה בסיס הנתונים נמצא / כל השרשרת
alembic stamp 0001רושמת ב-alembic_version "אני ב-0001", בלי להריץ כלום. לבסיס נתונים שכבר נמצא שם
alembic upgrade head --sqlמדפיסה את ה-SQL במקום להריץ אותו. בלי חיבור לבסיס הנתונים
autogenerate כותב טיוטה, לא migration

הוא רואה עמודות, types ואינדקסים. הוא לא יודע מה הכוונה: שינוי שם של עמודה נראה לו כמו "מחק עמודה, הוסף עמודה", כלומר מחיקה של כל הנתונים בה. והוא לא כותב backfill. כלל: כל קובץ שנוצר נקרא שורה אחרי שורה לפני שמריצים אותו, כמו קוד של עמית ב-pull request.

"""Alembic runs this file for every command. It says which database, and which tables."""

import os
from logging.config import fileConfig

from alembic import context
from dotenv import load_dotenv
from sqlalchemy import create_engine, pool

from agent.config import DEFAULT_DATABASE_URL
from agent.db import Base

config = context.config
if config.config_file_name is not None:
    fileConfig(config.config_file_name)  # the logging settings at the end of alembic.ini

# The tables as the code describes them. autogenerate compares the database to these.
target_metadata = Base.metadata

# Code that runs migrations (like the tests) passes the URL in; otherwise the same
# DATABASE_URL as the agent, from the terminal or from .env.
load_dotenv()
url = config.attributes.get("url") or os.getenv("DATABASE_URL", DEFAULT_DATABASE_URL)


def run_migrations_offline() -> None:
    """--sql: print the SQL instead of running it. No connection is made."""
    context.configure(url=url, target_metadata=target_metadata, literal_binds=True)
    with context.begin_transaction():
        context.run_migrations()


def run_migrations_online() -> None:
    """Connect, and run the migrations inside a transaction."""
    engine = create_engine(url, poolclass=pool.NullPool)
    with engine.connect() as connection:
        # render_as_batch: on SQLite, autogenerate writes changes that copy the table (7.7).
        context.configure(
            connection=connection, target_metadata=target_metadata, render_as_batch=True
        )
        with context.begin_transaction():
            context.run_migrations()


if context.is_offline_mode():
    run_migrations_offline()
else:
    run_migrations_online()

class DatabaseNotReady(Exception):
    """The database is missing migrations that this code needs."""


def alembic_config(url: str) -> Config:
    """What the alembic command reads from alembic.ini, for the database at `url`."""
    config = Config()
    config.set_main_option("script_location", str(MIGRATIONS))
    config.attributes["url"] = url  # migrations/env.py reads it from here
    return config


def upgrade(url: str, revision: str = "head") -> None:
    """Run the migrations on the database at `url`, like `alembic upgrade head`."""
    command.upgrade(alembic_config(url), revision)


def check_schema(engine: Engine) -> None:
    """Refuse to work with a database that is behind the code."""
    scripts = ScriptDirectory(str(MIGRATIONS))
    head = scripts.get_current_head()
    with engine.connect() as connection:
        current = MigrationContext.configure(connection).get_current_revision()
    if current == head:
        return
    if current is None:
        raise DatabaseNotReady(
            "The database has no migration history. A new database: run "
            "`uv run alembic upgrade head`. One from before migrations: see `alembic stamp`."
        )
    try:
        scripts.get_revision(current)
    except CommandError:
        # A revision we do not know: newer code has already migrated this database.
        # That is fine (the old code must keep working during a deploy), but say so.
        log.warning("database is at %s, newer than this code (%s)", current, head)
        return
    raise DatabaseNotReady(
        f"The database is at revision {current}, the code needs {head}. "
        "Run `uv run alembic upgrade head`."
    )


def make_engine(url: str) -> Engine:
    """Connect to the database at `url`, and make sure its tables match the code."""
    in_memory = url in ("sqlite://", "sqlite:///:memory:")
    if in_memory:
        # An in-memory database lives inside one connection, so everyone shares that one.
        engine = create_engine(url, poolclass=StaticPool, connect_args={"check_same_thread": False})
    else:
        engine = create_engine(url)
    if engine.dialect.name == "sqlite":
        event.listen(engine, "connect", turn_on_foreign_keys)
    if in_memory:
        # A new, empty database that disappears with the process (the tests): nothing to
        # migrate, so the tables come straight from the classes above.
        Base.metadata.create_all(engine)
    else:
        check_schema(engine)
    return engine

def differences(url):
    """What autogenerate would still write: the gap between the database and the classes."""
    engine = create_engine(url)
    with engine.connect() as connection:
        found = compare_metadata(MigrationContext.configure(connection), Base.metadata)
    engine.dispose()
    return found


def table_names(url):
    engine = create_engine(url)
    names = set(inspect(engine).get_table_names())
    engine.dispose()
    return names

7.7SQLite, batch mode, ומה ישתנה ב-Postgres

למה Alembic כתב with op.batch_alter_table(...) ולא פקודה פשוטה? כי SQLite יודע מעט מאוד ALTER TABLE. על המחשב הזה (SQLite 3.50): ADD COLUMN ו-DROP COLUMN עובדים, אבל שינוי של עמודה קיימת לא קיים בשפה:

op.alter_column(..., nullable=False) without batch mode, on SQLite
sqlite3.OperationalError: near "ALTER": syntax error
[SQL: ALTER TABLE t ALTER COLUMN title SET NOT NULL]

Batch mode עוקף את זה: הוא יוצר טבלה חדשה בשם _alembic_tmp_conversations במבנה החדש, מעתיק אליה את כל השורות, מוחק את הישנה ומשנה לחדשה את השם. זה גם ההסבר לשני דברים שראיתם. ההעתקה נכשלה על שורה עם NULL כי הטבלה החדשה כבר הייתה NOT NULL. וטבלת העזר נשארה, כי Alembic מודיע Will assume non-transactional DDL: עם הדרייבר של Python ל-SQLite, פקודות מבנה לא מתבטלות כשמשהו נכשל באמצע. מכאן שלושה כללים: גיבוי לפני כל migration, ניסיון על עותק כשיש ספק, ו-foreign keys כבויים בזמן ה-migration, אחרת מחיקת הטבלה הישנה הייתה נחסמת בגלל messages. זו הסיבה ש-env.py לא משתמש ב-make_engine.

ב-Postgres, שאליו הפרויקט עובר בפרק 8, הכול פשוט יותר: batch_alter_table כותב שם ALTER TABLE conversations ALTER COLUMN title SET NOT NULL ישירות, בלי העתקה, וכל migration רץ בתוך transaction אמיתית: כישלון באמצע מבטל הכול. אותם קבצים עובדים בשני המקומות, כל עוד לא כותבים בהם SQL שרק SQLite מבין. תרגיל 1 מראה את ה-SQL של Postgres בלי להתקין אותו.

7.8Migrations ב-git ובצוות

  • Migration שרץ במקום אחר לא נערך יותר. אם 0002 כבר רץ על השרת, שינוי בקובץ לא ישפיע שם: alembic_version אומר שהוא כבר רץ. טעות מתקנים ב-migration חדש. מותר לערוך רק מה שעוד לא יצא מהמחשב שלכם (ואז downgrade מקומי, עריכה, upgrade).
  • ה-migration וקוד שמשתמש בו נכנסים לאותו pull request, והבודק קורא את ה-migration ראשון: האם הוא נועל טבלה גדולה? מוחק? תואם לקוד הישן?
  • שני ענפים, שני migrations. git ימזג אותם בלי קונפליקט, כי אלה שני קבצים שונים. אבל לשניהם אותו down_revision, והשרשרת התפצלה לשני ראשים (heads). git לא רואה את זה; Alembic ו-test_migrations.py כן. תרגיל 4.
  • הסדר בעדכון גרסה: גיבוי, alembic upgrade head, ואז הקוד החדש. בגלל expand, migrate, contract, הקוד הישן ממשיך לעבוד בין שני הצעדים.
  • Rollback של קוד הוא כמעט תמיד בטוח, כי המבנה החדש תואם לקוד הישן. downgrade בשרת הוא צעד אחרון: הוא עלול למחוק נתונים, ולכן צוותים רבים מעדיפים לתקן קדימה, עם migration חדש. גיבוי הוא הדרך החזרה האמיתית.

  1. אתם: git switch -c feature/user-id. הוסיפו ל-ConversationRow מתחת ל-id: הערה # Who the conversation belongs to. Empty for now: the "expand" step (chapter 7). ו-user_id: Mapped[str | None] = mapped_column(String(64)). migration עם --rev-id 0004, upgrade head, commit.
  2. העמית: git switch main, git switch -c teammate/created-at-index. הוסיפו index=True ל-created_at של ConversationRow (ש-latest() ממיין לפיו). לעמית יש בסיס נתונים משלו: $env:DATABASE_URL = "sqlite:///teammate.db", upgrade head, ואז migration עם --rev-id 0004. נקו את המשתנה והקובץ, commit, ומזגו ל-main: ה-pull request שלו נכנס ראשון.
  3. אתם שוב: git switch feature/user-id, uv run alembic downgrade -1 (הורידו את שלכם מבסיס הנתונים, כל עוד יש לו מספר ברור), git merge main. הריצו uv run alembic heads ו-uv run pytest.
  4. תקנו: שנו את השם של הקובץ שלכם ל-0005_... (git mv), ובתוכו Revision ID, Revises, revision = "0005" ו-down_revision = "0004". upgrade head, pytest, commit, ומזגו ל-main.

תרגיל 5 · רשימת השיחות ב-API

בינוני

בענף feature/conversation-list: הוסיפו ל-Conversations מתודה newest(limit=50) שמחזירה (id, title) מהחדשה לישנה; ל-api.py שדה title ב-ConversationOut, schema חדש ConversationSummary, ו-GET /conversations (עם מפתח) שמחזיר את הרשימה; ו-version="0.7.0". כתבו ב-test_api.py בדיקה לסדר ובדיקה ל-401, והוסיפו לבדיקה של GET /conversations/{id} בדיקה של הכותרת.

תרגיל 6 · תוכנית ל-user_id

פתוח

בתרגיל 4 עשיתם רק את שלב ה-expand של user_id. כתבו תוכנית לשאר, כאילו השרת משרת אנשים כל הזמן: מאיפה הקוד יודע מי המשתמש (רמז: למי שייך ה-X-API-Key, ומה עם ה-terminal)? מה ממלאים לשיחות הישנות? אילו גרסאות קוד, אילו migrations, ובאיזה סדר, עד NOT NULL? מה עושים אם צריך לחזור אחורה בכל שלב? אין צורך לממש. בסוף, עדכנו את README.md (התקנה עם alembic upgrade head, סעיף Migrations, stamp 0001 לבסיס נתונים ישן, GET /conversations, הקבצים החדשים), commit, ואחדו: git switch main, git merge feature/conversation-list, git push, ומחקו את הענפים.

7.12מילון מונחים

schema
המבנה של בסיס הנתונים: טבלאות, עמודות, types, מפתחות ואינדקסים.
migration
שינוי אחד ב-schema (ולפעמים בנתונים), כתוב כקוד, עם דרך קדימה ודרך אחורה.
Alembic
כלי ה-migrations של SQLAlchemy.
revision / head / base
מזהה של migration / האחרון בשרשרת / לפני הראשון.
upgrade / downgrade
הרצה קדימה / אחורה בשרשרת.
baseline
migration ראשון שמתאר מבנה שכבר קיים.
stamp
רישום מיקום ב-alembic_version בלי להריץ דבר.
autogenerate
טיוטת migration מתוך ההבדל בין בסיס הנתונים למחלקות.
backfill
מילוי ערך חדש בשורות שהיו קיימות לפני השינוי.
backward compatible
שינוי שהקוד הקודם ממשיך לעבוד איתו.
expand, migrate, contract
שינוי שובר בשלבים: מוסיפים, מעבירים, ורק בסוף מחייבים או מוחקים.
batch mode
שינוי טבלה ב-SQLite דרך טבלה חדשה, העתקה, והחלפה.
rollback
חזרה לגרסה קודמת של קוד. של בסיס נתונים: גיבוי, או migration מתקן.

7.13מה הלאה

למבנה של בסיס הנתונים יש עכשיו היסטוריה, כמו לקוד: חמישה migrations ב-git, טבלה שזוכרת איפה היא, בדיקה ששומרת שהשרשרת והמחלקות מסכימות, ותהליך שלא מפיל קוד ישן. אבל כל זה עדיין רץ על קובץ במחשב שלכם, עם ה-Python שלכם וה-.venv שלכם. שרת אמיתי צריך Postgres, צריך להריץ alembic upgrade head לפני האפליקציה, וצריך לקבל בדיוק את אותה סביבה.

איך אורזים את הסוכן ואת בסיס הנתונים כך שירוצו אותו דבר בכל מחשב? זה פרק 8: Containers. שם DATABASE_URL יצביע על Postgres, ותגלו אם ה-migrations שכתבתם כאן באמת נכתבו בלי SQL של SQLite.
