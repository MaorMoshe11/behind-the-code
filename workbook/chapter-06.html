בסיסי נתונים

איך הסוכן מפסיק לשכוח: שומרים כל שיחה במקום שחי מחוץ לתהליך, ושואלים אותו שאלות בשפה שנבנתה בשביל זה.

בסוף הפרק תדעו

  • להסביר מה זה בסיס נתונים רלציוני: טבלאות, שורות, עמודות, primary key ו-foreign key.
  • לכתוב ביד SQL בסיסי: CREATE TABLE, INSERT, SELECT עם WHERE, ORDER BY, JOIN ו-GROUP BY, UPDATE ו-DELETE.
  • להסביר מה index עושה ומה הוא עולה, ולמדוד את ההבדל בעצמכם.
  • להשתמש ב-transaction כדי ששני שינויים יקרו יחד או לא יקרו בכלל.
  • לעבוד עם ORM (SQLAlchemy), ולהבין איזה SQL הוא כותב בשבילכם.
  • להסביר מתי בוחרים document store, מאגר אנליטי או cache, ומתי לא.
  • להסביר איך cache עובד, מה זה TTL ו-invalidation, ומתי הוא מחזיר תשובה ישנה.

6.1הבעיה: הסוכן שוכח בכל הפעלה מחדש

בצעד 4 של הדוגמה המודרכת בפרק 5 שלחתם שתי הודעות בדף הצ'אט, הפעלתם את השרת מחדש, ושלחתם הודעה שלישית. התשובה הייתה:

the chat page, after a server restart
שגיאה 404: "No conversation with this id."

הדף זכר את המזהה, אבל השרת שכח הכול. השיחות חיו במילון אחד, _messages, בזיכרון של תהליך אחד. כל עדכון גרסה, כל קריסה וכל --reload מוחקים את כל השיחות של כל המשתמשים. ובפרק 1, כשהסתכלתם ב-debugger על הרשימה messages, הבטחנו שהבעיה הזו תיפתר כאן.

הפתרון הנאיבי הוא לכתוב את המילון לקובץ JSON בכל הודעה. זה עובד עם משתמש אחד, ונשבר מהר: שני לקוחות שכותבים באותו רגע דורסים זה את זה, קריסה באמצע כתיבה משאירה קובץ חצי-כתוב, וכדי למצוא שיחה אחת צריך לקרוא את כל הקובץ. בסיס נתונים (database) הוא תוכנה שפותרת בדיוק את שלוש הבעיות האלה, ועשרות שנים של עבודה הושקעו בזה. בפרק הזה תלמדו לדבר איתו בשפה שלו, ואז תעבירו אליו את השיחות של הסוכן.

6.3המודל הרלציוני: טבלאות, שורות ומפתחות

בסיס נתונים רלציוני (relational database) שומר הכול בטבלאות. לכל טבלה (table) יש עמודות קבועות (columns), ולכל עמודה type. כל רשומה היא שורה (row). כך ייראו השיחות של הסוכן, בשתי טבלאות:

conversationsmessages
id (PK)created_atid (PK)conversation_id (FK)rolecontent
c110:001c1userhello
c211:302c1assistantHi! How can I help?
3c2usergood morning
  • Primary key (PK): עמודה שהערך בה שונה בכל שורה, ולכן מזהה אותה. בשיחות זה ה-conversation_id שכבר נוסע בכל בקשה מפרק 5. בהודעות זה מספר רץ שבסיס הנתונים נותן לבד.
  • Foreign key (FK): עמודה שמצביעה על primary key בטבלה אחרת. messages.conversation_id אומר לאיזו שיחה ההודעה שייכת, ובסיס הנתונים יכול לסרב להודעה של שיחה שלא קיימת.

למה שתי טבלאות, ולא עמודה אחת של "כל ההודעות" בשורה של השיחה? כי כך כל שאלה פשוטה: "ההודעות של c1 לפי הסדר", "כמה הודעות בכל שיחה", "כל ההודעות של היום". הכלל נקרא normalization: כל עובדה נשמרת פעם אחת, במקום אחד, והקשרים נבנים מהמפתחות. ושימו לב שאין כאן קיצוץ: הטבלה שומרת את כל ההודעות, גם אם למודל נשלחות רק האחרונות.

6.4SQL ביד, ב-SQLite

SQL (Structured Query Language) היא השפה שבה מדברים עם כמעט כל בסיס נתונים רלציוני. היא הצהרתית: אתם כותבים מה אתם רוצים, ובסיס הנתונים מחליט איך להשיג את זה. SQLite הוא בסיס הנתונים הפשוט ביותר להתחיל איתו: אין שרת, כל בסיס הנתונים הוא קובץ אחד, והוא מגיע מובנה בתוך Python. גם הכלי להסתכל לתוכו מובנה: python -m sqlite3, מגרסה 3.12. ענף חדש, ודבר ראשון: לוודא שקבצי בסיס נתונים לא ייכנסו ל-git.

PowerShell
cd ~\projects\my-agent
git switch main
git pull
git switch -c feature/database

פתחו את .gitignore ב-VS Code והוסיפו בסופו (לא עם > של PowerShell: פרק 2 הראה מה הוא עושה לקידוד):

.gitignore (add at the end)
# Local databases (SQLite files) and their temporary journal files
*.db
*.db-journal

שמרו: git add .gitignore, git commit -m "Ignore local database files". בסיס נתונים מקומי מכיל נתונים, לא קוד: הוא כבד, משתנה כל הזמן, ועלול להכיל דברים פרטיים שמשתמשים כתבו. עכשיו פתחו מעבדה:

PowerShell
uv run python -m sqlite3 lab.db
output

Type ".help" for more information; type ".quit" or CTRL-Z to quit.
sqlite>

הקובץ lab.db נוצר כי לא היה קיים. כל פקודת SQL מסתיימת ב-;, ובלעדיו ה-shell מחכה להמשך עם .... מילות המפתח באותיות גדולות הן הרגל, לא חובה. צרו את שתי הטבלאות:

sqlite>
CREATE TABLE conversations (
  id TEXT PRIMARY KEY,
  created_at TEXT NOT NULL
);
CREATE TABLE messages (
  id INTEGER PRIMARY KEY,
  conversation_id TEXT NOT NULL REFERENCES conversations (id),
  role TEXT NOT NULL,
  content TEXT NOT NULL
);

NOT NULL אומר שאסור לשורה להגיע בלי ערך בעמודה. INTEGER PRIMARY KEY ב-SQLite הוא מספר רץ: לא נותנים ערך, ובסיס הנתונים בוחר את הבא. REFERENCES הופך את conversation_id ל-foreign key. עכשיו נתונים, ושורה אחת שגויה בכוונה:

sqlite>
INSERT INTO conversations (id, created_at) VALUES ('c1', '2026-11-18 10:00');
INSERT INTO conversations (id, created_at) VALUES ('c2', '2026-11-18 11:30');
INSERT INTO conversations (id, created_at) VALUES ('c1', '2026-11-18 12:00');
INSERT INTO messages (conversation_id, role, content) VALUES
  ('c1', 'user', 'hello'),
  ('c1', 'assistant', 'Hi! How can I help?'),
  ('c1', 'user', 'what is SQL?'),
  ('c1', 'assistant', 'A language for asking questions about tables.'),
  ('c2', 'user', 'good morning');
output (the third INSERT)
IntegrityError (SQLITE_CONSTRAINT_PRIMARYKEY): UNIQUE constraint failed: conversations.id

זה ה-primary key בעבודה: שתי שיחות עם אותו מזהה הן בדיוק הבאג שבסיס הנתונים מונע בשבילכם. מחרוזות ב-SQL נכתבות במירכאות בודדות. ועכשיו שאלות. כל אחת מהן היא SELECT: אילו עמודות, מאיזו טבלה, אילו שורות (WHERE) ובאיזה סדר (ORDER BY):

sqlite>
SELECT role, content FROM messages WHERE conversation_id = 'c1' ORDER BY id;
SELECT conversation_id, COUNT(*) FROM messages GROUP BY conversation_id;
SELECT c.created_at, m.content
  FROM messages AS m JOIN conversations AS c ON c.id = m.conversation_id
  WHERE m.role = 'user';
output
('user', 'hello')
('assistant', 'Hi! How can I help?')
('user', 'what is SQL?')
('assistant', 'A language for asking questions about tables.')
('c1', 4)
('c2', 1)
('2026-11-18 10:00', 'hello')
('2026-11-18 10:00', 'what is SQL?')
('2026-11-18 11:30', 'good morning')

השאלה הראשונה היא בדיוק מה שהסוכן צריך לפני כל תשובה. בלי ORDER BY, הסדר לא מובטח, גם אם היום הוא נראה נכון. השנייה מקבצת שורות (GROUP BY) ומפעילה על כל קבוצה פונקציה (COUNT). השלישית מחברת שתי טבלאות (JOIN): לכל הודעה, השורה של השיחה שה-foreign key שלה מצביע עליה. AS m ו-AS c הם כינויים קצרים. הפלט מגיע כ-tuples של Python, כי זה ה-shell של Python.

ה-foreign key שלא שמר על כלום

sqlite>
INSERT INTO messages (conversation_id, role, content) VALUES ('nope', 'user', 'orphan');
SELECT id, conversation_id, content FROM messages WHERE conversation_id = 'nope';
output
(6, 'nope', 'orphan')

אין שיחה nope, וההודעה נכנסה בכל זאת. זו מלכודת ידועה של SQLite: מסיבות של תאימות לאחור, הוא בודק foreign keys רק אם מבקשים, ובכל חיבור מחדש:

sqlite>
DELETE FROM messages WHERE conversation_id = 'nope';
PRAGMA foreign_keys = ON;
INSERT INTO messages (conversation_id, role, content) VALUES ('nope', 'user', 'orphan');
output
IntegrityError (SQLITE_CONSTRAINT_FOREIGNKEY): FOREIGN KEY constraint failed

זכרו את זה: בסעיף 6.8 הקוד יבקש את זה בכל חיבור. ושימו לב ל-DELETE הראשון. UPDATE messages SET content = 'x' WHERE id = 3; משנה שורה אחת, ו-DELETE FROM messages WHERE ... מוחק את מה שמתאים. בלי WHERE, שתי הפקודות פועלות על כל השורות, בלי לשאול "בטוח?". מתכנתים מנוסים כותבים קודם SELECT עם אותו WHERE, בודקים מה חוזר, ורק אז מחליפים אותו ב-DELETE.

בסיס הנתונים זוכר גם את המבנה של עצמו, בטבלה מיוחדת. כך רואים אילו טבלאות קיימות (לכלי של Python אין פקודה .tables):

sqlite>
SELECT name FROM sqlite_master WHERE type = 'table';
output
('conversations',)
('messages',)

6.5אינדקסים: למה שאלה אחת מהירה ואחרת איטית

איך SQLite מוצא את ההודעות של c1? אפשר לשאול אותו:

sqlite>
EXPLAIN QUERY PLAN SELECT * FROM messages WHERE conversation_id = 'c1';
CREATE INDEX ix_messages_conversation_id ON messages (conversation_id);
EXPLAIN QUERY PLAN SELECT * FROM messages WHERE conversation_id = 'c1';
output
(2, 0, 216, 'SCAN messages')
(3, 0, 62, 'SEARCH messages USING INDEX ix_messages_conversation_id (conversation_id=?)')

SCAN פירושו לקרוא את כל הטבלה ולבדוק כל שורה. עם ארבע שורות זה לא משנה. עם מיליון הודעות, כל תשובה של הסוכן הייתה מתחילה בקריאה של מיליון שורות. Index הוא מבנה נוסף שבסיס הנתונים מתחזק לצד הטבלה, ממוין לפי עמודה, כמו אינדקס בסוף ספר: במקום לדפדף בכל הספר, קופצים לעמוד. אחרי CREATE INDEX התוכנית היא SEARCH. בתרגיל 3 תמדדו כמה זה שווה על חצי מיליון הודעות.

אז למה לא index על כל עמודה? כי הוא עולה. כל INSERT ו-UPDATE צריך לעדכן גם אותו, והוא תופס מקום בקובץ. הכלל: index על עמודות שמחפשים לפיהן, מסננים לפיהן או מחברים לפיהן הרבה, כמו conversation_id. על ה-primary key יש index אוטומטית.

6.6Transactions: הכול או כלום

כשהסוכן עונה, נוספות שתי שורות: ההודעה שלכם והתשובה. מה אם השרת קורס אחרי הראשונה? בשיחה יש שאלה בלי תשובה, ובפרק 1 ראיתם שה-API של Claude דורש שהתורות יתחלפו. Transaction היא קבוצת פקודות שבסיס הנתונים מבטיח שיקרו כיחידה אחת: או כולן, או אף אחת. נסו:

sqlite>
BEGIN;
DELETE FROM messages;
SELECT COUNT(*) FROM messages;
ROLLBACK;
SELECT COUNT(*) FROM messages;
output
(0,)
(5,)

בתוך ה-transaction הטבלה ריקה. ROLLBACK ביטל הכול, כאילו לא קרה. COMMIT היה הופך את השינוי לקבוע. ה-shell הזה עובד במצב autocommit: כל פקודה מחוץ ל-BEGIN היא transaction קטנה משלה. כתבו .quit כדי לצאת.

מאחורי זה ארבע הבטחות שנקראות יחד ACID: atomicity (הכול או כלום), consistency (חוקים כמו foreign keys נשמרים), isolation (מי שקורא באמצע לא רואה חצי שינוי) ו-durability (מה שעבר COMMIT שורד גם הפסקת חשמל). זה ההבדל העיקרי מקובץ JSON.

לא מחזיקים transaction פתוחה בזמן שמחכים לרשת

שאלה ל-Claude לוקחת שניות. אם transaction פתוחה כל הזמן הזה, היא עלולה לחסום כותבים אחרים: ב-SQLite רק כותב אחד יכול להחזיק את הקובץ בכל רגע. לכן הסוכן יקרא את ההיסטוריה, יסגור, ישאל את המודל, ורק כשהתשובה ביד יכתוב את שתי ההודעות ב-transaction אחת קצרה. ואם המודל נכשל, אין מה לבטל: עוד לא נכתב כלום.

6.7ORM: SQLAlchemy

אפשר לכתוב את כל הסוכן עם SQL במחרוזות ומודול sqlite3. בפרויקט אמיתי זה נהיה מסורבל: להמיר כל שורה למילון ובחזרה, לכתוב CREATE TABLE שמתאים לקוד, ולכתוב SQL קצת שונה לכל בסיס נתונים. ORM (Object-Relational Mapper) הוא ספרייה שמחברת בין מחלקות Python לטבלאות. ב-Python, הנפוצה היא SQLAlchemy. ארבעה מושגים:

מושגמה הואאצלנו
Model (מחלקת טבלה)מחלקה שכל attribute שלה הוא עמודה, וכל מופע שלה הוא שורהConversationRow, MessageRow
Engineיודע לאיזה בסיס נתונים מתחברים, ומחזיק את החיבוריםנבנה מ-DATABASE_URL
Sessionיחידת עבודה: אוספת שינויים, ושולחת אותם ב-transaction אחתwith self.sessions.begin() as session:
select(...)SQL שנבנה מביטויי Python, ולא ממחרוזותselect(MessageRow).where(...)

ה-URL של בסיס הנתונים נראה כמו כתובת: sqlite:///agent.db הוא קובץ agent.db בתיקיית העבודה, sqlite:// הוא בסיס נתונים בזיכרון, ו-postgresql+psycopg://user:password@host/db הוא שרת Postgres. הקוד לא משתנה, רק המחרוזת. בפרק 8 זה יהיה כל המעבר ל-Postgres.

למה לא פשוט f-string?

אם הייתם כותבים f"SELECT * FROM messages WHERE conversation_id = '{cid}'", מזהה שמכיל מירכאה היה משנה את משמעות השאלה. משתמש זדוני יכול לשלוח "מזהה" שהוא בעצם פקודה. זו SQL injection, מהפרצות הוותיקות והנפוצות שיש. הפתרון: parameters. ה-SQL נשלח עם ?, והערכים נשלחים בנפרד, כך שהם תמיד נתונים ואף פעם לא קוד. SQLAlchemy עושה את זה תמיד, וכשתכתבו SQL ביד ב-Python, תעשו את זה גם אתם (תרגיל 3). נחזור לזה בפרק 14.

6.8דוגמה מודרכת: השיחות עוברות לבסיס הנתונים

1החבילה, והטבלאות כמחלקות

PowerShell
uv add sqlalchemy
output (shortened)
Resolved 40 packages in 1.02s
Installed 1 package in 258ms
 + sqlalchemy==2.1.9

צרו agent\db.py:

agent\db.py
"""The database: two tables, and the engine that connects to them.

DATABASE_URL says which database. The default is a SQLite file, agent.db.
"""

from datetime import UTC, datetime
from typing import Any

from sqlalchemy import Engine, ForeignKey, String, Text, create_engine, event
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column
from sqlalchemy.pool import StaticPool


def now() -> datetime:
    return datetime.now(UTC)


class Base(DeclarativeBase):
    """Every table class inherits from this, so SQLAlchemy knows about all of them."""


class ConversationRow(Base):
    """One row of the conversations table."""

    __tablename__ = "conversations"

    id: Mapped[str] = mapped_column(String(32), primary_key=True)
    created_at: Mapped[datetime] = mapped_column(default=now)


class MessageRow(Base):
    """One row of the messages table: one message, in one conversation."""

    __tablename__ = "messages"

    id: Mapped[int] = mapped_column(primary_key=True)
    conversation_id: Mapped[str] = mapped_column(ForeignKey("conversations.id"), index=True)
    role: Mapped[str] = mapped_column(String(16))
    content: Mapped[str] = mapped_column(Text)
    created_at: Mapped[datetime] = mapped_column(default=now)


def turn_on_foreign_keys(connection: Any, record: Any) -> None:
    """SQLite ignores foreign keys unless every new connection asks for them."""
    connection.execute("PRAGMA foreign_keys = ON")


def make_engine(url: str) -> Engine:
    """Connect to the database at `url`, and create the tables that do not exist yet."""
    if url in ("sqlite://", "sqlite:///:memory:"):
        # An in-memory database lives inside one connection, so everyone shares that one.
        engine = create_engine(url, poolclass=StaticPool, connect_args={"check_same_thread": False})
    else:
        engine = create_engine(url)
    if engine.dialect.name == "sqlite":
        event.listen(engine, "connect", turn_on_foreign_keys)
    # create_all adds missing tables. It never changes a table that already exists.
    Base.metadata.create_all(engine)
    return engine

השוו ל-CREATE TABLE שכתבתם: Mapped[str] הוא עמודה NOT NULL, Mapped[str | None] הייתה מתירה ריק, index=True הוא ה-CREATE INDEX, ו-default=now ממלא את created_at בזמן UTC. השם ConversationRow ולא Conversation, כדי לא להתבלבל עם ה-schema Message של api.py: זה שורה בטבלה, וזה מה שנוסע ב-HTTP. turn_on_foreign_keys היא ה-PRAGMA מסעיף 6.4, שרצה בכל חיבור חדש.

שתי החלטות פשוטות במכוון. create_all יוצר טבלאות שחסרות, וזו הדרך הפשוטה והכנה ליצור אותן היום. ובסיס נתונים בזיכרון (sqlite://) קיים רק בתוך החיבור שיצר אותו, ולכן StaticPool גורם לכולם, גם ל-threads של FastAPI, להשתמש באותו חיבור. זה בשביל הבדיקות. שמרו: git add pyproject.toml uv.lock agent\db.py, git commit -m "Add SQLAlchemy and the database tables".

החליפו את agent\conversations.py:

agent\conversations.py
"""The core of the agent: conversations and their messages.

The terminal chat and the HTTP API both use this module, so they behave the same.
Every message is saved in the database, so conversations survive a restart.
"""

import logging
import uuid

from anthropic.types import MessageParam
from sqlalchemy import Engine, delete, select
from sqlalchemy.orm import Session, sessionmaker

from agent.db import ConversationRow, MessageRow
from agent.history import trim_history
from agent.llm import ChatClient

log = logging.getLogger(__name__)


class ConversationNotFound(Exception):
    """No conversation has this id (it was deleted, or never existed)."""


def to_param(row: MessageRow) -> MessageParam:
    """A row from the database, in the shape the model client expects."""
    if row.role == "user":
        return {"role": "user", "content": row.content}
    return {"role": "assistant", "content": row.content}


class Conversations:
    """Every conversation, by id, and the one way to add a message to it."""

    def __init__(self, client: ChatClient, max_turns: int, engine: Engine) -> None:
        self.client = client
        self.max_turns = max_turns
        self.sessions = sessionmaker(engine)

    def _require(self, session: Session, conversation_id: str) -> None:
        if session.get(ConversationRow, conversation_id) is None:
            raise ConversationNotFound(conversation_id)

    def start(self) -> str:
        """Open a new, empty conversation and return its id."""
        conversation_id = uuid.uuid4().hex
        with self.sessions.begin() as session:
            session.add(ConversationRow(id=conversation_id))
        return conversation_id

    def messages(self, conversation_id: str) -> list[MessageParam]:
        """Every message in this conversation, oldest first."""
        with self.sessions() as session:
            self._require(session, conversation_id)
            rows = session.scalars(
                select(MessageRow)
                .where(MessageRow.conversation_id == conversation_id)
                .order_by(MessageRow.id)
            )
            return [to_param(row) for row in rows]

    def send(self, conversation_id: str, text: str) -> str:
        """Send the user's message with the recent history, and save both messages."""
        history = self.messages(conversation_id)
        # The model sees only the last turns; the database keeps all of them.
        prompt = trim_history(history, self.max_turns) + [{"role": "user", "content": text}]
        log.info("sending %d messages", len(prompt))
        reply = self.client.reply(prompt)  # if this fails, nothing was saved
        # One transaction: both messages are saved, or neither is.
        with self.sessions.begin() as session:
            session.add(MessageRow(conversation_id=conversation_id, role="user", content=text))
            session.add(
                MessageRow(conversation_id=conversation_id, role="assistant", content=reply)
            )
        return reply

    def reset(self, conversation_id: str) -> None:
        """Delete every message in this conversation, but keep the conversation."""
        with self.sessions.begin() as session:
            self._require(session, conversation_id)
            session.execute(delete(MessageRow).where(MessageRow.conversation_id == conversation_id))

    def delete(self, conversation_id: str) -> None:
        """Delete the conversation and its messages. Its id stops working."""
        with self.sessions.begin() as session:
            self._require(session, conversation_id)
            session.execute(delete(MessageRow).where(MessageRow.conversation_id == conversation_id))
            session.execute(delete(ConversationRow).where(ConversationRow.id == conversation_id))

אותן חמש מתודות, אותן חתימות, אותה חריגה. השינוי היחיד בממשק הוא engine בבנאי. sessions.begin() פותח session ו-transaction: ביציאה מה-with בלי חריגה הוא עושה COMMIT, ועם חריגה ROLLBACK. send בנוי לפי ה-callout מסעיף 6.6: קריאה, שאלה למודל מחוץ ל-transaction, ואז כתיבה אחת של שתי השורות. ה-messages.pop() מפרק 5 נעלם, כי כבר אין מה לבטל. ו-delete מוחק הודעות ושיחה באותה transaction: את השיחה אי אפשר למחוק קודם, כי ה-foreign key של ההודעות מצביע עליה.

הכלל לבחירה

מתחילים מבסיס נתונים רלציוני, ובפרויקט שרץ על שרת, Postgres. מוסיפים מאגר אחר רק כשיש צורך מסוים שהוא לא עונה עליו, ושמדדתם: שאלות סיכום שלוקחות דקות (אנליטי), אותה קריאה יקרה שחוזרת אלפי פעמים (cache), רשומות בלי מבנה משותף שנקראות תמיד בשלמותן (מסמכים, ולפעמים עמודת JSON ב-Postgres מספיקה). כל מאגר נוסף הוא עוד דבר להריץ, לגבות, לנטר ולשמור מסונכרן. שאלו "מה יישבר אם לא נוסיף אותו?", לא "מה נוסיף?".

ומה עם שני תהליכים של השרת, שבפרק 5 ראינו שכל אחד מהם היה מכיר רק חצי מהשיחות? עכשיו שניהם קוראים את אותו בסיס נתונים. עם SQLite זה עובד כל עוד הם על אותו מחשב, וכותב אחד בכל רגע. כשהשרתים על מחשבים שונים, צריך בסיס נתונים שהוא שרת בעצמו, כמו Postgres. נגיע לזה בפרק 8.

Cache מקרוב: עותק מהיר, שלפעמים משקר

מכל המאגרים בטבלה, cache הוא זה שתפגשו הכי הרבה, ולא רק בתור Redis. הרעיון תמיד זהה: משהו יקר להשיג, כמו שאלה כבדה לבסיס הנתונים או קריאה ל-Claude שעולה כסף ולוקחת שניות, ולכן שומרים את התוצאה במקום מהיר, ובפעם הבאה מחזירים אותה משם. התבנית הנפוצה נקראת cache-aside: הקוד שלכם מסתכל קודם ב-cache, ורק אם אין שם תשובה הוא הולך למקור ושומר את מה שקיבל.

cache-aside
def cached_answer(cache: TTLCache, question: str) -> str:
    answer = cache.get(question)          # 1. look in the cache
    if answer is None:                    #    a miss: it is not there
        answer = slow_answer(question)    # 2. go to the source
        cache.set(question, answer)       # 3. keep a copy for next time
    return answer

כשהתשובה נמצאת ב-cache זה hit, וכשלא, miss. היחס ביניהם קובע אם ה-cache שווה משהו: על שאלות שכמעט לא חוזרות הוא רק מוסיף קוד וזיכרון.

המחיר הוא שמרגע שיש עותק, יש שתי גרסאות של האמת. אם המקור משתנה, ה-cache ממשיך להחזיר את התשובה הישנה, מהר ובלי שום סימן לכך שהיא ישנה. לנתון כזה קוראים stale. יש שתי דרכים מקובלות להגביל את הנזק, ולרוב משתמשים בשתיהן:

  • TTL (time to live): כל ערך נשמר לזמן קצוב, ואז נמחק מעצמו. פשוט, אבל עד שהזמן עובר התשובה עלולה להיות ישנה. ה-TTL הוא התשובה לשאלה "כמה זמן מותר לנו לטעות?": לשעות פתיחה, שעה. ליתרה בחשבון, אפס.
  • Invalidation: מי שמשנה את המקור גם מוחק את המפתח מה-cache. מדויק, אבל צריך לזכור לעשות את זה בכל מקום שכותב, ושכחה אחת היא באג שקשה למצוא.
שלושה כללים לפני שמוסיפים cache

המפתח כולל כל מה שהתשובה תלויה בו. אם התשובה תלויה במשתמש והמפתח הוא רק השאלה, משתמש אחד יקבל תשובה של משתמש אחר. זו דליפת מידע, לא רק באג.

המערכת עובדת נכון גם כשה-cache ריק. הוא עותק ולא מקור. אם מחיקה שלו שוברת משהו, שמרתם בו דבר שאסור לאבד.

מודדים קודם. Cache מסתיר איטיות ולא מתקן אותה, ולפעמים index (סעיף 6.5) מתקן אותה באמת.

ואיפה ה-cache יושב? מילון בזיכרון של התהליך הוא הפשוט ביותר (ב-Python יש גם functools.lru_cache, בלי TTL). אבל כל תהליך מחזיק עותק משלו, והעותק נמחק בכל הפעלה מחדש: אותה בעיה של שני התהליכים מפרק 5. Redis הוא שרת נפרד שכל התהליכים פונים אליו, ולכן כולם רואים אותו cache. בתרגיל 7 תבנו את הגרסה שבזיכרון, ותראו אותה מחזירה תשובה ישנה.

את אותו רעיון תפגשו שוב, בשמות אחרים: ה-layer cache של Docker (פרק 8), cache של תלויות ב-CI (פרק 9), ו-prompt caching מול Claude (פרק 19). גם הדפדפן שלכם שומר עותקים של דפים וקבצים. בכל המקרים השאלות זהות: מה המפתח, ומתי העותק מפסיק להיות נכון.

6.10תרגילים

כל התרגילים על הענף feature/database. בתרגילים שמשנים קוד, הריצו בסוף את ארבעת הכלים ו-commit. פתרונות, כולל הפלטים, נמצאים בדף נפרד.

תרגיל 1 · ארבע שאלות ב-SQL

מודרך

פתחו שוב את lab.db וכתבו, כל אחת בפקודה אחת:

  1. התוכן של ההודעות בשיחה c1, מהחדשה לישנה (רמז: DESC).
  2. כמה הודעות יש מכל role.
  3. הוסיפו שיחה c3 בלי הודעות, ומצאו בשאלה אחת את כל השיחות שאין בהן אף הודעה (רמז: LEFT JOIN ו-IS NULL).
  4. מחקו את השיחה c2 ואת ההודעות שלה. נסו קודם למחוק רק את השיחה, אחרי PRAGMA foreign_keys = ON;. מה קרה? עשו את זה נכון, ב-transaction אחת.

תרגיל 2 · מה באמת נשמר

מודרך

הגדירו בחלון $env:CHAT_MAX_TURNS = "2", הריצו את הסוכן ב-terminal (uv run python -m agent, עם CHAT_MOCK=1 ב-.env), וכתבו חמש הודעות. פתחו את agent.db וכתבו שאלה אחת שמחזירה לכל שיחה את המזהה, את created_at ואת מספר ההודעות, מהישנה לחדשה. בסוף, Remove-Item Env:CHAT_MAX_TURNS.

תרגיל 3 · כמה שווה index

בינוני

כתבו scripts\index_lab.py עם המודול sqlite3 של Python בלבד, ובסיס נתונים בזיכרון (sqlite3.connect(":memory:")), כדי שלא יישאר קובץ. הסקריפט יוצר טבלת messages, ממלא אותה ב-500,000 הודעות מזויפות ב-10,000 שיחות (executemany עם ?, לא f-string), ומודד את הזמן הממוצע של SELECT content FROM messages WHERE conversation_id = ? ORDER BY id על 200 שיחות שונות, לפני CREATE INDEX ואחריו. הדפיסו גם את ה-EXPLAIN QUERY PLAN ואת הזמן שלקח לבנות את ה-index. mypy agent scripts צריך לעבור.

תרגיל 4 · --continue

בינוני

ב-terminal, כל הרצה פותחת שיחה חדשה. הוסיפו ל-Conversations מתודה latest() שמחזירה את המזהה של השיחה החדשה ביותר, או None, בשאלה אחת (רמז: order_by(...desc()) ו-limit(1)). הוסיפו ל-chat_loop פרמטר resume: bool = False, ול-main דגל --continue עם argparse (continue היא מילה שמורה: dest="resume"). בהמשך שיחה, הדפיסו Continuing the last conversation (N turns).. כתבו בדיקה ב-test_cli.py שמריצה chat_loop פעמיים על אותו קובץ ב-tmp_path (רמז: dataclasses.replace על SETTINGS).

תרגיל 5 · בדיקות ל-transactions

בינוני

כתבו ב-test_conversations.py שלוש בדיקות, שבודקות את בסיס הנתונים ישירות, ב-SQL (engine.connect() ו-text("SELECT COUNT(*) FROM messages")), ולא דרך הקוד שנבדק: (א) מודל שנכשל (BrokenClient) לא משאיר אף שורה; (ב) delete מוחק גם את ההודעות של השיחה, ולא נוגע בשיחה אחרת; (ג) בסיס הנתונים מסרב ל-MessageRow של שיחה שלא קיימת (IntegrityError). אחר כך שברו בכוונה את send: שמרו את הודעת המשתמש ב-transaction משלה, לפני השאלה למודל. איזו בדיקה נכשלה? החזירו.

תרגיל 6 · לבחור מאגר

פתוח

לכל אחד מהתרחישים, בחרו איפה הייתם שומרים את הנתונים, והסבירו לפי הכלל מסעיף 6.9. מותר לענות "באותו Postgres", ומותר להציע שני מאגרים.

  1. מנהלת המוצר רוצה גרף יומי: כמה הודעות, כמה tokens ומאיזה מודל, על שנתיים של שיחות, 300 מיליון הודעות.
  2. הסוכן יקבל כלים (פרק 18). כל קריאה לכלי מחזירה JSON בצורה אחרת, ורוצים לשמור אותו ליד ההודעה.
  3. שאלת "מה שעות הפתיחה?" נשאלת אלף פעם ביום, ותשובה של Claude עולה כסף.
  4. צריך להגביל כל API key ל-60 בקשות בדקה (פרק 14).

תרגיל 7 · cache קטן, ונתון שהתיישן

בינוני

כתבו scripts\cache_lab.py, עם הספרייה הסטנדרטית בלבד. (א) מקור איטי: מילון SOURCE עם שאלה אחת ותשובה, ופונקציה slow_answer(question) שישנה 0.2 שניות (time.sleep) ואז מחזירה את התשובה. היא עומדת במקום קריאה יקרה למודל. (ב) מחלקה TTLCache(ttl) עם get (מחזירה None אם המפתח חסר או שזמנו עבר), set, delete, ומונים hits ו-misses. רמז: שמרו לכל מפתח את הערך ואת רגע התפוגה, עם time.monotonic(). (ג) cached_answer בתבנית cache-aside מסעיף 6.9. (ד) main שמדפיס חמישה שלבים, עם הזמן של כל קריאה: שלוש קריאות בלי cache; שלוש עם cache (TTL של שנייה) והמונים; שינוי של התשובה ב-SOURCE וקריאה נוספת; המתנה של 1.1 שניות וקריאה; ושינוי נוסף יחד עם cache.delete, וקריאה. mypy agent scripts צריך לעבור.

בסוף, עדכנו את README.md (DATABASE_URL בטבלת המשתנים, איך מסתכלים לתוך agent.db, --continue, הקבצים החדשים) ואת .env.example, commit, ואחדו: git switch main, git merge feature/database, git push, git branch -d feature/database.

6.13מילון מונחים

database
תוכנה ששומרת נתונים מחוץ לתהליך, ומבטיחה גישה בטוחה, מהירה ובו-זמנית אליהם.
relational
מודל שבו הכול בטבלאות, והקשרים בין טבלאות נבנים ממפתחות.
table / row / column
טבלה / רשומה אחת / שדה עם שם ו-type קבועים.
primary key
עמודה שהערך בה שונה בכל שורה, ומזהה אותה.
foreign key
עמודה שמצביעה על primary key בטבלה אחרת.
SQL
שפה הצהרתית לשאילת שאלות ולשינוי נתונים בבסיס נתונים רלציוני.
SQLite
בסיס נתונים רלציוני שכולו קובץ אחד, בלי שרת. מובנה ב-Python.
index
מבנה ממוין לצד הטבלה, שמאפשר למצוא שורות בלי לקרוא את כולה. מאט כתיבה.
transaction
קבוצת שינויים שמתקיימת כולה (COMMIT) או לא בכלל (ROLLBACK).
ACID
ארבע ההבטחות של transaction: atomicity, consistency, isolation, durability.
ORM
ספרייה שממפה מחלקות לטבלאות ואובייקטים לשורות, וכותבת את ה-SQL.
engine / session
ב-SQLAlchemy: החיבור לבסיס הנתונים / יחידת עבודה אחת מולו.
SQL injection
פרצה שבה קלט של משתמש הופך לחלק מפקודת SQL. נמנעת עם parameters.
document store
מאגר ששומר מסמכי JSON, בלי מבנה קבוע. למשל MongoDB.
columnar / analytical
מאגר ששומר עמודה-עמודה, ומהיר בסיכומים על המון שורות. למשל ClickHouse.
cache
עותק מהיר, בזיכרון, של נתונים שיש להם מקור אחר. למשל Redis.
cache hit / miss
התשובה נמצאה ב-cache / לא נמצאה, והולכים למקור.
cache-aside
תבנית: בודקים ב-cache, וב-miss קוראים מהמקור ושומרים עותק.
TTL
Time to live: כמה זמן ערך נשמר ב-cache לפני שהוא נמחק מעצמו.
stale
עותק שהמקור שלו כבר השתנה.
invalidation
מחיקה של ערך מה-cache ברגע שהמקור שלו משתנה.

6.14מה הלאה

הסוכן זוכר: כל הודעה נשמרת ב-transaction, שיחות שורדות הפעלה מחדש, ה-API, הדף וה-CLI לא השתנו, והבדיקות רצות על בסיס נתונים בזיכרון. אבל בצעד 7 ראיתם את הגבול: ברגע ש-agent.db מכיל נתונים, כל שינוי במבנה של טבלה, כמו כותרת לשיחה או מזהה משתמש, שובר את התוכנית. למחוק את הקובץ זה למחוק את השיחות של כולם.

איך משנים מבנה של טבלה שכבר מלאה, בלי לאבד דבר, ממלאים ערך לשורות הישנות, ויכולים לחזור אחורה אם משהו השתבש? זה פרק 7: Migrations, עם Alembic. ו-create_all יפנה שם את מקומו.
