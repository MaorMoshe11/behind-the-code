Messaging ו-pipelines

עבודה שהמשתמש לא צריך לחכות לה, פעולה שחוצה שני שירותים בלי transaction משותפת, ועבודה שרצה פעם בלילה: שלוש צורות של "לא עכשיו, ולא כאן".

בסוף הפרק תדעו

  • להבדיל בין קריאה סינכרונית להודעה, ובין queue ל-stream, ולבחור ביניהם.
  • להסביר topic, partition, key, offset ו-consumer group ב-Kafka, ולקרוא את ה-lag של צרכן.
  • להסביר את שלוש הבטחות המסירה, ולמה "exactly once" בפועל הוא "at least once" ועוד צרכן idempotent.
  • לבנות saga עם פעולת תיקון לכל צעד, ולומר מה היא לא נותנת.
  • לקרוא ולכתוב DAG של Airflow, ולדעת מתי מספיק cron ומתי צרכן של Kafka.

זמן משוער: חמש עד שש שעות. מה צריך: הפרויקט מסוף פרק 11, Docker Desktop עם כ-3 GB זיכרון פנוי, וחלון terminal אחד. הכול במצב mock.

12.3קריאה, queue ו-stream

בקריאה סינכרונית (פרק 11) השולח מחכה, והצד השני חייב להיות למעלה עכשיו. בהודעה, השולח מוסר אותה למתווך (broker), שרת שתפקידו לשמור הודעות, וממשיך. מי שצריך אותה יקרא אותה כשיוכל. אם הוא למטה, ההודעה מחכה. יש שני סוגים של מתווכים, והם מתנהגים אחרת לגמרי:

איך יודעים מה כבר נקראהמתווך מוחק מה שאושרכל קבוצה שומרת מיקום, offset, ומזיזה אותו בעצמה

האירועים של הצ'אט הם עובדות, ויהיו להם כמה צרכנים (היום סטטיסטיקה, מחר סיכומים). לכן stream. שימו לב לשם: אירוע (event) מתאר מה קרה, בזמן עבר (message.created), ולא מה לעשות. הצ'אט לא יודע מי קורא, וזה בדיוק העניין.

12.4Kafka בשש מילים

a sketch of chat-events: 3 partitions, each an append-only list
partition 0:  [0] [1] [2] [3] [4] [5]  <- every event with key 6b77... lands here
                          ^ usage-worker committed offset 3: it is done with 0 to 2
partition 1:  [0]                      <- key 02a1... lands here
partition 2:                           (no key has landed here yet)
  • Topic: שם לזרם של אירועים מסוג אחד, כמו טבלה. אצלנו chat-events.
  • Partition: topic מחולק לכמה רשימות, שנכתבות ונקראות במקביל. הסדר נשמר בתוך partition, לא בין partitions.
  • Key: ממנו נקבעת ה-partition. מפתח זהה, partition זהה, ולכן סדר. המפתח שלנו הוא מזהה השיחה: האירועים של שיחה אחת מגיעים לפי הסדר. בלי מפתח, אין הבטחה כזו.
  • Offset: המיקום של הודעה בתוך ה-partition: 0, 1, 2, וכן הלאה. לא משתנה לעולם.
  • Consumer group: צרכנים שעובדים יחד על topic. Kafka מחלק ביניהם את ה-partitions, כל אחת לצרכן אחד בקבוצה, ושומר לכל קבוצה את ה-offset שלה. שתי קבוצות שונות לא מפריעות זו לזו.
  • Commit: הצרכן מודיע "סיימתי עד כאן". מה שלא אושר יגיע שוב אחרי נפילה. Lag הוא הפער בין סוף ה-partition ל-offset שאושר: כמה הקבוצה מפגרת.

12.5הבטחות מסירה

הצרכן קורא הודעה, עושה את העבודה, ומאשר. נפילה יכולה לקרות בין כל שני צעדים, והסדר שבחרתם קובע מה יקרה:

הבטחהאיךאחרי נפילה
at most onceמאשרים, ואז עושיםההודעה לא תגיע שוב: אם העבודה לא נעשתה, היא אבדה
at least onceעושים, ואז מאשריםההודעה תגיע שוב: אם העבודה כבר נעשתה, היא תיעשה פעמיים
exactly onceat least once, ועוד צרכן שזוכר מה כבר עשהההודעה מגיעה שוב, והצרכן מזהה ומדלג

בפועל בוחרים כמעט תמיד at least once, ומטפלים בכפילויות. זה אותו רעיון של פרק 11: שם השירות זכר Idempotency-Key; כאן הצרכן זוכר event_id, באותה transaction של העבודה עצמה, כך שהשתיים נשמרות יחד או לא נשמרות בכלל. ל-Kafka יש גם מנגנון שנקרא exactly-once, אבל הוא מכסה רק כתיבות ל-Kafka עצמו; ברגע שהעבודה נכתבת לבסיס נתונים אחר, הוא לא עוזר.

שני מושגים נוספים. Dead letter queue (DLQ): הודעה שאי אפשר להבין (JSON שבור) תיכשל בכל ניסיון, והצרכן ייתקע עליה לנצח, כי בלי commit היא חוזרת. לכן מעבירים אותה ל-topic צדדי, chat-events-dlq, שאדם יסתכל בו, וממשיכים. וכתיבה כפולה (dual write): ה-api שומר הודעה ב-Postgres, ואז מפרסם אירוע ל-Kafka. אם התהליך נופל בין השניים, ההודעה נשמרה והאירוע לא נשלח לעולם. אין transaction שעוטפת Postgres ו-Kafka. הפתרון המקובל הוא outbox: כותבים את האירוע לטבלה באותו בסיס נתונים, באותה transaction של ההודעה, ותהליך נפרד קורא מהטבלה ומפרסם. בפרק הזה לא נבנה אותו; תתכננו אותו בתרגיל 6.

agent\events.py (shortened)
def event(kind: str, conversation_id: str, **fields: Any) -> dict[str, Any]:
    """One event. event_id is unique, so a consumer can tell a repeat from a new event."""
    return {"event_id": uuid.uuid4().hex, "type": kind, "conversation_id": conversation_id,
            "occurred_at": datetime.now(UTC).isoformat(), **fields}


class KafkaEvents:
    """Publishes events to a Kafka topic. Never blocks the chat: produce() only queues."""

    def __init__(self, servers: str, topic: str = TOPIC) -> None:
        self.topic = topic
        self.producer = Producer({
            "bootstrap.servers": servers,
            "acks": "all",  # the broker confirms only after the event is safely stored
            "enable.idempotence": True,  # a retried send is stored once, not twice
            "message.timeout.ms": 30000,  # give up on an event after 30 s
        })

    def publish(self, event: dict[str, Any]) -> None:
        # The key decides the partition: all events of one conversation stay in order.
        self.producer.produce(self.topic, key=event["conversation_id"],
                              value=json.dumps(event).encode("utf-8"), on_delivery=self._delivered)
        self.producer.poll(0)  # run the callbacks of earlier sends; do not wait

_delivered רושם ללוג אירוע שלא הגיע, ו-close() שולח את מה שעוד בתור, ונקרא כש-uvicorn נעצר (lifespan של FastAPI). ב-api.py, אחרי ש-conversations.send הצליח: publish("message.created", conversation_id, user_chars=..., reply_chars=...), ואחרי מחיקה conversation.deleted. create_app מקבל פרמטר שלישי, events, ו-tests\test_events.py מעביר רשימה שמשחקת את Kafka. 3ה-worker

חבילה חדשה, worker. ב-worker\usage.py טבלה usage (שיחה, תורות, תווים), ופונקציה שמחילה אירוע אחד, בלי Kafka, כדי שאפשר יהיה לבדוק אותה:

worker\usage.py (first version)
def apply(session: Session, event: dict[str, Any]) -> bool:
    """Apply one event, inside the caller's transaction."""
    conversation_id = event["conversation_id"]
    row = session.get(UsageRow, conversation_id)
    if event["type"] == "message.created":
        if row is None:
            row = UsageRow(conversation_id=conversation_id, turns=0, chars=0)
            session.add(row)
        row.turns += 1
        row.chars += event.get("user_chars", 0) + event.get("reply_chars", 0)
    elif event["type"] == "conversation.deleted" and row is not None:
        session.delete(row)
    return True

וב-worker\__main__.py הלולאה. שימו לב לסדר בסוף: קודם העבודה, אחר כך ה-commit. זה at least once:

worker\__main__.py (the loop, shortened)
    consumer = Consumer({
        "bootstrap.servers": servers,
        "group.id": group,  # the group's offsets are kept by Kafka, per partition
        "enable.auto.commit": False,  # we commit ourselves, after the work is done
        "auto.offset.reset": "earliest",  # a new group starts at the oldest event
    })
    consumer.subscribe([TOPIC])
    while running:  # SIGTERM (docker stop) sets running = False
        message = consumer.poll(1.0)
        ...
        try:
            event = parse(message.value())
        except BadEvent as problem:
            dead_letter(producer, message, str(problem))  # park it in chat-events-dlq
        else:
            with sessions.begin() as session:
                apply(session, event)
            log.info("partition %s offset %s: %s %s", ...)
            if crash:  # WORKER_CRASH_BEFORE_COMMIT=1, for step 5
                os._exit(1)  # die at once, like a power cut: no cleanup, no commit
        # Done with this message: move the group's offset past it.
        consumer.commit(message=message, asynchronous=False)
    consumer.close()  # leave the group, so its partitions move to another worker at once

12.7Saga: transaction בלי transaction

מחיקת שיחה צריכה לשנות שני בסיסי נתונים, של שני שירותים. Saga מחליפה את ה-transaction הגדולה, שאין, בשרשרת של צעדים מקומיים, שכל אחד מהם transaction רגילה בשירות אחד. לכל צעד יש פעולת תיקון (compensating action). אם צעד נכשל, מריצים את פעולות התיקון של הצעדים שכבר הצליחו, מהאחרון לראשון.

פעולת תיקון היא לא rollback. Rollback מבטל משהו שאף אחד לא ראה. פעולת תיקון היא פעולה חדשה שמבטלת במובן העסקי: הערה שנמחקה "חוזרת" כהערה חדשה, עם מזהה חדש. כך גם בעולם: טיסה שבוטלה לא נמחקת מההיסטוריה, מקבלים החזר.

יתרוןהזרימה כתובה במקום אחד; קל להבין ולבדוקאין תלות בשירות מרכזי; הוספת משתתף לא משנה אחרים

שלושה כללים. כל צעד וכל תיקון חייבים להיות idempotent: אחרי timeout לא יודעים אם צעד קרה (פרק 11), ומנסים שוב. הסדר חשוב: קודם צעדים שקל לתקן, ואחרונה נקודת האל-חזור (pivot), שאחריה רק מתקדמים. ואין בידוד (isolation): בין הצעדים, אחרים רואים מצב ביניים, למשל שיחה שעוד קיימת וההערות שלה כבר נמחקו. לכן הצעד הראשון שלנו מסתיר את השיחה (ארכוב), כדי שאיש לא יכתוב אליה בזמן המחיקה.

@dataclass(frozen=True)
class Step:
    name: str
    action: Callable[[], None]
    compensate: Callable[[], None] | None = None  # None: nothing to undo


def run_saga(name: str, steps: list[Step]) -> None:
    """Run the steps in order. If one fails, compensate those done, then raise its error."""
    done: list[Step] = []
    for step in steps:
        try:
            step.action()
        except Exception:
            log.warning("saga %s: step %r failed; compensating", name, step.name)
            for finished in reversed(done):
                if finished.compensate is None:
                    continue
                try:
                    finished.compensate()
                    log.warning("saga %s: compensated %r", name, finished.name)
                except Exception:
                    # Now the data is inconsistent, and only a person can fix it: say so loudly.
                    log.exception("saga %s: COMPENSATION FAILED for %r", name, finished.name)
            raise
        log.info("saga %s: step %r done", name, step.name)
        done.append(step)

12.9Batch, streaming ו-Airflow

ה-worker הוא streaming: כל אירוע מטופל כשהוא מגיע, והתוצאה תמיד כמעט עדכנית. דוח יומי הוא batch: פעם בלילה, על כל הנתונים של יום שהסתיים, ממקור האמת (טבלת ההודעות). Batch פשוט יותר, זול יותר, וקל לתקן: באג בדוח של אתמול? מתקנים, ומריצים את אתמול שוב.

מתזמן (scheduler) או מתזמר (orchestrator) של pipelines מריץ עבודות לפי לוח זמנים ולפי תלויות ביניהן. Airflow הוא הנפוץ שבהם. המושגים שלו:

  • DAG (directed acyclic graph): pipeline אחד, משימות וחצים ביניהן, בלי מעגלים. נכתב כקובץ Python.
  • Task: צעד אחד. תלות: write רץ רק אחרי ש-extract הצליח.
  • Schedule: מתי, בתחביר של cron. Retries: כמה פעמים לנסות שוב משימה שנכשלה.
  • Backfill: הרצה על ימים שעברו, למשל אחרי תיקון באג. אפשרי רק אם כל משימה idempotent: יום שרץ פעמיים נותן אותה תוצאה, לא שתי תוצאות.

הקוד עצמו נמצא ב-pipelines\usage_report.py, ב-Python רגיל, בלי Airflow: extract(database_url, day) מחזירה שורה לכל שיחה (שאילתת GROUP BY על messages בין חצות לחצות, UTC), ו-write_report(rows, day, folder) כותבת reports\usage-<day>.csv לקובץ צדדי ואז מחליפה, כך שהרצה שנייה דורסת את הראשונה ואין לעולם חצי קובץ. כך בודקים אותן ב-pytest, ומריצים ביד:

import os
from datetime import date, datetime, timedelta
from pathlib import Path
from typing import Any

from airflow.sdk import dag, task

from pipelines import usage_report

DATABASE_URL = os.environ.get("REPORT_DATABASE_URL", "sqlite:///agent.db")
REPORTS = Path(os.environ.get("REPORT_FOLDER", "reports"))


def day_before(logical_date: datetime | None) -> date:
    """The run at 02:00 on the 19th reports on the 18th, a day that is over."""
    assert logical_date is not None  # Airflow passes it to every scheduled run
    return logical_date.date() - timedelta(days=1)


@dag(
    schedule="0 2 * * *",  # cron: every day at 02:00 UTC
    start_date=datetime(2026, 11, 1),  # no run is about anything earlier
    catchup=False,  # do not run every missed night at once; backfill on purpose
    default_args={"retries": 2, "retry_delay": timedelta(minutes=5)},
    tags=["my-agent"],
)
def daily_usage_report() -> None:
    @task
    def extract(logical_date: datetime | None = None) -> list[dict[str, Any]]:
        # Airflow fills logical_date from the run (it is a name Airflow knows).
        return usage_report.extract(DATABASE_URL, day_before(logical_date))

    @task
    def write(rows: list[dict[str, Any]], logical_date: datetime | None = None) -> str:
        return str(usage_report.write_report(rows, day_before(logical_date), REPORTS))

    write(extract())  # extract runs first; its rows reach write through XCom


daily_usage_report()
  1. from airflow.sdk import dag, task: הממשק של Airflow 3 לכתיבת DAGs. Airflow לא תלות של הפרויקט: הקובץ רץ בתוך התקנה של Airflow, שצריכה גם את pipelines (ולכן pipelines לא מייבא את agent).
  2. ההגדרות מגיעות ממשתני סביבה, כמו בכל השירותים שלנו: Airflow רץ במקום אחר, עם בסיס נתונים בכתובת אחרת.
  3. day_before: על איזה יום הריצה. logical_date הוא הזמן שהריצה "שייכת" לו. הריצה של 02:00 ב-19 מדווחת על ה-18, יום שכבר נגמר. בלי זה, הדוח היה על יום שרק התחיל.
  4. @dag(...): לוח הזמנים (cron: דקה 0, שעה 2, כל יום), מאיזה תאריך, ו-catchup=False: מי שמפעיל את ה-DAG לראשונה לא מקבל ריצה על כל לילה מאז start_date. ימים שעברו מריצים בכוונה (backfill). retries=2: בסיס נתונים שלא ענה בשתיים בלילה מקבל עוד שתי הזדמנויות, חמש דקות זו מזו.
  5. @task: כל פונקציה היא משימה, שרצה בתהליך משלה, אולי על מכונה אחרת. לכן היא דקה: קוראת לפונקציה הרגילה, ולא יותר.
  6. write(extract()): נראה כמו קריאה, אבל בזמן שהקובץ נקרא היא רק מתארת את הגרף: extract לפני write. ערך ההחזרה של extract נשמר ב-XCom, המנגנון של Airflow להעביר ערכים קטנים בין משימות, ומגיע ל-write. נתונים גדולים לא מעבירים כך: כותבים לקובץ או לטבלה, ומעבירים את השם.

--- 4. smoke test: one message, then delete the conversation
    ok: [mock reply, turn 1] You said: smoke test
staging runs my-agent:0.12.0.

ה-smoke test מוחק את השיחה שלו, כלומר עובר כבר דרך ה-saga, וב-logs worker של staging מופיעים message.created ו-conversation.deleted שלו.

12.11תרגילים

על compose מהדוגמה המודרכת (docker compose up -d --wait). שינויי קוד על ענף, עם שורה תחת Unreleased. פתרונות, עם הפלטים, בדף נפרד. בסוף, docker compose stop: Kafka אוכל זיכרון.

תרגיל 3 · שני workers, ואז ארבעה

בינוני

docker compose up -d --scale worker=2 worker, חכו כמה שניות, ו-kafka-consumer-groups.sh ... --describe --group usage-worker. שלחו הודעות בשתי שיחות שהאירועים שלהן ב-partitions שונות, ו-docker compose logs worker --tail 2. אחר כך --scale worker=4, ו---describe --group usage-worker --members. בסוף, --scale worker=1.

תרגיל 4 · הצעד השלישי נכשל

בינוני

ב-tests\test_saga.py, כתבו test_a_failure_after_the_notes_were_deleted_restores_them: שיחה עם שתי הערות בשירות המזויף, ו-monkeypatch.setattr(conversations, "delete", broken_delete) עם פונקציה שזורקת RuntimeError. הריצו את ה-saga, ובדקו ששתי ההערות חזרו, באילו מזהים, ושהשיחה עדיין נגישה (conversations.title).

תרגיל 5 · Backfill

בינוני

עם DATABASE_URL של צעד 12.9: foreach ($d in 15..18) { uv run python -m pipelines.usage_report --day "2026-11-$d" } (החליפו בתאריכים שלכם), ואז את היום האחרון שוב, ו-ls reports. אם יש לכם זמן וזיכרון, הריצו גם את try_in_docker.sh, עם תאריך משלכם כפרמטר אחרון.

תרגיל 6 · תכנון outbox

פתוח

היום, אירוע שה-api לא הספיק לשלוח אובד (12.5). כתבו ב-docs\architecture.md סעיף "Plan: an outbox": איזו טבלה, מי כותב אליה ובאיזו transaction, מי קורא ממנה ושולח, מתי שורה נחשבת "נשלחה", ומה קורה כשהשולח נופל בין השליחה לסימון. עדכנו גם את "Known gaps". Commit.

12.14מילון מונחים

message broker
שרת ששומר הודעות בין מי ששולח למי שקורא.
queue
מתווך שבו כל הודעה הולכת לצרכן אחד ונמחקת אחרי שאושרה.
stream / log
מתווך שבו ההודעות נשמרות לפי הסדר, וכל קבוצת צרכנים קוראת את כולן בקצב שלה.
event
הודעה שמתארת עובדה שקרתה, בזמן עבר.
topic
שם לזרם של אירועים ב-Kafka.
partition
חלק של topic; הסדר נשמר בתוכו.
key
הערך שקובע את ה-partition של אירוע.
offset
המיקום של הודעה בתוך partition.
consumer group
צרכנים שמחלקים ביניהם את ה-partitions; לכל קבוצה offsets משלה.
commit
אישור של צרכן: "קראתי עד כאן".
lag
כמה הודעות קבוצה עוד לא אישרה.
replay
קריאה מחדש של הודעות ישנות.
at least once
כל הודעה מטופלת, אולי יותר מפעם אחת.
idempotent consumer
צרכן שזוכר מה כבר טיפל בו, ומדלג על חזרות.
dead letter queue
מקום צדדי להודעות שאי אפשר לטפל בהן.
dual write
כתיבה לשני מקומות בלי transaction משותפת; אחת יכולה להצליח והשנייה לא.
outbox
טבלה שבה נכתב האירוע יחד עם השינוי, ותהליך נפרד שמפרסם ממנה.
saga
פעולה על כמה שירותים, כשרשרת צעדים מקומיים עם פעולת תיקון לכל אחד.
compensating action
פעולה חדשה שמבטלת צעד במובן העסקי.
orchestration / choreography
מתזמר אחד שמריץ את הצעדים / שירותים שמגיבים לאירועים זה של זה.
batch / streaming
הרבה נתונים בבת אחת, בלוח זמנים / כל אירוע כשהוא מגיע.
DAG
pipeline ב-Airflow: משימות, ותלויות ביניהן בלי מעגלים.
backfill
הרצה של pipeline על תקופות שעברו.

12.15מה הלאה

תסתכלו כמה מקומות פתחתם בפרק הזה כדי להבין מה קרה: agent.log בתוך ה-container של ה-api, docker compose logs worker, כלי של Kafka בתוך עוד container, ו-psql בשני בסיסי נתונים. עכשיו דמיינו שמשתמש כותב "מחקתי שיחה, והיא חזרה". איזו בקשה זו הייתה? באיזה שירות הצעד נכשל, כמה זמן זה לקח, ומי עוד הושפע? היום אין דרך לחבר שורה בלוג של הצ'אט לשורה בלוג של שירות ההערות ולאירוע ב-Kafka.

לוגים מובנים עם מזהה בקשה שעובר בין שירותים, מדדים, tracing, התראות, ותקלה שתאבחנו מהלוגים בלבד: פרק 13: מערכת חיה.
