Deployment וענן

איך לוקחים את ה-image הבדוק מפרק 9 ומריצים אותו בשביל אנשים אחרים: בכמה סביבות, עם סודות במקום הנכון, עם בדיקות בריאות, ועם דרך חזרה כשגרסה נשברת.

בסוף הפרק תדעו

  • להסביר מה זה deployment, ולמה staging ו-prod הם אותו image עם הגדרות שונות.
  • לשמור סודות מחוץ לקוד, ל-git ול-image, ולהעביר אותם לשירות כקבצים, כמו ש-secrets manager עושה.
  • להבדיל בין liveness ל-readiness, ולחבר אותם ל-healthcheck ול-restart policy.
  • לפרוס גרסה, לבדוק אותה, לקדם אותה ל-prod, ולחזור לגרסה הקודמת בלי לשבור את בסיס הנתונים.
  • לקרוא מפה של שירותי ענן ודוגמה של infrastructure as code (Terraform), ולדעת אילו שאלות לשאול לפני שמשהו עולה לענן.

זמן משוער: ארבע עד חמש שעות. מה צריך: הפרויקט מסוף פרק 9 ו-Docker Desktop. החלק המעשי רץ כולו במחשב שלכם: שתי סביבות, זו לצד זו. החלק על הענן הוא קריאה בלבד, בלי חשבון ובלי כרטיס אשראי.

10.1הבעיה: "אצלי זה עובד" כבר לא מספיק

דנה, חברה מהצוות, רוצה לנסות את הסוכן מהמחשב שלה. יש לכם image מתויג, my-agent:0.9.0, אז נראה שנשאר רק להריץ אותו על מכונה שהיא יכולה להגיע אליה:

PowerShell
docker run --rm my-agent:0.9.0
output (the end)
  File "/app/agent/api.py", line 99, in create_app
    raise ConfigError("AGENT_API_KEY is not set. Put a long random value in .env.")
agent.config.ConfigError: AGENT_API_KEY is not set. Put a long random value in .env.

במחשב שלכם המפתח הגיע מ-.env, וה-.dockerignore מפרק 8 שומר שהקובץ הזה לא ייכנס ל-image. התיקון המהיר שעולה בראש הוא לכתוב את מה שחסר ישר ב-Dockerfile, ובהזדמנות גם ליצור שם את בסיס הנתונים, כדי שה-image "פשוט יעבוד בכל מקום":

Dockerfile (a quick fix: do not do this)
ENV AGENT_API_KEY=dana-7Qx2-test CHAT_MOCK=1
RUN alembic upgrade head

וזה באמת עובד: docker build -t my-agent:quickfix ., docker run, דנה שולחת הודעה ומקבלת תשובה. ואז שלוש בעיות, אחת אחרי השנייה:

docker image inspect --format "{{json .Config.Env}}" my-agent:quickfix (shortened)
["PATH=/app/.venv/bin:...","PYTHONUNBUFFERED=1","AGENT_API_KEY=dana-7Qx2-test","CHAT_MOCK=1"]
  • סוד במקום הלא נכון. כל מי שיכול להוריד את ה-image (וב-registry של פרק 9 זה עשוי להיות כל העולם) קורא את המפתח בפקודה אחת. ו-docker history מראה אותו גם בשכבות.
  • הגדרות שאי אפשר לשנות. CHAT_MOCK=1 אפוי בפנים. כדי שמשתמשים אמיתיים יקבלו תשובות אמיתיות צריך image אחר, כלומר גרסה אחרת של מה שבדקתם. ובסיס הנתונים הוא קובץ SQLite בתוך ה-image: כשהחלפנו את ה-container בחדש, GET /conversations החזיר []. השיחה של דנה נעלמה.
  • אין דרך חזרה. מחר תבנו גרסה חדשה, תחליפו את ה-container, ומשהו יישבר. מה רץ קודם? באיזו פקודה מחזירים אותו? ו-docker compose up --build של פרק 8 בונה my-agent-api:latest, שם שכל בנייה דורסת.

הפרק הזה עונה על שלושתן. להריץ תוכנה בשביל אחרים, באופן שאפשר לחזור עליו ולבטל אותו, נקרא deployment (פריסה). מכאן נכתוב deploy.

10.3סביבות הן הגדרות, לא קוד

סביבה (environment) היא מקום שבו גרסה של השירות רצה, עם הנתונים, ההגדרות והסודות של אותו מקום. שלוש מקובלות:

סביבהבשביל מינתוניםאצלנו
localמי שכותב את הקודמה שתרצו; מוחקים בלי לחשובuv run ו-compose.yaml מפרק 8
stagingהצוות: לנסות גרסה לפני המשתמשיםנתוני ניסוי. אפשר לאפסdeploy/staging.env
prod (production)המשתמשיםאמיתיים. לא מאפסים לעולםdeploy/prod.env

הכלל החשוב: אותו image בכל הסביבות, וההבדל ביניהן נמצא כולו בהגדרות שמגיעות מבחוץ, כמו שפרק 1 הבטיח. אם בונים image נפרד ל-prod, מה שרץ אצל המשתמשים הוא לא מה שבדקתם ב-staging. גם בקוד אין מקום ל-if env == "prod" מפוזר: כל הבדל הוא ערך של הגדרה (רמת לוג, מספר תורות, כתובת בסיס נתונים), והקוד קורא את הערך.

הקוד כן צריך לדעת באיזו סביבה הוא, משתי סיבות: כדי לדווח עליה (בלוג וב-/ready, שנבנה עוד מעט), וכדי לסרב לברירות מחדל מסוכנות. לשם כך משתנה אחד, APP_ENV, עם שלושה ערכים מותרים. ערך אחר (production, Prod) הוא שגיאת הקלדה, והשירות לא עולה. וברירת המחדל של DATABASE_URL, קובץ SQLite בתיקייה הנוכחית, מותרת רק ב-local: שרת שהיה נופל אליה בשקט היה שומר שיחות בתוך ה-container, ומאבד אותן בהחלפה הבאה, כמו השיחה של דנה.

10.4סודות: איפה הם גרים בכל סביבה

סוד (secret) הוא ערך שמי שמחזיק אותו יכול לפעול בשמכם: מפתח API, סיסמה של בסיס נתונים. הגדרה (configuration) היא ערך שאין בעיה שכל הצוות יראה: פורט, רמת לוג, שם מודל. ההפרדה ביניהם קובעת איפה כל אחד נשמר:

איפההגדרותסודות
local.env, או ברירות מחדל בקוד.env, שאינו ב-git (פרק 2)
CIבקובץ ה-workflowrepository secrets של GitHub (פרק 9)
staging, prod אצלנוdeploy/<env>.env, ב-gitקבצים ב-deploy/secrets/<env>/, מחוץ ל-git ול-image
בענןהגדרות השירות, או קובץ ב-git (10.10)secrets manager: שירות שמחזיק סודות מוצפנים

Secrets manager שומר כל סוד מוצפן, נותן גישה רק למי שקיבל הרשאה (השירות עצמו, לא כל מפתח בצוות), רושם מי קרא מה ומתי, ומאפשר להחליף ערך בלי לגעת בקוד. השירות מקבל את הסוד בזמן ריצה, באחת משתי דרכים: כמשתנה סביבה, או כקובץ שמופיע בתוך ה-container. הקובץ עדיף: משתני סביבה מופיעים ב-docker inspect, עוברים לכל תהליך-בן, ונדפסים בטעות בלוגים של שגיאה. גם Docker Compose יודע להחזיק סודות כקבצים: הוא מרכיב כל קובץ, לקריאה בלבד, בנתיב /run/secrets/<name>. זה מה שנבנה. המוסכמה המקובלת לקריאה: אם NAME_FILE מוגדר, קוראים את הסוד מהקובץ שהוא מצביע עליו; אחרת מ-NAME. ה-image הרשמי של Postgres כבר תומך בה (POSTGRES_PASSWORD_FILE).

ועוד הפרדה אחת: DATABASE_URL בפרק 8 הכיל את הסיסמה בתוכו. מעכשיו הכתובת (איפה בסיס הנתונים) היא הגדרה, והסיסמה סוד נפרד, DATABASE_PASSWORD, שהקוד משלב בכתובת.

10.5חי, מוכן, ומה עושים עם זה

בתרגיל 4 של פרק 8 ראיתם ש-/health עונה ok גם כש-Postgres כבוי. הוא לא משקר: התהליך באמת חי. הוא פשוט עונה על שאלה אחת, ויש שתיים:

liveness (חי)readiness (מוכן)
השאלההתהליך עונה, או שהוא תקוע?העותק הזה יכול לשרת בקשה עכשיו?
בודקתרק את עצמה. בלי בסיס נתוניםגם את מה שהבקשה צריכה: בסיס הנתונים
כשהיא נכשלתמפעילים את התהליך מחדשמפסיקים לשלוח אליו בקשות, ומחכים
אצלנוGET /healthGET /ready: 200, או 503 כשבסיס הנתונים לא עונה

למה לא לבדוק את בסיס הנתונים גם ב-liveness? כי אז Postgres שנפל לדקה גורם לכל העותקים של השירות להיות מופעלים מחדש, שוב ושוב, ואף אחד מהם לא מתקן כלום. הפעלה מחדש עוזרת רק לבעיה שבתוך התהליך.

מי שואל את השאלות? מערכת שמריצה containers (orchestrator, כמו Kubernetes או שירות ענן) שואלת את שתיהן בנפרד ופועלת לפי הטבלה. Docker לבד פשוט יותר, ושני כלים שלו נכנסים לפרק:

  • HEALTHCHECK ב-Dockerfile: פקודה ש-Docker מריץ בתוך ה-container כל כמה שניות. שלושה כישלונות ברצף, והסטטוס הופך ל-unhealthy. Docker רק מדווח (ב-docker ps, וב-docker compose up --wait שמחכה ל-healthy); הוא לא מפעיל מחדש בגלל זה. נחבר אותו ל-/ready.
  • Restart policy ב-compose: restart: unless-stopped מפעיל מחדש container שהתהליך שלו יצא, עד שמישהו עוצר אותו ביד. זה בדיוק המקרה של השירות שלנו כשבסיס הנתונים לא זמין בהפעלה: make_engine נכשל, uvicorn יוצא, ו-Docker מנסה שוב, עד שבסיס הנתונים חוזר.

ב-agent\config.py נוספים ENVIRONMENTS = ("local", "staging", "prod"), שדה app_env: str = "local" בסוף Settings, ושלוש פונקציות:

agent\config.py (new parts)
from sqlalchemy.engine import make_url

def read_secret(name: str) -> str | None:
    """A secret from the file named in NAME_FILE (how secret stores hand them over), or NAME."""
    path = os.getenv(f"{name}_FILE")
    if path:
        try:
            return Path(path).read_text(encoding="utf-8").strip() or None
        except OSError as error:
            raise ConfigError(f"{name}_FILE is {path!r}, which cannot be read.") from error
    return os.getenv(name) or None


def read_app_env() -> str:
    """APP_ENV: local (the default), staging or prod. Anything else is a typo, so stop."""
    app_env = os.getenv("APP_ENV", "local")
    if app_env not in ENVIRONMENTS:
        raise ConfigError(f"APP_ENV must be one of {', '.join(ENVIRONMENTS)}, got {app_env!r}.")
    return app_env


def database_url() -> str:
    """DATABASE_URL, with the password from DATABASE_PASSWORD(_FILE) when that is set.

    The URL says where the database is (configuration); the password is a secret.
    """
    url = os.getenv("DATABASE_URL")
    if url is None:
        if read_app_env() != "local":
            # A server must never fall back to a SQLite file inside its container.
            raise ConfigError("DATABASE_URL is not set. Outside local, it is required.")
        url = DEFAULT_DATABASE_URL
    password = read_secret("DATABASE_PASSWORD")
    if password:
        url = make_url(url).set(password=password).render_as_string(hide_password=False)
    return url

ב-load_settings: api_key=read_secret("ANTHROPIC_API_KEY"), agent_api_key=read_secret("AGENT_API_KEY"), database_url=database_url(), app_env=read_app_env(). ה-migrations צריכות אותה כתובת, ולכן ב-migrations\env.py השורה של url הופכת ל-url = config.attributes.get("url") or database_url() (והייבוא בהתאם). make_url(...).set(password=...) מכניס את הסיסמה בצורה נכונה גם כשיש בה תווים כמו @ או /, ששרשור מחרוזות היה שובר.

2/ready, ובדיקה בתוך ה-image

agent\api.py (in create_app, after /health)
    @app.get("/ready")
    def ready(response: Response) -> dict[str, str]:
        """Readiness: can this copy serve a chat right now? It needs the database for that."""
        info = {"version": project_version(), "environment": settings.app_env}
        try:
            with engine.connect() as connection:
                connection.execute(text("SELECT 1"))
        except SQLAlchemyError:
            log.warning("not ready: the database does not answer")
            response.status_code = 503
            return {"status": "not ready", "database": "unreachable", **info}
        return {"status": "ready", "database": "ok", **info}

(הייבוא: Response מ-fastapi, text מ-sqlalchemy, SQLAlchemyError מ-sqlalchemy.exc. ולפני make_engine, שורת לוג: log.info("starting my-agent %s, environment %s", project_version(), settings.app_env).) התשובה כוללת את הגרסה והסביבה: אחרי deploy זו הדרך לוודא מה באמת רץ.

בדיקת מוכנות חייבת לענות מהר, גם כשהיא נכשלת. Postgres שלא עונה יכול להשאיר את psycopg מחכה דקות (פרק 8). ב-agent\db.py, ב-make_engine, ענף חדש לפני ה-else:

עכשיו הבודק עצמו, שרץ בתוך ה-container. ב-python:3.13-slim אין curl, אבל יש Python:

agent\healthcheck.py
"""The container's health check: exit 0 when the service is ready, 1 when it is not.

Docker runs it inside the container, every few seconds (HEALTHCHECK in the Dockerfile).
"""

import sys
import urllib.error
import urllib.request

READY_URL = "http://127.0.0.1:8000/ready"


def main() -> None:
    try:
        # A health check that hangs is worse than one that fails: always a timeout.
        with urllib.request.urlopen(READY_URL, timeout=3) as response:
            print(f"ready ({response.status})")
    except urllib.error.HTTPError as error:  # the service answered: 503, not ready
        sys.exit(f"not ready ({error.code})")
    except OSError as error:  # no answer at all: the process is down or stuck
        sys.exit(f"no answer: {error}")


if __name__ == "__main__":
    main()
Dockerfile (before CMD)
# Docker asks every 5 s: is the service ready? 3 failures in a row mark it "unhealthy".
HEALTHCHECK --interval=5s --timeout=4s --start-period=20s --retries=3 \
    CMD ["python", "-m", "agent.healthcheck"]

--start-period נותן לשירות 20 שניות לעלות, שבהן כישלון לא נספר. ב-tests\test_api.py שתי בדיקות: /ready עונה ready; וכש-Engine.connect מוחלף (monkeypatch) בפונקציה שזורקת OperationalError, /ready מחזיר 503 ו-/health עדיין 200. git add -A, git commit -m "Add /ready, and a health check inside the image".

3תיאור של סביבה: deploy\compose.yaml

קובץ compose אחד לכל הסביבות שנפרסות. אין בו build: ה-image נבנה פעם אחת, ממקום אחר. כל מה שמשתנה בין סביבות הוא ${...}, ש-compose ממלא מקובץ ההגדרות של הסביבה:

deploy\compose.yaml
# One deployed environment of my-agent: its own database, migrations and API.
# The same file serves staging and prod; deploy/<environment>.env says how they differ.
# Run it through scripts/deploy.py, which passes the project name and the env file.
services:
  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: agent
      POSTGRES_DB: agent
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password  # the image reads the file itself
    secrets: [db_password]
    volumes:
      - pgdata:/var/lib/postgresql/data  # one volume per environment: separate data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U agent -d agent"]
      interval: 2s
      timeout: 5s
      retries: 30
    restart: unless-stopped

  migrate:
    image: my-agent:${IMAGE_TAG:?IMAGE_TAG is not set}  # the image is built once, never here
    command: ["alembic", "upgrade", "head"]
    environment:
      DATABASE_URL: postgresql+psycopg://agent@db:5432/agent  # where: configuration
      DATABASE_PASSWORD_FILE: /run/secrets/db_password  # the password: a secret
      APP_ENV: ${APP_ENV:?APP_ENV is not set}
    secrets: [db_password]
    depends_on:
      db:
        condition: service_healthy
    profiles: [migrate]  # runs only when asked for: a separate step of a deploy

  api:
    image: my-agent:${IMAGE_TAG:?IMAGE_TAG is not set}
    environment:
      APP_ENV: ${APP_ENV}
      DATABASE_URL: postgresql+psycopg://agent@db:5432/agent
      DATABASE_PASSWORD_FILE: /run/secrets/db_password
      AGENT_API_KEY_FILE: /run/secrets/agent_api_key
      CHAT_MOCK: ${CHAT_MOCK:-0}
      CHAT_MODEL: ${CHAT_MODEL:-claude-opus-5-5}
      CHAT_MAX_TURNS: ${CHAT_MAX_TURNS:-10}
      CHAT_LOG_LEVEL: ${CHAT_LOG_LEVEL:-INFO}
    secrets: [db_password, agent_api_key]
    ports:
      - "127.0.0.1:${API_PORT:?API_PORT is not set}:8000"
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped  # if the process exits, Docker starts it again

# Each secret is a file on the host that never enters git or the image. Compose mounts it
# read-only at /run/secrets/<name> inside the containers that list it.
secrets:
  db_password:
    file: ./secrets/${APP_ENV}/db_password.txt
  agent_api_key:
    file: ./secrets/${APP_ENV}/agent_api_key.txt

scripts\deploy.py (main; the helpers read_env_file, run and call are in the checkpoint)
def main() -> None:
    parser = argparse.ArgumentParser(description="Deploy one environment and check it.")
    parser.add_argument("environment", choices=["staging", "prod"])
    parser.add_argument("--skip-migrations", action="store_true", help="for a rollback")
    args = parser.parse_args()
    env_file = DEPLOY / f"{args.environment}.env"
    config = read_env_file(env_file)
    version, base = config["IMAGE_TAG"], f"http://127.0.0.1:{config['API_PORT']}"
    compose = ["docker", "compose", "-p", f"my-agent-{args.environment}"]
    compose += ["-f", str(DEPLOY / "compose.yaml"), "--env-file", str(env_file)]

    print(f"=== deploy my-agent:{version} to {args.environment}", flush=True)
    if args.skip_migrations:
        print("--- 1. migrations: skipped", flush=True)
    else:
        print("--- 1. migrations, with the new image", flush=True)
        run([*compose, "run", "--rm", "migrate"])
    print("--- 2. start the new containers, and wait until they are healthy", flush=True)
    run([*compose, "up", "-d", "--wait", "--wait-timeout", "120"])
    try:
        print("--- 3. /ready reports the new version", flush=True)
        ready = call("GET", f"{base}/ready")
        print(f"    {ready}", flush=True)
        if ready["version"] != version:
            sys.exit(f"FAILED: {args.environment} runs {ready['version']}, not {version}.")
        print("--- 4. smoke test: one message, then delete the conversation", flush=True)
        key = (DEPLOY / "secrets" / args.environment / "agent_api_key.txt").read_text().strip()
        reply = call("POST", f"{base}/chat", key, {"message": "smoke test"})
        call("DELETE", f"{base}/conversations/{reply['conversation_id']}", key)
        print(f"    ok: {reply['reply']}", flush=True)
    except OSError as error:  # urllib's errors: no answer, or an error status
        sys.exit(f"FAILED: {error}")
    print(f"{args.environment} runs my-agent:{version}.")

-p my-agent-staging הוא שם ה-project של compose: כל ה-containers, הרשת וה-volume מקבלים אותו כקידומת, ולכן שתי הסביבות לא נוגעות זו בזו. --wait מחכה שכל container יהיה healthy, וזה ה-HEALTHCHECK מצעד 2. Smoke test היא בדיקה קצרה אחרי deploy, שמוודאת שהדבר הבסיסי עובד באמת ("אין עשן"). git add -A, git commit -m "Describe the staging and prod environments, with their secrets outside git".

10.10Infrastructure as code

אפשר להקים את כל זה בלחיצות באתר של הספק. אחרי חצי שנה אף אחד לא יודע מי שינה מה, ו-staging כבר לא דומה ל-prod. Infrastructure as code (IaC) פירושו לתאר את התשתית בקבצים שנמצאים ב-git: עוברים review, יש להם היסטוריה, ומקימים מהם סביבה שנייה זהה. הכלי הנפוץ, שעובד עם כל הספקים, הוא Terraform (ויש לו גרסה פתוחה תואמת, OpenTofu). הנה staging שלנו על Google Cloud, מקוצר. לקריאה בלבד: לא מריצים אותו בפרק.

main.tf (a sketch for reading: no network, database user, IAM or migrations job)
terraform {
  required_providers {
    google = { source = "hashicorp/google" }
  }
}

variable "project" { type = string }
variable "image_tag" { type = string } # the version to run, like IMAGE_TAG

provider "google" {
  project = var.project
  region  = "europe-west1"
}

# The managed database. deletion_protection: `terraform destroy` refuses to delete it.
resource "google_sql_database_instance" "db" {
  name                = "my-agent-staging"
  database_version    = "POSTGRES_17"
  deletion_protection = true
  settings {
    edition = "ENTERPRISE"
    tier    = "db-f1-micro"
  }
}

# A place for a secret. The value is added by a person, never written in this file.
resource "google_secret_manager_secret" "agent_api_key" {
  secret_id = "my-agent-staging-agent-api-key"
  replication {
    auto {}
  }
}

# The service: the same image as on your computer, with staging's settings.
resource "google_cloud_run_v2_service" "api" {
  name     = "my-agent-staging"
  location = "europe-west1"
  template {
    containers {
      image = "europe-west1-docker.pkg.dev/${var.project}/my-agent/my-agent:${var.image_tag}"

        container_port = 8000

        name  = "APP_ENV"
        value = "staging"
      }

        name = "AGENT_API_KEY"

            secret  = google_secret_manager_secret.agent_api_key.secret_id

          }
        }
      }

        http_get { path = "/ready" }
      }
      liveness_probe {
        http_get { path = "/health" }
      }
    }
  }
}

הקובץ מצהיר מה צריך להתקיים (declarative), לא אילו פקודות להריץ. ארבע פקודות מנהלות אותו: terraform init מוריד את ה-provider (הקוד שמדבר עם הספק); terraform plan משווה את הקובץ למה שקיים ומדפיס תוכנית, בלי לשנות דבר; terraform apply מבצע אותה, אחרי אישור; terraform destroy מוחק. בתוכנית, + הוא יצירה, ~ שינוי במקום, -/+ החלפה (מחיקה ויצירה מחדש: לקרוא פעמיים כשזה בסיס נתונים), ו-- מחיקה. Terraform זוכר מה הקים בקובץ state, שיכולים להיות בו ערכים רגישים, ולכן בצוות שומרים אותו באחסון מרוחק מוצפן עם נעילה, ולא ב-git. ומה עם deploy? גרסה חדשה היא image_tag חדש: התוכנית מראה ~ על השירות, וזה הכול. ה-startup_probe וה-liveness_probe הם 10.5 בשפה של Cloud Run.

10.11סיור מודרך בענן (קריאה)

אם תרצו לעלות באמת, כך נראה המסלול על Google Cloud, בקווים כלליים. הוא שמרני בכוונה; בדקו כל צעד בתיעוד העדכני של הספק, כי ממשקים ומחירים משתנים.

  1. פרויקט לכל סביבה, ותקציב קודם. my-agent-staging ו-my-agent-prod כפרויקטים נפרדים: הרשאות וחשבונות נפרדים, וטעות ב-staging לא נוגעת ב-prod. לפני כל משאב, התראת תקציב (budget alert). Cloud SQL, למשל, עולה כסף כל שעה שהוא קיים, גם כשאין שימוש.
  2. Registry. מאגר ב-Artifact Registry, ו-release.yml מפרק 9 דוחף אליו (במקום, או בנוסף, ל-ghcr.io). ההתחברות מ-GitHub Actions נעשית בלי מפתח קבוע, דרך workload identity federation.
  3. בסיס נתונים וסודות. Cloud SQL עם Postgres 17, משתמש agent, והסיסמה, AGENT_API_KEY ו-ANTHROPIC_API_KEY ב-Secret Manager. ל-service account של השירות יש הרשאת קריאה (Secret Accessor) רק לסודות שלו (פרק 14).
  4. Migrations כצעד. Cloud Run job עם אותו image ו-alembic upgrade head, שמריצים לפני השירות: migrate שלנו.
  5. השירות. Cloud Run עם ה-tag, ההגדרות כמשתני סביבה, הסודות כמשתנים או כקבצים (ואז _FILE שלנו עובד כמו שהוא), container_port 8000 (ברירת המחדל שם 8080), ושתי הבדיקות. Cloud Run נותן כתובת HTTPS עם תעודה, ומוסיף עותקים לפי העומס.
  6. Deploy ו-rollback. כל deploy יוצר revision חדש. Rollback הוא העברת התנועה ל-revision הקודם; canary הוא חלוקת תנועה, למשל 90/10. וה-migrations: אותו כלל כמו ב-10.7.
  7. דומיין, וסיום. שם משלכם דרך DNS, אם רוצים. כשמסיימים להתנסות: מחיקת הפרויקט מוחקת את כל מה שבו, ועוצרת את החיוב.

10.15מילון מונחים

deployment
הרצה של גרסה בשביל אחרים, בתהליך שאפשר לחזור עליו ולבטל אותו.
environment
מקום שבו גרסה רצה, עם הנתונים, ההגדרות והסודות שלו: local, staging, prod.
staging
סביבה דומה ל-prod, שבה מנסים גרסה לפני המשתמשים.
prod (production)
הסביבה שהמשתמשים משתמשים בה, עם הנתונים האמיתיים.
configuration
ערך שמשנה התנהגות ואינו סודי: פורט, רמת לוג, שם מודל.
secret
ערך שמי שמחזיק אותו יכול לפעול בשמכם: מפתח, סיסמה.
secrets manager
שירות ששומר סודות מוצפנים, עם הרשאות ויומן גישה, ומעביר אותם לשירות בזמן ריצה.
liveness
בדיקה שהתהליך חי ועונה. כשהיא נכשלת, מפעילים מחדש.
readiness
בדיקה שהעותק יכול לשרת עכשיו. כשהיא נכשלת, לא שולחים אליו בקשות.
healthcheck
פקודה ש-Docker מריץ בתוך container ומסמנת אותו healthy או unhealthy.
restart policy
מה Docker עושה כשהתהליך של container יוצא.
smoke test
בדיקה קצרה, מיד אחרי deploy, שהדבר הבסיסי עובד.
rollback
חזרה לגרסה הקודמת, על ידי פריסה של ה-image שלה.
roll forward
תיקון בעזרת גרסה חדשה, במקום חזרה לישנה.
rolling / blue-green / canary
פריסה שמחליפה עותקים בהדרגה / מעבירה תנועה בין שתי סביבות שלמות / שולחת לחדש אחוז קטן קודם.
GitOps
שמירת המצב הרצוי של הסביבות (למשל איזו גרסה רצה) ב-git.
managed service
שירות שהספק מתפעל בשבילכם: התקנה, גיבוי, עדכונים.
infrastructure as code
תיאור התשתית בקבצים שב-git, שכלי מקים לפיהם.
Terraform state
הקובץ שבו Terraform זוכר מה הוא הקים. רגיש, ונשמר מרוחק עם נעילה.

10.16מה הלאה

הסוכן רץ עכשיו בשתי סביבות, עם סודות במקום, בדיקות בריאות, ודרך חזרה. אבל שימו לב מה קורה לשירות עצמו: הוא עונה לצ'אט, שומר שיחות, מנהל כותרות, ועוד מעט ירצה גם ידע חיצוני, הערות וכלים. כל תכונה נכנסת לאותו image, ונפרסת יחד עם כל השאר. באג בתכונה אחת מחזיר אחורה את כולן, ותכונה כבדה אחת מכריחה להגדיל את כל השירות.

מתי נכון לפצל שירות שני מהשירות היחיד, ומה זה עולה (רשת שיכולה להיכשל, timeouts, ניסיונות חוזרים, ו-deploy כפול): זה פרק 11: ארכיטקטורה.
