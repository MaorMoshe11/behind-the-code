פרק 18 מתוך 21

Tools ו-integrations

איך עוברים מכלי אחד שחובר ביד לרשימה של כלים שמנוהלת במקום אחד, איך מעצבים כלי שמודל מצליח להשתמש בו, איך מקבלים מהמודל נתונים ולא טקסט, ואיך חושפים את הכלים לכל אפליקציה דרך MCP.

בסוף הפרק תדעו

  • לבנות tool registry: כלים כנתונים, קלט שנבדק מול schema לפני שמשהו רץ, ולולאה שלא יודעת דבר על אף כלי.
  • לעצב כלי שהלקוח שלו הוא מודל: שם ותיאור, קלט שקשה לטעות בו, פלט קצר, שגיאה שאומרת איך להתאושש, idempotency וגבולות גודל.
  • להפעיל כמה כלים בצעד אחד ולהחזיר את כל התוצאות כמו שה-API דורש.
  • לבקש structured output, לבדוק אותו עם Pydantic, ולדעת מה עושים כשהבדיקה נכשלת.
  • להסביר מה זה MCP, ולהריץ שרת MCP משלכם ולקוח שמתחבר אליו.

זמן משוער: חמש עד שש שעות. מה צריך: הפרויקט מסוף פרק 17 (גרסה 0.16.0), ושירות ההערות רץ בחלון נפרד, כמו בפרק 16. הכול במצב mock, בלי מפתח ובלי עלות.

18.1הבעיה: סוכן שיודע רק לקרוא

בגרסה 0.16.0 לסוכן יש כלי אחד, list_notes, שחובר ביד ל-answer(). בקשו ממנו לשמור משהו, ואחר כך שאלו עליו:

agent> [mock reply, turn 1] You said: Remember that I parked on level 3, row F.

you> Where did I park? Check my notes.

מודל אמיתי היה עונה משהו כמו "I can't save notes, but you can use /note" (תשובה לדוגמה, לא ריצה מוקלטת). ההערה לא נשמרה, כי אין כלי ששומר. כדי להוסיף אחד צריך לגעת ב-answer(), ב-trace.py ובבדיקות, ואת הבדיקות של הקלט לכתוב שוב ביד, שדה אחרי שדה. בכלי השני זה מעצבן; בעשירי זה כבר באג שמחכה לקרות.

ויש בעיה עמוקה יותר. נניח שמישהו כותב את הכלי הבא בחיפזון, כמו שכתוב ב-API של שירות ההערות: get_notes, תיאור "Gets notes.", וקלט של conversation_id, q ו-limit. מאיפה המודל ידע את מזהה השיחה? הוא ימציא אחד, או יעתיק מזהה שראה בטקסט. ואת התוצאה, JSON גולמי עם שדות שהוא לא צריך, הוא יקבל שוב בכל צעד. הכלי "עובד", ובכל זאת הסוכן מתנהג רע. הפרק הזה עוסק בשני הצדדים: איך מוסיפים כלים בלי לגעת בלולאה, ואיך כותבים כלי שמודל מצליח להשתמש בו.

18.3כלים כנתונים: tool registry

בפרק 16 כלי היה Tool עם פונקציה שבודקת את הקלט בעצמה. עכשיו כלי הוא נתונים, ואת העבודה הכללית עושה קוד אחד. לכל כלי חמישה דברים: שם, תיאור שנכתב בשביל המודל, מודל קלט (מחלקת Pydantic שה-JSON schema שלה נשלח למודל, והיא גם זו שבודקת מה המודל שלח), הפונקציה, וסימון אם הכלי כותב:

agent\tools.py (the definition)
class ToolInput(BaseModel):
    """The base of every tool's input. A field the tool does not know is an error, not ignored."""

    model_config = ConfigDict(extra="forbid")


@dataclass(frozen=True)
class ToolContext:
    """What a tool works on, chosen by our code for one conversation. The model never sees it."""

    notes: NotesClient
    conversation_id: str


@dataclass(frozen=True)
class Tool:
    name: str
    description: str  # written for the model: what it does, when to call it, what comes back
    input_model: type[ToolInput]  # the input's JSON schema, and its validation
    run: Callable[[ToolContext, Any], str]  # our code: (context, validated input) -> text
    writes: bool = False  # it changes something; offered only when CHAT_WRITE_TOOLS=1

ToolRegistry מחזיק את כל הכלים, בשמות ייחודיים. לכל ריצה הוא נותן Toolbox: הכלים שמותר להציע (בלי הכותבים, אם הם כבויים) קשורים ל-ToolContext של השיחה הזו. ה-Toolbox הוא מה שהלולאה מקבלת, והשינוי בה הוא שתי שורות: params = toolbox.params() במקום לבנות את הרשימה, ו-toolbox.result(call) במקום run_tool. בלולאה אין יותר אף שם של כלי. כלי חדש הוא רישום אחד, והלולאה, agent.trace ושרת ה-MCP מקבלים אותו מיד.

הבדיקה של הקלט עוברת למקום אחד, ל-Toolbox.call: model_validate על מה שהמודל שלח, ושגיאת Pydantic הופכת לשורה אחת שהמודל יכול לפעול לפיה. הכללים של פרק 16 לא השתנו: כלי לא מוכר, קלט שגוי, שירות שנפל ובאג, כולם הופכים ל-tool_result עם is_error, ושום חריגה לא עוברת את הלולאה.

18.5כלים שכותבים: חזרה, הרשאה, בעלות

list_notes לא יכול להזיק: קריאה מיותרת עולה כמה טוקנים. add_note ו-delete_note משנים נתונים, ושלוש שאלות עולות מיד.

מה קורה כשצעד חוזר? המשתמש שלח "Remember that..." דרך ה-API, ה-timeout של הלקוח פג, והוא שלח שוב. המודל קורא ל-add_note שוב, עם אותו טקסט. ה-Idempotency-Key של פרק 11 נוצר מחדש בכל add(), ולכן הוא מגן רק מפני ה-retries של ה-HTTP. לכלי, הקוד מייצר מפתח מהשיחה ומהטקסט: tool- ועוד 40 תווי sha256. אותה הערה באותה שיחה מקבלת אותו מפתח, ושירות ההערות מחזיר את ההערה הראשונה (200, "replayed"). המודל לא בוחר את המפתח ולא יודע עליו.

מי מרשה? הכלים הכותבים מסומנים writes=True, ומוצעים למודל רק כש-CHAT_WRITE_TOOLS=1. ברירת המחדל כבויה: least privilege של פרק 14, ביישום הכי פשוט שיש. כל קריאה לכלי נכתבת ללוג עם "writes" ומזהה השיחה, כך שאפשר לדעת אחר כך מי שינה מה. זה לא אישור אנושי. כלי מסוכן צריך שאדם יאשר לפני שהוא רץ, וזה נבנה בפרק 21; עד אז ההחלטה היא אם להדליק את הכותבים בכלל.

של מי ההערה? ב-API של שירות ההערות, DELETE /v1/notes/{id} לא בודק לאיזו שיחה ההערה שייכת. אם המודל ישלח ref של שיחה אחרת (העתיק מטקסט, או ניחש), delete_note מחפש אותו קודם בין ההערות של השיחה הזו, ושולח DELETE רק אם מצא. שוב: השיחה נקבעת בקוד, והכלי לא סומך על מה שהמודל כתב.

18.7פלט מובנה: נתונים, לא טקסט

לפעמים לא רוצים תשובה, רוצים נתונים: כותרת לשיחה ונושא מתוך רשימה, תגיות להערה, שדות מתוך טקסט. אפשר לבקש "answer in JSON" בפרומפט, ולקוות. ל-API יש לזה פיצ'ר: structured outputs. שולחים output_config עם {"format": {"type": "json_schema", "schema": ...}}, וה-API מבטיח שהטקסט שחוזר הוא JSON שמתאים לצורה של ה-schema.

"לצורה" היא מילת המפתח. ה-API לא תומך בכל JSON schema: אין minLength, maxLength, מינימום ומקסימום למספרים. הפונקציה anthropic.transform_schema של ה-SDK מורידה אותם מה-schema ומעבירה אותם לתיאור, ואת מה שהורד בודקים בעצמכם, עם Pydantic. זה /title, הפקודה החדשה בצ'אט:

agent\titles.py (shortened)
class TitleSuggestion(BaseModel):
    model_config = ConfigDict(extra="forbid")

    title: str = Field(min_length=1, max_length=TITLE_LENGTH, description="A short title, ...")
    topic: Literal["code", "work", "study", "personal", "other"]


def title_schema() -> dict[str, object]:
    return anthropic.transform_schema(TitleSuggestion.model_json_schema())


def suggest_title(client: AgentClient, messages: list[MessageParam]) -> TitleSuggestion | None:
    question = PROMPT + transcript(messages)
    for attempt in range(1, ATTEMPTS + 1):  # the first answer, and one retry
        answer = client.reply_json([{"role": "user", "content": question}], title_schema())
        try:
            return TitleSuggestion.model_validate_json(answer)
        except ValidationError as error:
            reasons = ...  # "title: String should have at most 50 characters"
            log.warning("title suggestion rejected: %s", reasons, extra={"attempt": attempt})
            question = f"{RETRY_MARK}: {reasons}. Answer again.\n\n{PROMPT}{transcript(messages)}"
    return None  # the caller keeps the automatic title

שלוש החלטות. ניסיון חוזר אחד, עם הסיבות: בקשה חדשה, לא שיחה שעורכים בה תשובה קודמת. אחריו, ברירת מחדל: הכותרת האוטומטית מפרק 15 נשארת, והמשתמש לא רואה שגיאה. ללוג הולכות הסיבות בלבד, לא הטקסט של השיחה (פרק 14). ב-ClaudeClient, reply_json הוא אותה קריאה של _create עם output_config, וזורק LLMError כש-stop_reason הוא refusal או max_tokens, כי אז ה-JSON עלול להיות חלקי. ל-SDK יש גם client.messages.parse(output_format=...) שעושה את הבקשה ואת הבדיקה יחד; כאן הן נפרדות, כדי שאותה בדיקה תרוץ גם על ה-mock.

טכניקה ותיקה לאותה מטרה היא tool as schema: מגדירים "כלי" שהקלט שלו הוא הנתונים שרוצים, ומכריחים את המודל לקרוא לו (tool_choice מסוג tool). עם claude-opus-5-5 זה לא אפשרי: כפייה של כלי נדחית ב-400. נשארים output_config.format לנתונים, ו-"strict": true על הגדרת כלי כשרוצים שגם הקלט של כלי אמיתי יתאים בדיוק ל-schema. הפרויקט לא משתמש ב-strict, כי Pydantic בודק כל קלט ממילא.

18.8Integrations ו-MCP

הכלים שלכם נגישים עכשיו לסוכן אחד: הצ'אט. אבל משתמשים עובדים בכמה אפליקציות של מודלים: עורך קוד עם סוכן, אפליקציית צ'אט שולחנית, הסוכן שלכם. אם כל אפליקציה כותבת חיבור משלה לכל שירות, יש מכפלה של חיבורים: N אפליקציות כפול M שירותים, כל אחד עם קוד, באגים ותחזוקה.

Model Context Protocol (MCP) הוא פרוטוקול פתוח שהופך את המכפלה לחיבור: שירות כותב MCP server אחד, כל אפליקציה כותבת MCP client אחד, וכל אחד מדבר עם כל אחד. האפליקציה שמריצה את המודל נקראת host, והיא מחזיקה לקוח לכל שרת שהוגדר לה. שרת חושף שלושה סוגים של דברים:

  • tools: פעולות שהמודל מבקש, בדיוק כמו בפרק 16: שם, תיאור, input schema.
  • resources: נתונים לקריאה, לפי URI, שה-host מחליט אם ומתי לצרף להקשר.
  • prompts: תבניות של הודעות שהמשתמש בוחר, למשל "סכם את ההערות שלי".

ההודעות עצמן הן JSON-RPC, ועוברות ב-transport: stdio, שבו ה-host מפעיל את השרת כתהליך ומדבר איתו דרך ה-stdin וה-stdout שלו (שרת מקומי, בלי פורט), או Streamable HTTP, לשרת שרץ ברשת. הפרויקט משתמש ב-stdio, עם ה-SDK הרשמי, החבילה mcp (גרסה 2). השרת לא מגדיר כלים חדשים: הוא מתרגם את הרישום.

agent\mcp_server.py (the heart of it, shortened)
def build_server(toolbox: Toolbox) -> Server:
    """An MCP server whose tools are the toolbox's: listed, and run, through the registry."""

    async def list_tools(ctx, params) -> types.ListToolsResult:  # types shortened here
        return types.ListToolsResult(tools=[
            types.Tool(
                name=tool.name, description=tool.description, input_schema=tool.schema(),
                annotations=types.ToolAnnotations(read_only_hint=not tool.writes, ...),
            )
            for tool in toolbox.tools.values()
        ])

    async def call_tool(ctx, params) -> types.CallToolResult:
        # Toolbox.call is ordinary blocking code (HTTP): run it in a thread.
        outcome = await anyio.to_thread.run_sync(toolbox.call, params.name, params.arguments or {})
        return types.CallToolResult(
            content=[types.TextContent(text=outcome.content)], is_error=outcome.is_error
        )

    return Server("my-agent-notes", version=project_version(),
                  on_list_tools=list_tools, on_call_tool=call_tool)

ב-main() השרת טוען את .env, בוחר שיחה (--conversation, ברירת מחדל: האחרונה), בונה Toolbox עם CHAT_WRITE_TOOLS, ומריץ server.run בתוך stdio_server(). דבר אחד חשוב: ב-stdio, ה-stdout שייך לפרוטוקול. print אחד במקום הלא נכון שובר את החיבור, ולכן הלוג הולך ל-mcp.log והודעות שגיאה ל-stderr. ל-SDK יש גם MCPServer, שבונה schema מחתימה של פונקציה; כאן ה-schema כבר קיים ברישום, ולכן משתמשים בשרת ה-low-level, שמקבל אותו כמו שהוא.

איך host משתמש בשרת. כל אפליקציה מגדירה את זה במקום אחר, וזה משתנה מגרסה לגרסה, אבל השדות כמעט תמיד אותם: איזה תהליך להפעיל, עם אילו ארגומנטים, באיזו תיקייה, ואילו משתני סביבה. לשרת הזה: C:\Users\you\projects\my-agent\.venv\Scripts\python.exe, הארגומנטים -m agent.mcp_server, ותיקיית הפרויקט כתיקיית עבודה. ה-host מפעיל אותו, שואל אילו כלים יש, ומציע אותם למודל שלו לצד הכלים האחרים. רמזים כמו read_only_hint עוזרים לו להחליט על מה לבקש אישור מהמשתמש. ולצד השני: ה-SDK של anthropic יודע להמיר כלים של שרת MCP לכלים של ה-API, ויש גם MCP connector שבו ה-API עצמו מתחבר לשרת מרוחק. בשניהם, הסוכן שלכם הוא ה-host.

    def call(self, name: str, tool_input: object) -> Outcome:
        """Validate the input, run the tool, and turn every failure into a result for the model."""
        tool = self.tools.get(name)
        try:
            if tool is None:
                known = ", ".join(self.tools) or "none"
                raise ToolError(f"There is no tool named {name!r}. The tools are: {known}.")
            try:  # the model wrote this input: check it before anything runs
                checked = tool.input_model.model_validate(tool_input)
            except ValidationError as error:
                raise ToolError(explain(name, error)) from None
            outcome = Outcome(tool.run(self.context, checked), False)
        except ToolError as error:  # an expected failure: the message is written for the model
            outcome = Outcome(str(error), True)
        except Exception:  # a bug in our tool: the details go to our log, not to the model
            log.exception("tool %s crashed", name)
            outcome = Outcome("The tool failed unexpectedly.", True)
        ...  # the metric and one log line: tool, outcome, writes, conversation_id
        return outcome

def note_key(conversation_id: str, text: str) -> str:
    """The same note in the same conversation, the same key. Made by our code, never by the model."""
    digest = hashlib.sha256(f"{conversation_id}\n{text}".encode()).hexdigest()
    return f"tool-{digest[:40]}"


class AddNoteInput(ToolInput):
    text: str = Field(min_length=1, max_length=2000,
                      description="The note, in the user's words. One note per call.")


def add_note(context: ToolContext, args: AddNoteInput) -> str:
    text = " ".join(args.text.split())
    try:
        note = context.notes.add(
            context.conversation_id, text, idempotency_key=note_key(context.conversation_id, text)
        )
    except NotesUnavailable as error:
        raise ToolError(UNAVAILABLE + " The note was not saved.") from error
    return f"Saved: {line(note)[2:]}"


def delete_note(context: ToolContext, args: DeleteNoteInput) -> str:
    try:
        # Only a note of THIS conversation can be deleted: look for the ref among its notes.
        mine = context.notes.list(context.conversation_id, limit=100)
        found = [note for note in mine if note.id.startswith(args.note)]
        if not found:
            raise ToolError(f"No note [{args.note}] in this conversation. "
                            "Call list_notes to see the notes and their refs.")
        context.notes.delete(found[0].id)
    except NotesUnavailable as error:
        raise ToolError(UNAVAILABLE + " Nothing was deleted.") from error
    return f"Deleted: {line(found[0])[2:]}"

ה-ref מוגדר ב-DeleteNoteInput עם pattern=r"^[0-9a-f]{8}$", כך ש-"the milk one" נדחה לפני כל בקשה. list_notes מבקש מהשירות PAGE + 1 הערות (21), מציג 20, ואם הגיעה העשרים ואחת מוסיף "(Only the first 20 notes are shown. הוסיפו לשרת resource אחד, notes://conversation: ההערות של השיחה כטקסט. ב-SDK, לשרת ה-low-level יש גם on_list_resources ו-on_read_resource; קראו את החתימות שלהם בקוד של החבילה (.venv\Lib\site-packages\mcp\server\lowlevel\server.py) לפני שאתם כותבים. השתמשו באותו קוד של list_notes, ו-URI אחר יחזיר שגיאה. הרחיבו את mcp_try.py כך ש-read <uri> יקרא אותו, והוסיפו בדיקה בתוך התהליך.

18.14מילון מונחים

tool registry
המקום האחד שבו רשומים כל הכלים, כנתונים; הלולאה וכל ממשק אחר לוקחים אותם משם.
input model
מחלקת Pydantic של קלט הכלי: ממנה ה-JSON schema שנשלח, ובה נבדק מה שחזר.
toolbox
הכלים שמוצעים בריצה אחת, קשורים לשיחה אחת.
ref
מזהה קצר של הערה (8 תווים), שהמודל מקבל מכלי ומחזיר לכלי אחר.
parallel tool use
כמה בקשות לכלים בתשובה אחת; כל התוצאות חוזרות בהודעה אחת.
least privilege
לתת לכל רכיב, וגם למודל, רק את מה שהוא חייב.
structured outputs
פיצ'ר של ה-API: התשובה היא JSON שמתאים לצורה של schema.
tool as schema
טכניקה ותיקה: כלי שהקלט שלו הוא הנתונים המבוקשים, והמודל נדרש לקרוא לו.
MCP
Model Context Protocol: פרוטוקול פתוח שבו שרתים חושפים כלים, resources ו-prompts לכל host.
host
האפליקציה שמריצה את המודל ומחזיקה לקוח MCP לכל שרת.
resource
נתונים שהשרת חושף לקריאה לפי URI; ה-host מחליט מתי לצרף אותם.
stdio transport
ה-host מפעיל את השרת כתהליך ומדבר איתו דרך stdin ו-stdout.
server tools
כלים שרצים אצל ספק המודל (חיפוש ברשת, הרצת קוד), לא בקוד שלכם.

18.15מה הלאה

לסוכן יש עכשיו ארבעה כלים, ובכל קריאה הוא שולח את ההגדרות של כולם, את ההיסטוריה, ואת התוצאות של הצעדים הקודמים. בתרגיל 1 מדדתם כמה עולים כלים שאף אחד לא קרא להם; בפרק 16 ראיתם שכל צעד שולח את כל מה שהיה. ככל שהשיחה מתארכת, החלון של המודל מתמלא, כל הודעה עולה יותר, ומה שנחתך בסוף, נשכח. ובין שיחות הסוכן לא זוכר דבר: מה שקרא בכלי לא נשמר בכלל. איך מחליטים מה נכנס להקשר, איך משלמים פחות על מה שחוזר בכל קריאה, ואיך סוכן זוכר לאורך זמן: פרק 19: Context ו-memory.
