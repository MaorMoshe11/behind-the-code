איך מסתכלים על המערכת שבניתם בעיניים של מי שרוצה לנצל אותה, ומה עושים עם מה שמוצאים: סודות, הרשאות, קלט עוין, תלויות, הגבלת קצב ומידע אישי.

בסוף הפרק תדעו

  • לבנות מודל איום פשוט: מה מגינים עליו, מאיפה נכנסים, ואיפה עובר גבול האמון.
  • לסרוק היסטוריה של git לסודות, ולדעת מה עושים כשסוד נכנס בכל זאת: קודם מחליפים, אחר כך מנקים.
  • להבדיל בין אימות להרשאה, ולתת לכל חלק במערכת רק את מה שהוא צריך: מפתח לכל לקוח, משתמש בלי הרשאות ב-container, אסימון נפרד ל-/metrics.
  • להתייחס לכל קלט כעוין: גבולות עם Pydantic, למה SQL injection ו-XSS קורים ואיך הקוד שלכם כבר מונע אותם.
  • לבדוק תלויות לחולשות ידועות, להגביל קצב עם 429, ולטפל במידע אישי: מה שומרים, מה לא כותבים ללוג, ואיך מוחקים.

זמן משוער: חמש עד שש שעות. מה צריך: הפרויקט מסוף פרק 13, Docker Desktop, וחיבור לאינטרנט (להורדת gitleaks ולבדיקת התלויות). הכול במצב mock.

מצאתם גם משהו טוב: docker compose logs api notes worker | Select-String על הטקסט ששלחתם ועל המפתחות מחזיר אפס שורות. ההחלטה מפרק 13 לא לכתוב תוכן ללוג מחזיקה. אבטחה היא בדיוק זה: הרגל של שתי שאלות שחוזרות על כל חלק במערכת. מי יכול לעשות מה? ומה אם הקלט הזה עוין?

14.3סודות

מפתח שדלף אינו "כמעט בסדר". מפתח ה-API של Anthropic שווה כסף, כי מי שמחזיק בו מוציא מהחשבון שלכם. סיסמת בסיס נתונים שווה את כל השיחות. ומאגרים ציבוריים נסרקים כל הזמן על ידי תוכנות שמחפשות מפתחות, כך שהזמן מדחיפה ועד שימוש לרעה נמדד לפעמים בדקות. בפרק 2 עצרתם את .env עם .gitignore. אבל סוד יכול להגיע ל-git גם בדרכים אחרות: מודבק ל-.env.example, לבדיקה, להערה בקוד.

סורקים את ההיסטוריה

gitleaks הוא כלי שעובר על כל ה-commits ומחפש מחרוזות שנראות כמו סודות, לפי מאות כללים (מפתחות של Anthropic, AWS, GitHub, ומחרוזות אקראיות ארוכות ליד מילים כמו key). זה קובץ exe אחד, בלי התקנה ובלי הרשאות מנהל. מורידים מדף ה-releases שלו, ובודקים שהקובץ הוא מה שהיוצרים פרסמו:

Invoke-WebRequest "$base/gitleaks_${v}_windows_x64.zip" -OutFile gitleaks.zip -UseBasicParsing
Invoke-WebRequest "$base/gitleaks_${v}_checksums.txt" -OutFile checksums.txt -UseBasicParsing
(Get-FileHash gitleaks.zip -Algorithm SHA256).Hash.ToLower()

git סורק את ההיסטוריה, לא רק את הקבצים של היום. --redact מסתיר את הסוד עצמו בפלט, כי גם פלט של כלי יכול להגיע ללוג של CI. יש גם gitleaks dir, שסורק תיקייה, אבל בפרויקט שלנו הוא נכנס גם ל-.venv ומוצא שם ארבע "דליפות" בקוד של SQLAlchemy: false positives. כל סורק טועה לפעמים לשני הכיוונים, ולכן הוא רשת ביטחון, לא תחליף לזהירות.

ואם סוד כבר נכנס?

תרגיל 1 מראה את זה בעיניים: commit שמכניס מפתח (מזויף), commit שמוחק אותו, ו-gitleaks עדיין מוצא אותו, כי ההיסטוריה זוכרת. הסדר:

  1. קודם מחליפים (rotate): יוצרים מפתח חדש, מבטלים את הישן אצל הספק. מהרגע שהמפתח נדחף הוא אצל אחרים: בעותקים, ב-forks, ב-caches. מחיקה מההיסטוריה לא מחזירה אותו.
  2. בודקים אם השתמשו בו: לוח הבקרה של הספק מראה שימוש ועלויות.
  3. מנקים את ההיסטוריה רק אחר כך, אם בכלל: כלים כמו git filter-repo כותבים אותה מחדש, וכל מי שעובד על המאגר צריך לשכפל מחדש. על ענף שלא נדחף, מספיק למחוק את הענף.

ובשביל שזה לא יקרה: pre-commit hook, סקריפט ש-git מריץ לפני כל commit ועוצר אותו אם הוא נכשל. הכלי הנפוץ לניהול שלהם נקרא pre-commit, ול-gitleaks יש מצב בשבילו (gitleaks git --pre-commit --staged). ובשרת, הסריקה רצה ב-CI על כל pull request (סעיף 14.11). GitHub עצמו מציע secret scanning שחוסם דחיפה של מפתחות מוכרים.

14.4אימות, הרשאה, ומינימום הרשאות

שתי שאלות שונות. אימות (authentication): מי אתה? הרשאה (authorization): מה מותר לך? X-API-Key של פרק 5 עונה על הראשונה בקירוב גס ("מישהו שיש לו את המפתח"), ועל השנייה בכלל לא: מי שעבר את הבדיקה רשאי לכל דבר. כש-50 השיחות של כולם חוזרות ללקוח אחד, זו בעיה של הרשאה.

למה hash אחד של SHA-256 מספיק כאן, כשלסיסמאות אומרים "רק bcrypt או argon2"? כי סיסמה שאדם בחר קצרה מספיק כדי לנחש אותה מיליארדי פעמים בשנייה מול ה-hash, ופונקציה איטית מאטה את זה. מפתח של 256 ביטים אקראיים אי אפשר לנחש בכל מהירות שהיא.

מינימום הרשאות

Least privilege: כל חלק מקבל בדיוק את מה שהוא צריך, ולא יותר, כדי שכשמשהו נפרץ (וזה יקרה), הנזק יהיה קטן. ארבעה מקומות אצלנו:

  • ה-container. שירות לא צריך להיות root. כמשתמש בלי הרשאות, מי שמריץ בו קוד לא יכול לשנות את הקוד, להתקין כלים או לגעת בקבצים של המערכת.
  • בסיס הנתונים. ה-api מתחבר כ-agent, הבעלים של הטבלאות, ובסביבה המקומית אפילו superuser. אבל הוא צריך רק לקרוא ולכתוב שורות. רק migrate צריך לשנות טבלאות. תרגיל 4 בונה משתמש כזה.
  • CI. ל-ci.yml כבר יש permissions: contents: read (פרק 9). כאן נוסיף נעיצה של כל action ל-commit, בסעיף 14.8.
  • ענן. שם זה נקרא IAM: לכל שירות יש זהות (service account) עם רשימת הרשאות. השירות שקורא סודות מקבל "קריאה של הסוד הזה", לא "מנהל הסודות של החשבון" (פרק 10). ומי שיכול להריץ docker על השרת הוא בפועל מנהל שלו.

agent\api.py
def key_checker(clients: dict[str, str]) -> Callable[[str | None], str]:
    """Build the dependency that says who is calling: no key, or an unknown key, gets 401."""

    def check(key: Annotated[str | None, Depends(api_key_header)]) -> str:
        # We look up the key's hash, never the key itself. A wrong key changes its whole
        # hash, so how long the lookup takes reveals nothing about the right keys.
        client = clients.get(hash_key(key)) if key else None
        if client is None:
            raise HTTPException(status_code=401, detail="Missing or wrong X-API-Key header.")
        return client

    return check

ה-compare_digest של פרק 5 נעלם, והתגובה בקוד מסבירה למה זה בטוח: מי שמנחש לא שולט ב-hash של מה שהוא שולח, ולכן זמן החיפוש לא מלמד אותו כלום.

2הגבלת קצב

כל הודעה ל-/chat עולה כסף, ולקוח אחד (או מפתח אחד שדלף) יכול לשלוח אלפים. הגבלת קצב (rate limiting) אומרת: עד N בקשות לפרק זמן, ומעבר לזה 429 (Too Many Requests) עם כותרת Retry-After שאומרת בעוד כמה שניות לנסות שוב. הלקוח של פרק 11 כבר מנסה שוב אחרי 429, עם המתנה (אם כי הוא עוד לא קורא את Retry-After).

agent\security.py (shortened)
class RateLimiter:
    """At most `limit` requests per client in every window of `window` seconds."""

    def check(self, client: str) -> int | None:
        """Count one request. None: allowed. A number: refused, retry after that many seconds."""
        now = self.clock()
        start, count = self.counts.get(client, (now, 0))
        if now - start >= self.window:
            start, count = now, 0  # a new window begins
        if count >= self.limit:
            return max(1, math.ceil(start + self.window - now))
        self.counts[client] = (start, count + 1)
        return None

ב-/chat, אחרי האימות: wait = limiter.check(caller), ואם יש wait, HTTPException(429, ..., headers={"Retry-After": str(wait)}). ברירת המחדל: 30 בדקה (CHAT_RATE_LIMIT). הבדיקות מזיזות שעון מזויף במקום לחכות דקה. ומה-14.1, אותה לולאה, עם 40 בקשות:

הגבולות שלו. הספירה בזיכרון של תהליך אחד: שני עותקים של ה-api מרשים פי שניים, והפעלה מחדש מאפסת. לכן מגבילים בשני מקומות. בקצה (edge: ה-proxy, ה-load balancer או שירות ה-CDN שלפני השירותים), לפי כתובת IP: זול, עוצר הצפה לפני שהיא מגיעה אליכם, אבל לא יודע מי הלקוח. באפליקציה, לפי לקוח: יודע מי, ויודע כמה כל פעולה עולה. כשיש כמה עותקים, הספירה עוברת למקום משותף, בדרך כלל Redis. 14.9תעבורה: HTTPS ו-CORS

HTTPS הוא HTTP בתוך TLS: הצפנה (מי שבדרך לא קורא), שלמות (לא משנה), וזהות (תעודה שמוכיחה שזה באמת השרת). בלעדיו, כל מי שברשת (Wi-Fi בבית קפה, ספק, נתב) קורא את X-API-Key ואת ההודעות. אצלנו הכול על 127.0.0.1, ולכן HTTP מספיק. בייצור, ה-TLS בדרך כלל מסתיים בקצה: ה-load balancer או הפלטפורמה (Cloud Run, למשל, פרק 10) מחזיקים את התעודה, ומשם התעבורה ממשיכה פנימה. ופנימה זה חשוב: "הרשת הפנימית בטוחה" היא הנחה שנשברת בפריצה הראשונה. ארגונים רבים מצפינים גם בין שירותים (mTLS, שבו גם הלקוח מציג תעודה, וזו גם דרך טובה יותר לזהות את הצ'אט מול שירות ההערות מאשר מפתח משותף). בסיסי נתונים, Kafka ו-Redis תומכים כולם ב-TLS.

CORS (Cross-Origin Resource Sharing): דפדפן לא נותן לדף מאתר אחד לקרוא תשובות מאתר אחר, אלא אם האתר השני מרשה זאת בכותרות. בלי זה, כל אתר שתבקרו בו היה יכול לשלוח בקשות לשירותים שלכם בשמכם ולקרוא את התשובות. הדף שלנו מוגש מאותו מקור כמו ה-API, ולכן לא צריך CORS בכלל, ולא הדלקנו אותו. אם יום אחד דף מדומיין אחר יצטרך גישה, מרשים בדיוק את המקור הזה (CORSMiddleware עם allow_origins מפורש), ולעולם לא "*" יחד עם הרשאות.

14.10מידע אישי

מידע אישי הוא כל מידע על אדם מזוהה או שאפשר לזהות: שם, מייל, טלפון, כתובת IP, ומה שאנשים כותבים לצ'אט ("תוצאות בדיקת הדם שלי חזרו"). אצלנו: ההודעות, ההערות, ובמידה פחותה גם מזהי שיחות ושעות, שמקשרים פעולות לאדם. חמישה עקרונות:

  • מזעור (data minimization): לא אוספים מה שלא צריך. האירועים ב-Kafka נושאים user_chars, לא את הטקסט; המדדים סופרים, לא מצטטים.
  • לא בלוג. בדקתם ב-14.1: אפס שורות עם תוכן או מפתח, והבדיקה מתרגיל 5 של פרק 13 שומרת על זה. מפתח בלוג הוא דליפה של סוד, ותוכן בלוג הוא עותק נוסף של מידע אישי, במקום שנשמר זמן רב ושיותר אנשים קוראים.
  • שמירה ומחיקה (retention): מחליטים כמה זמן שומרים, ומוחקים אחרי זה. ה-saga של פרק 12 היא המנגנון של "הזכות להימחק": היא מוחקת הודעות, הערות, ושורת השימוש של ה-worker. מה שהיא לא מגיעה אליו: אירועים ב-Kafka (7 ימים), לוגים, וגיבויים. אלה צריכים תקופה מוגדרת.
  • הצפנה: בתעבורה (TLS, 14.9) ובמנוחה (encryption at rest: דיסקים ובסיסי נתונים מוצפנים, כברירת מחדל אצל רוב ספקי הענן).
  • שקיפות: לומר למשתמשים מה נשמר, כמה זמן, ולמי זה נשלח. כאן, למשל, הטקסט נשלח לספק המודל.

חוקים בעולם מחייבים חלק מזה: ה-GDPR באירופה, וחוק הגנת הפרטיות בישראל, למשל. מה בדיוק הם דורשים משירות מסוים, ומתי, זו שאלה לעורך דין. מה שכתוב כאן אינו ייעוץ משפטי. אבל מערכת שבנויה לפי חמשת העקרונות האלה מוכנה לרוב מה שחוק כזה ישאל.

14.11CI, deploy, וגרסה 0.14.0

ב-ci.yml, job רביעי, security: checkout עם fetch-depth: 0 (כל ההיסטוריה, כי סוד ב-commit ישן עדיין דלף), gitleaks/gitleaks-action (חינם למאגרים של משתמש פרטי; ארגון צריך רישיון חינמי מהם), ו-uv audit --locked בשני הפרויקטים. ה-actions נעוצים ל-commits, ו-actionlint נקי. ci_local.py מדלג על ה-action של gitleaks (הוא של GitHub בלבד) ומריץ את שתי הבדיקות; את gitleaks מריצים מקומית ביד.

ב-deploy\: ה-api מקבל רק hashes (AGENT_API_KEYS_FILE, מהקובץ api_clients.txt), ו-deploy.py משתמש ב-deploy_key.txt, שלא יוצא מהמחשב שלכם. make_secrets.py יוצר את שניהם. ה-worker מקבל APP_ENV: בפרק 13 כתבתם ש-fault injection צריך להיחסם בסביבות אמיתיות, ושירות ההערות אכן מסרב לו ב-prod, אבל WORKER_CRASH_BEFORE_COMMIT לא נבדק בכלל. עכשיו גם הוא מסרב. גרסה 0.14.0, שירות ההערות 0.3.1 (רק ה-Dockerfile השתנה), ו-CHANGELOG.md משחרר גם את התיקון מתרגיל 4 של פרק 13 שחיכה תחת Unreleased. Merge, תגית v0.14.0.

14.15מילון מונחים

threat model
מפה של מה מגינים עליו, מאיפה נכנסים, ואיפה עוברים גבולות אמון.
trust boundary
מקום שבו נתונים עוברים ממי שלא סומכים עליו למי שכן; שם בודקים.
secret scanning
חיפוש אוטומטי של מפתחות וסיסמאות בקוד ובהיסטוריה (gitleaks).
rotation
החלפת סוד בחדש וביטול הישן, בלי להפיל את מי שמשתמש בו.
pre-commit hook
סקריפט ש-git מריץ לפני כל commit, ועוצר אותו אם הוא נכשל.
authentication
אימות: מי אתה.
authorization
הרשאה: מה מותר לך.
least privilege
לתת לכל רכיב רק את ההרשאות שהוא צריך.
hash
פונקציה חד-כיוונית: מהמפתח קל לחשב, מהתוצאה אי אפשר לחזור למפתח.
OAuth 2.0 / JWT
תקן להנפקת אסימונים על ידי שירות זהות; אסימון JSON חתום, עם תוקף.
SQL injection
קלט שמשנה את טקסט השאילתה; נמנע עם פרמטרים.
XSS
קלט שהופך לקוד שרץ בדפדפן; נמנע כשמציגים טקסט כטקסט.
prompt injection
טקסט שמנסה לגרום למודל לעשות משהו שלא התכוונתם (פרק 21).
CVE
מזהה ציבורי של חולשה ידועה בתוכנה.
supply chain
כל מה שהקוד סומך עליו בדרך: חבילות, images, actions.
rate limiting
הגבלת מספר הבקשות לזמן; מעבר לזה 429 עם Retry-After.
TLS / HTTPS
הצפנה, שלמות וזהות לחיבור; HTTPS הוא HTTP בתוכו.
CORS
הכללים שבהם אתר מרשה לדפים מאתר אחר לקרוא ממנו.
personal data
מידע על אדם מזוהה או שאפשר לזהות.
retention
כמה זמן שומרים מידע, ומתי מוחקים אותו.

14.16מה הלאה

המערכת בנויה: שני שירותים, בסיסי נתונים, אירועים, CI, סביבות, ניטור, ועכשיו גם מי מורשה למה. כל זה נבנה כאן על ידי אדם אחד, עם ספר שאומר מה הצעד הבא. בעבודה אמיתית אין ספר: יש צוות. מישהו מבקש משהו במשפט אחד בצ'אט, ואתם צריכים להבין מה בדיוק, לכתוב את זה כמשימה, להחליט לפני שכותבים קוד אם צריך מסמך תכנון, להעריך כמה זמן זה ייקח (ולטעות בצורה סבירה), ולהשאיר אחריכם תיעוד שמישהו אחר יבין.

משימות (tickets), מסמך תכנון קצר, הערכות זמן ותיעוד, וכרטיס אחד שאתם לוקחים מהתיאור ועד pull request ממוזג: פרק 15: עבודה בצוות.
